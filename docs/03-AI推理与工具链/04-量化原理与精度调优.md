# 量化原理与精度调优

## 本章解决什么

「量化之后精度掉了」是社区里出现频率最高的一类问题，也是最难自查的一类 —— 因为量化链路有五个环节，每一环节出错的表现都可能很像。

这一章给出三样东西：量化到底在做什么（机制），精度掉了按什么顺序查（顺序），以及每一步用什么工具什么命令验证（手段）。

**核心方法是「逐阶段对拍」**：把 `onnx → original_float.onnx → optimized_float.onnx → calibrated.onnx → quantized.onnx → .bin` 这条链上的每一个中间产物都单独跑一遍，找出精度在哪一步掉下去。跳过这一步直接猜「是不是量化参数不对」，是最常见的浪费时间的做法。

> 来源：官方文档 FAQ/toolchain（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）「模型精度调优 checklist」
> 来源：官方文档 Advanced_development/toolchain_development/overview（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/toolchain_development/overview）

## 量化在做什么

### 为什么必须量化

官方写得很直接：

> 「目前在 GPU 上训练的模型大部分都是浮点模型，即参数使用的是 float 类型存储；D-Robotics BPU 架构的处理器使用的是 INT8 的计算精度（业内处理器的通用精度），只能运行定点量化模型。」

> 来源：官方文档 Advanced_development/toolchain_development/overview（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/toolchain_development/overview）

BPU 没有 FP32 通路。这不是「FP32 慢一点」，是「FP32 根本不支持」。所以量化不是可选的优化，是上板的前置条件。

### PTQ 与 QAT

官方把量化分成两类：

> 「依据是否要对量化后的参数进行调整，我们可以将量化方法分为 QAT（Quantification Aware Training）量化感知训练和 PTQ（Post-Training Quantization）训练后量化。
> D-Robotics 算法工具链主要使用的是**训练后量化 PTQ** 方法，只需使用一批校准数据对训练好的浮点模型进行校准，将训练过的 FP32 网络直接转换为定点计算的网络，此过程中无需对原始浮点模型进行任何训练，只对几个超参数调整就可完成量化过程」

> 来源：官方文档 Advanced_development/toolchain_development/overview（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/toolchain_development/overview）

两者的定位差异：

| | PTQ | QAT |
| --- | --- | --- |
| 需要训练数据 | 只要校准集（100 张左右） | 需要完整训练集 |
| 需要重训 | 不需要 | 需要微调 5~10 epoch |
| 时间成本 | 分钟级 | 小时级 |
| 精度上限 | 受模型结构限制 | 接近浮点 |
| 工具链支持 | `hb_mapper` 全流程 | `horizon_plugin_pytorch` |
| 产物 | `.bin` | `.hbm` |

官方在 FAQ 里对两种产物的区别有一句明确的说明：「它生成的模型文件（如 `.bin` 用于 PTQ，`.hbm` 用于 QAT）」。

> 来源：官方文档 FAQ/toolchain（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）Q5

**需要特别提醒**：QAT 在社区几乎没有可复现的公开案例。社区帖 34983 里，社区管理员对「有没有 QAT 例程」这个问题的回答是：

> 「QAT 由于难度过于深度，社区上没有对应案例，有关 QAT 的内容一般以手册内容为准」

> 来源：社区帖 34983（https://forum.d-robotics.cc/t/topic/34983）

所以本章 95% 的篇幅在讲 PTQ —— 那才是实际能跑通的路。

### 校准（calibration）的机制

PTQ 的核心是给每一层定一个「阈值」：这一层输出值的动态范围有多大，从而算出 `scale`（缩放系数）和 `zero_point`（零点）。

官方把这一步叫 calibrate，日志里能看到：

```
2026-05-07 11:55:26,384 file: model_builder.py func: model_builder line No: 35 Start to calibrate the model.
...
2026-05-07 12:16:04,892 file: model_builder.py func: model_builder line No: 38 End to calibrate the model.
2026-05-07 12:16:06,040 file: model_builder.py func: model_builder line No: 265 Saving model to: motionbert_lite_calibrated_model.onnx.
```

> 来源：社区帖 34983（https://forum.d-robotics.cc/t/topic/34983）

校准有四种策略，可选的 `calibration_type`：

| 值 | 原理 | 适用 |
| --- | --- | --- |
| `max` | 取绝对值最大值（可配 `max_percentile` 截断） | 通用，最稳定 |
| `kl` | KL 散度最小化，让量化前后分布最接近 | 分布有长尾的激活 |
| `default` | 工具自动搜索 | 不确定时用它 |
| `mix` | 混合策略 | 追求精度、可接受更慢 |

`max_percentile` 是 `max` 策略的截断分位数，含义是「只取 99.9% 分位的值作为范围上限」，避免单个离群点把整层的 scale 撑得过大。常见取值 `0.99999` / `0.99995` / `0.9999` / `0.9995` / `0.999`。

社区帖 34885 的配置示例完整展示了这几个参数的关系：

```yaml
calibration_parameters:
  cal_data_dir: '../hb_calibration_data_f32'
  cal_data_type: 'float32'
  preprocess_on: False
  per_channel: True
  # 取值: 'default' 'skip' 'ml'
  calibration_type: 'max'
  # 取值: 0.99999 0.99995 0.9999 0.9995 0.999
  max_percentile: 0.9999
```

> 来源：社区帖 34885（https://forum.d-robotics.cc/t/topic/34885）

工具在 `default` 模式下会做自动搜索，日志里的选择过程是可见的：

```
The activation calibration parameters:
calibration_type: ['max', 'kl']
max_percentile: [0.99995, 1.0]
per_channel: [True, False]
asymmetric: [True, False]
The modelwise search parameters:
similarity: 0.995

```

最后输出最终选择：

```

```

> 来源：社区帖 34983（https://forum.d-robotics.cc/t/topic/34983）

这段日志说明：`default` 不是「不做校准」，而是「把上面这组组合都试一遍，选余弦相似度最高的」。代价是校准时间显著变长（那个案例里从 11:55 跑到 12:16，21 分钟）。

### 反量化与 requantize

量化模型的每一层输出都是 int8。当两个量化层串联时，前一层的输出 scale 和后一层的输入 scale 不同，中间必须插一个 **requantize** —— 它把数据从一种定点表示转到另一种。日志里能看到这种节点：

```
/blocks_ts.0/attn_s/Mul_output_0_calibrated_Requantize  BPU id(0)  HzRequantize  --  --  int8
```

> 来源：社区帖 34983（https://forum.d-robotics.cc/t/topic/34983）

当数据要从 BPU 交给 CPU 算子时，还需要 **dequantize**（int8 → float）。这两个环节是精度损失的次要来源，但在「多子图 + 大量 CPU 算子」的模型上会累积得很明显。

板端读到的是最终结果，所以量化参数需要能在板端拿到 —— 3.5.0 的 `hbm_runtime` 通过 `output_quants` 暴露：

```python
tensor_qparams = model.output_quants[model_name][output_name]
print("scale:", tensor_qparams.scale)
print("zero_point:", tensor_qparams.zero_point)
print("type:", tensor_qparams.quant_type)   # NONE 或 SCALE
print("axis:", tensor_qparams.axis)
```

> 来源：官方文档 Basic_Application/multi_media_sp_dev_api/RDK_X5/pydev_multimedia_api_x5/ai-python-api（https://developer.d-robotics.cc/rdk_x_doc/Basic_Application/multi_media_sp_dev_api/RDK_X5/pydev_multimedia_api_x5/ai-python-api）

## 精度排查的官方五步法

官方给了一份 checklist，原文的要求是：

> 「请严格按照下图中步骤 1-5 来进行模型精度验证并保留每个步骤的代码和结果」
> 「在进行排查前，请确认当前模型转换所用的 Docker 镜像或转换环境版本，并保留版本信息」

> 来源：官方文档 FAQ/toolchain（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）

这五步的骨架是：

| 步 | 对比对象 | 期望 | 若不符，说明 |
| --- | --- | --- | --- |
| 1 | 浮点 onnx vs 训练框架结果 | 完全一致（nv12 除外） | 你的预处理/后处理写错了 |
| 2 | original_float.onnx vs 浮点 onnx | 完全一致 | yaml 的 norm 配置与代码重复/冲突 |
| 3 | optimize_float.onnx vs original_float.onnx | 完全一致 | 图优化引入了误差 |
| 4 | quantized.onnx 的精度指标 | 满足预期 | 量化本身掉点 |
| 5 | .bin vs quantized.onnx | 小数点后 2~3 位对齐 | 编译/板端环节有问题 |

**这个顺序的价值在于「排除法」**：如果第 1 步就不对，后面全都不用看；如果第 4 步不对但第 3 步对，那问题一定在量化参数；如果前四步都对、只有第 5 步不对，那问题在编译或板端。

### 第 1 步：验证浮点 onnx

```python
from horizon_tc_ui import HB_ONNXRuntime
import numpy as np

def preprocess(input_name):
    # BGR->RGB、Resize、CenterCrop
    # HWC->CHW
    # normalization
    return data

sess = HB_ONNXRuntime(model_file=MODEL_PATH)
input_names  = [i.name for i in sess.get_inputs()]
output_names = [o.name for o in sess.get_outputs()]

feed_dict = {name: preprocess(name) for name in input_names}
# 原始浮点 onnx，dtype=float32，input_offset=0
outputs = sess.run_feature(output_names, feed_dict, input_offset=0)
postprocess(outputs)
```

> 来源：官方文档 FAQ/toolchain（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）

这一步的期望是「与训练后的模型推理结果完全一致（nv12 格式除外，可能会引入少许差异）」。

**如果这一步就不对，后面所有排查都是浪费。** 说明你的 Python 预处理/后处理代码本身有问题，与工具链无关。

### 第 2 步：验证 yaml 与前处理是否重复

这一步是整份 checklist 里最关键、也最容易被跳过的一步。官方特别解释了 `HzPreprocess` 节点：

> 「由于 HzPreprocess 节点的存在，会使得转换后的模型其预处理操作可能会和原始模型有所不同，该算子是在进行模型转换时，根据 yaml 配置文件中的配置参数（`input_type_rt`、`input_type_train` 以及 `norm_type`、`mean_value`、`scale_value`）来决定是否为模型加入 HzPreprocess 节点」

> 来源：官方文档 FAQ/toolchain（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）

然后是这段极其重要的说明：

> 「理想状态下，这个 HzPreprocess 节点应该完成 `input_type_rt` 到 `input_type_train` 的完整转换，但实际情况是整个 type 转换过程需要使用 D-Robotics AI 芯片硬件完成，但 ONNX 模型里面并没有包含硬件转换的部分，因此 ONNX 的真实输入类型会使用一种中间类型，这种中间类型就是硬件对 `input_type_rt` 的处理结果类型，故针对图像输入数据类型为：RGB/BGR/NV12/YUV444/GRAY，并且数据 dtype=uint8 的模型时，在预处理代码中**需要做 -128 的操作**，featuremap 数据类型因为使用的是 float32，因此预处理代码中**不需要 -128** 的操作；original_float.onnx 的数据 layout(NCHW/NHWC)会保持和原始浮点模型的输入 layout 一致。」

> 来源：官方文档 FAQ/toolchain（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）

**这条「-128」是一半以上「量化精度掉」问题的真正原因。** 只要你的 yaml 是 `input_type_train: rgb`（或 bgr/nv12/yuv444/gray）且数据是 uint8，那么在这一步的 Python 预处理里就必须减 128，否则对拍结果永远对不上。

代码模板：

```python
def preprocess(input_name):
    # BGR->RGB、Resize、CenterCrop
    # HWC->CHW（看 onnx 输入节点 shape 决定是否转）
    # normalization（若已在 yaml 里配了 norm，这里不要重复做）
    # -128（图像输入模型：仅 hb_session.run 接口需要手动 -128，
    #       其他接口通过 input_offset 控制）
    return data

# 图像输入模型（RGB/BGR/NV12/YUV444/GRAY），dtype=uint8
outputs = sess.run(output_names, feed_dict, input_offset=128)

# featuremap 模型，dtype=float32
outputs = sess.run_feature(output_names, feed_dict, input_offset=0)
```

> 来源：官方文档 FAQ/toolchain（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）

注意 `input_offset=128` 和手工 `-128` 是**同一件事的两种写法**，只能做一次。两个都做就是减 256。

### 第 3 步：验证图优化

对比 `optimize_float.onnx` 与 `original_float.onnx`，期望「完全一致」。这一步基本不会出问题，但如果前面都对、这里不对，说明 `constant_folding` 之类的 pass 有 bug。

日志里能看到这一步在做什么：

```
After constant_folding, the number of nodes has changed from 1423 to 1107.
After constant_folding, the number of parameters has changed from 15970727 to 15970727.
```

> 来源：社区帖 34983（https://forum.d-robotics.cc/t/topic/34983）

节点数从 1423 降到 1107，参数数不变 —— 这是正常的常量折叠。如果参数数也大幅变化，就要怀疑折叠逻辑出错了。

### 第 4 步：验证量化精度

跑 `quantized.onnx`，和浮点结果对比。这一步看两个数：

**余弦相似度**（`Cosine Similarity`）：越接近 1 越好。经验判据：

| 相似度 | 判断 |
| --- | --- |
| ≥ 0.999 | 优秀 |
| 0.99 ~ 0.999 | 正常 |
| 0.98 ~ 0.99 | 需要关注 |
| < 0.98 | 该层有问题 |

**Chebyshev Distance**：越小越好。社区经验是「`cls` 输出的 Chebyshev < 0.5 基本就能正常检测；> 2.0 检测会出问题；`bbox` 输出可以稍大一些（因为 DFL 解码有容错性）」。

> 来源：社区帖 34084（https://forum.d-robotics.cc/t/topic/34084）

量化报告在 `*_quant_info.json`，也可以直接看日志里的算子表：

### 第 5 步：验证 .bin 与 quantized.onnx 一致

```bash
hb_model_verifier \
  --original_model model.onnx \
  --quantized_model model_quantized_model.onnx \
  --bin_model model.bin
```

官方对这一工具的要求是：

> 「使用 `hb_model_verifier` 工具验证 `quantized.onnx` 和 `.bin` 的一致性，模型输出应至少满足小数点后 2-3 位对齐」
> 「若模型一致性校验通过，则请仔细检查开发板端的前、后处理代码！若 `quantized.onnx` 与 `.bin` 模型一致性校验失败，请联系 D-Robotics 技术人员」

> 来源：官方文档 FAQ/toolchain（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）

**注意括号里那句话的指向**：一致性校验**通过**之后，问题就在你的板端前后处理代码里，不在模型。这是一个非常强的分流判据。

社区帖 34824 的用户就卡在这里：

> 「使用工具 `hb_verifier` 对比 `*_quantized_model.onnx` 与 `.bin` 模型，也是会提示严重不符」

> 来源：社区帖 34824（https://forum.d-robotics.cc/t/topic/34824）

最后查出来的原因是系统版本 —— 3.0.0 的 `hobot_dnn` 对这个 5 通道 featuremap 输入支持不好，升级到 3.5.0 后「板端部署的精度与 `*_quantized_model.onnx` 量化模型精度基本一致」。这是「第 5 步失败但模型其实没问题」的典型案例。

## 精度掉了的排查顺序（实操版）

官方的五步法是「验证链」，实际排查时还要加一层「先看现象再决定从哪步开始」。下面是压缩后的实操顺序。

### 第 0 步：先分清「掉多少」

| 现象 | 优先怀疑 |
| --- | --- |
| 完全检不出任何目标，或输出值域明显异常（如 `-300000`） | 反量化/预处理，不是量化参数 |
| 能检出但框错乱、数量异常 | 输出格式（NCHW/NHWC）、类别数、anchors |
| 能检出但置信度偏低、漏检 | 校准数据质量或量化策略 |
| ONNX 正常、bin 异常、verifier 通过 | 板端前后处理代码 |
| ONNX 正常、bin 异常、verifier 失败 | 系统版本或工具链版本 |

**「完全检不出」和「精度略降」是两个完全不同的问题，不要用同一套方法查。** 前者几乎都是工程错误（预处理、反量化、格式），后者才是真正的量化掉点。

社区帖 34084 的作者把这个区分讲得很清楚 —— 他的症状是「板端推理所有 cls 输出为强负数（max≈-10~-21），sigmoid 后为 0」，根因是校准数据做了双重归一化，属于工程错误，不是量化算法问题。

> 来源：社区帖 34084（https://forum.d-robotics.cc/t/topic/34084）

### 第 1 步：核对预处理一致性（最高频根因）

官方把这条列为 Pipeline 检查的第一项：

> 「**与训练时是否一致**：这是最关键的一点。确保部署时的预处理操作（如 resize 方式、归一化参数、均值方差、颜色空间转换如 RGB/BGR、letterbox 的 padding 方式和颜色等）与模型训练时所用的预处理**完全一致**。任何细微的差异都可能导致模型性能急剧下降。」

> 来源：官方文档 FAQ/toolchain（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）Q13

自查清单：

| 检查项 | 常见错误 |
| --- | --- |
| RGB vs BGR | 训练用 RGB，板端 cv2 读图默认 BGR，没转 |
| 归一化 | 校准数据 /255 了，yaml 里又配了 `scale_value` |
| resize 方式 | 训练用 letterbox（灰边 114），板端直接 `cv2.resize` 拉伸 |
| padding 值 | letterbox 灰边用了 0 而不是 114 |
| mean/std | 训练做 `(x-mean)/std`，yaml 里 `norm_type` 写成 `data_scale` |
| -128 | 图像输入模型，预处理没减 128 |

第三、四项是 YOLO 系最常见的。社区的 letterbox 实现（灰边 114）与训练时的 letterbox 必须完全对齐：

```python
canvas = np.full((640, 640, 3), 114, dtype=np.uint8)
top  = (640 - new_h) // 2
left = (640 - new_w) // 2
canvas[top:top+new_h, left:left+new_w] = resized
```

> 来源：社区帖 34084（https://forum.d-robotics.cc/t/topic/34084）

### 第 2 步：检查校准数据

三个维度，缺一不可：

| 维度 | 检查方法 | 判据 |
| --- | --- | --- |
| 数值范围 | 读第一个文件看 min/max | `max` 应接近 255（配 `scale_value` 时） |
| 通道顺序 | 存一张图出来肉眼比对 | 与 `input_type_train` 一致 |

**定位到敏感层之后怎么改？** 三条路，按侵入性从低到高：

**路径 A：调整校准策略**

```yaml
calibration_parameters:
  calibration_type: 'kl'        # 从 max 换成 kl
  max_percentile: 0.9999        # 从 0.99999 降到 0.9999
  per_channel: True             # 开启逐通道
```

官方对 `max_percentile` 的说明是「max 校准方式的参数」，社区实践是「数据量增加后可进一步降低」。

> 来源：社区帖 34983（https://forum.d-robotics.cc/t/topic/34983）

**路径 B：敏感层用 int16**

```yaml
model_parameters:
  node_info: {
    "Conv_170": {'ON': 'BPU', 'InputType': 'int16', 'OutputType': 'int16'},
    "Conv_171": {'ON': 'BPU', 'InputType': 'int16', 'OutputType': 'int16'},
    "Sigmoid_230": {'ON': 'BPU', 'InputType': 'int16', 'OutputType': 'int16'}
  }
```

> 来源：社区帖 34824（https://forum.d-robotics.cc/t/topic/34824）

int16 能把动态范围扩大 256 倍，代价是这些层慢一倍、显存占用翻倍。**只对确实掉点的少数几层用**，不要全局开。

**路径 C：敏感层移到 CPU**

```yaml
model_parameters:
  node_info: {
    "ScatterND_337": {'ON': 'CPU'},
    "Where_263_add": {'ON': 'CPU'}
  }
```

> 来源：社区帖 34824（https://forum.d-robotics.cc/t/topic/34824）

CPU 是 FP32，精度无损。代价是数据要在 BPU 和 CPU 之间来回搬，性能损失很大 —— 但通常比 int16 更彻底。

**这两条路径不是等价的，选择依据是「这类算子在模型里的数量」。** 一个末端 Softmax 移 CPU 只多一次搬运；一段 ScatterND 密集的 backbone 移 CPU 会把模型切碎。

### 第 4 步：检查算子回退造成的子图切分

这一步经常被漏掉，但它是「ONNX 精度正常、bin 精度异常」的常见原因。社区帖 34824 的官方分析：

> 「`*_quantized_model.onnx` 是在 x86 CPU 上通过 ONNX Runtime 模拟运行的。它模拟的是"理想量化"，即：BPU 算子输出 int8 → 反量化为 float32 → 输入给 CPU 算子 → CPU 算子输出 float32 → 量化为 int8 → 输入给下一个 BPU 算子。
> `.bin` 是板端实际运行。在 BPU 和 CPU 切换时，数据需要在 DDR 中传输。如果编译器生成的反量化（Dequantize）和重量化（Requantize）参数（Scale/ZeroPoint）与 ONNX 模拟时的逻辑有细微偏差（例如对齐方式、舍入模式 RoundHalfToEven vs RoundHalfUp），误差会在多次 BPU<->CPU 切换中累积。」

> 来源：社区帖 34824（https://forum.d-robotics.cc/t/topic/34824）

**处置原则：减少切换次数。** 要么把整条敏感路径全移到 CPU，要么全留在 BPU，不要让它一半一半。

```yaml
# 方案 A：整条路径 CPU
node_info: {
  "Conv_170": {'ON': 'CPU'},
  "Conv_171": {'ON': 'CPU'},
  "Add_172": {'ON': 'CPU'},
  "Concat_178": {'ON': 'CPU'},
  "Conv_179": {'ON': 'CPU'},
  "Sigmoid_230": {'ON': 'CPU'},
  "ScatterND_337": {'ON': 'CPU'},
  "ScatterND_414": {'ON': 'CPU'}
}
```

> 来源：社区帖 34824（https://forum.d-robotics.cc/t/topic/34824）

### 第 5 步：检查系统版本与接口

**这一步要放在靠后位置，但绝对不能漏。** 社区帖 34824 的最终结论是：

> 「目前 RDK 系统由 3.0.0 升级到 3.5.0 版本后，板端部署的精度与 `*_quantized_model.onnx` 量化模型精度基本一致；核心问题在于：当前系统版本是初始版本，对于 featuremap 数据的输入支持比较差」

> 来源：社区帖 34824（https://forum.d-robotics.cc/t/topic/34824）

官方在另一处给出了接口层面的原因：

> 「原接口对 featuremap 兼容不好，所以推出了接口」

> 来源：社区帖 34824（https://forum.d-robotics.cc/t/topic/34824）

同类案例还有社区帖 34918：用户在 3.5.0 上部署一个 3D 卷积模型，`quantized.onnx` 精度正常（87%），`.bin` 只有 51%，`hb_verifier` 一致性检验**通过**。官方最后给出的排查方向是：

注意这个案例的三个关键词：**反量化、预处理、-128**。这三个词与前面第 1 步、第 2 步完全对应 —— 说明即使 `verifier` 通过，问题也大概率在这三处。

## 用余弦相似度定位敏感算子：完整案例

### 问题描述

## 一个必须警惕的精度陷阱：删 Dequantize 换性能

社区帖 35445 记录了一个「为了性能删掉反量化节点，结果精度全崩」的完整过程：

> 「浮点模型 → hb_mapper INT8 量化 → hb_model_modifier 删除了所有 10 个 Dequantize 节点 → 输出纯 int32 累加器值」

删完之后的现象：

| 项 | 状态 |
| --- | --- |
| 帧率 | ~30 FPS，纯 BPU 推理，快 |
| 输出格式 | 10 路分离 int32，NCHW 布局 |
| 值域 | `cls` 约 `[-300000, -8000]` |
| 直接 sigmoid | 极端负值→0 被过滤；接近 0 的值→0.5 成噪声 |
| Scale 乘回去 | scale 值是对的（与日志匹配），但乘完值在 `[-60, -1.6]`，sigmoid 全 0 |

> 来源：社区帖 35445（https://forum.d-robotics.cc/t/topic/35445）

**根因**：删掉 Dequantize 节点后，`zero_point` 信息丢了。只乘 `scale` 是不够的，正确公式是 `(int32 - zero_point) * scale`。

这个案例给出的两条路：

- **A（不推荐）**：继续用 int32 输出，调高 `CONF_THRES` 到 0.55~0.60 过滤噪声。代价是「置信度不再有物理含义（0.5 不代表 50% 概率）」。
- **B（推荐）**：不删 Dequantize 节点，让 BPU 自动反量化，输出正常 float32 logit。

> 来源：社区帖 35445（https://forum.d-robotics.cc/t/topic/35445）

**这条经验的核心是**：不要为了省几毫秒去删工具链生成的节点。删掉的是「精度正确性所依赖的元信息」，不是「冗余计算」。

## 板端反量化的正确写法

3.5.0 的 `hbm_runtime` 把量化参数暴露成结构化对象，正确用法是：

```python
import numpy as np
from hbm_runtime import HB_HBMRuntime, hbDNNQuantiType

model = HB_HBMRuntime("/path/to/model.bin")
model_name = model.model_names[0]

# 取出原始输出与量化参数
raw_outputs = model.run(input_tensor)

def dequantize(tensor: np.ndarray, qp) -> np.ndarray:
    """按 quant_type 决定是否反量化"""
    if qp.quant_type == hbDNNQuantiType.NONE:
        # 模型输出已经是 float，不要重复处理
        return tensor.astype(np.float32, copy=False)
    # SCALE 类型：float = (int - zero_point) * scale
    return (tensor.astype(np.float32) - qp.zero_point) * qp.scale

for out_name, raw in raw_outputs[model_name].items():
    qp = model.output_quants[model_name][out_name]
    val = dequantize(raw, qp)
    print(out_name, qp.quant_type.name, val.shape, val.min(), val.max())
```

> 来源：官方文档 Basic_Application/multi_media_sp_dev_api/RDK_X5/pydev_multimedia_api_x5/ai-python-api（https://developer.d-robotics.cc/rdk_x_doc/Basic_Application/multi_media_sp_dev_api/RDK_X5/pydev_multimedia_api_x5/ai-python-api）

三个要点：

1. **先判 `quant_type`**，`NONE` 就直接用，不要再乘 scale。
2. **`zero_point` 不能省**，公式是 `(v - zp) * scale`，不是 `v * scale`。
3. **per-channel 量化时 `scale` 是数组**，`axis` 指明量化轴，需要 reshape 后才能广播。

官方示例里的标准实现叫 `dequantize_outputs(outputs, output_quants)`，说明是「结果反量化，输入：模型输出，指定类型，返回：反量化后的结果」。

> 来源：官方文档 Basic_Application/pydev_demo_sample/RDK_X5/detection_sample（https://developer.d-robotics.cc/rdk_x_doc/Basic_Application/pydev_demo_sample/RDK_X5/detection_sample）

## 一个精简版排查脚本骨架

把五步法写成可执行的检查函数，每次改完 yaml 跑一遍：

```python
#!/usr/bin/env python3
"""量化精度排查骨架 —— 在 OE Docker 内运行"""
import json, subprocess, sys
from pathlib import Path

WORK = Path("./model_output")
PREFIX = "obstacle"

STAGES = [
    ("original_float", "浮点模型 + HzPreprocess"),
    ("optimized_float", "图优化后"),
    ("calibrated", "校准后"),
    ("quantized", "量化后"),
]

def check_artifacts():
    """第 0 关：确认四个中间产物都在"""
    missing = []
    for stage, _ in STAGES:
        p = WORK / f"{PREFIX}_{stage}_model.onnx"
        if not p.exists():
            missing.append(str(p))
    if missing:
        print("[FAIL] 缺少中间产物：")
        for m in missing:
            print("   ", m)
        sys.exit(1)
    print("[OK] 四个中间产物齐全")

def check_quant_report():
    """第 4 关：读量化报告，列出相似度最低的层"""
    j = WORK / f"{PREFIX}_quant_info.json"
    if not j.exists():
        print("[SKIP] 无 quant_info.json")
        return
    data = json.loads(j.read_text())
    rows = []
    for name, info in data.items():
        if isinstance(info, dict) and "cosine_similarity" in info:
            rows.append((info["cosine_similarity"], name))
    rows.sort()
    print(f"[INFO] 共 {len(rows)} 层，相似度最低 10 层：")
    for sim, name in rows[:10]:
        flag = " <== 需关注" if sim < 0.98 else ""
        print(f"   {sim:.6f}  {name}{flag}")

def check_bin_consistency():
    """第 5 关：bin 与 quantized.onnx 一致性"""
    cmd = ["hb_model_verifier",
           "--original_model", str(WORK / f"{PREFIX}_original_float_model.onnx"),
           "--quantized_model", str(WORK / f"{PREFIX}_quantized_model.onnx"),
           "--bin_model", str(WORK / f"{PREFIX}.bin")]
    print("[RUN]", " ".join(cmd))
    r = subprocess.run(cmd, capture_output=True, text=True, encoding="utf-8", errors="replace")
    print(r.stdout[-2000:])
    if r.returncode != 0:
        print("[FAIL] 一致性校验失败，需联系官方")

if __name__ == "__main__":
    check_artifacts()
    check_quant_report()
    check_bin_consistency()
```

这个骨架不是官方工具，是把官方的五步法串起来的最小实现。实际使用时按自己的产物命名规则改 `PREFIX` 和 `STAGES`。

## 常见误区

**误区一：精度一掉就去调 `calibration_type`。** 官方五步法的顺序是有道理的：前四步分别是「验证预处理」「验证 yaml」「验证图优化」「验证量化」。跳过前三步直接调量化参数，很可能在调一个根本不存在的问题。真正的高频根因是**预处理不一致**和**校准数据双重归一化**，两者都不在量化参数里。

**误区二：以为 `hb_verifier` 通过就说明模型没问题。** 社区帖 34824 和 34918 两个案例里，`verifier` 都通过了，但实际精度都不对。前者根因是系统版本对 featuremap 支持不好，后者根因是反量化/预处理/`-128`。`verifier` 验证的是「编译链路是否正确」，不验证「你的前后处理是否与训练对齐」。

**误区三：以为 MatMul 和 Softmax 一样能上 int16。** 日志会把 MatMul 静默降回 int8：`the quantization parameters of conv int16 is not supported ... will be set back to int8`。所以「Attention 层全设 int16」这个方案在工具链上是不成立的。

**误区四：为了性能删 Dequantize 节点。** 删掉之后值域会变成 `[-300000, -8000]` 这种 int32 累加器值，而且 `zero_point` 信息丢失，只乘 scale 还原不回来。正确做法是保留节点，或按 `(v - zp) * scale` 手动还原。

**误区五：只看总余弦相似度，不看单层。** 最终输出相似度 0.999 里可能藏着某一层 0.92 的 Softmax。要看 `*_quant_info.json` 里的逐层数据，用 `sort -k5 -n` 挑出最低的 20 层逐个看。

**误区六：认为 QAT 是「更高级的 PTQ」，随时可以升级过去。** QAT 需要完整训练集 + 模型改造 + 重训，产物是 `.hbm` 而不是 `.bin`，而且社区几乎没有可复现案例（官方社区管理员原话：「QAT 由于难度过于深度，社区上没有对应案例」）。在 PTQ 上把工程问题修干净，比迁移到 QAT 的收益大得多。
