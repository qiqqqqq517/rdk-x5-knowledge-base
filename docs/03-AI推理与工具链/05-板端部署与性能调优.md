# 3.5 板端部署与性能调优

## 本章解决什么

模型转换成功、`.bin` 也生成了，但上板一跑发现帧率不对 —— 这是整条链路上最后也最容易被误判的一环。

这一章给出一套测量与归因的方法：先把「性能」拆成可分别测量的几段，再用工具分别测出来，最后按数据定位瓶颈在哪一段。同时覆盖多线程、零拷贝、VIO/BPU 直通这几条实际能提升吞吐的工程手段。

核心观点只有一句：**「模型跑得慢」这个描述没有信息量**。真正有用的信息是「BPU 推理 3.3ms，但线程等待 83.5ms」，前者说明模型没问题，后者说明工程有问题 —— 这两个结论导向完全不同的修法。

> 来源：官方文档 Basic_Application/pydev_demo_sample/RDK_X5/detection_sample（https://developer.d-robotics.cc/rdk_x_doc/Basic_Application/pydev_demo_sample/RDK_X5/detection_sample）
> 来源：官方文档 FAQ/toolchain（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）

## 3.5.1 先建立正确的性能模型

### 3.5.1.1 端到端延迟的四段结构

一次完整的推理，时间花在四个地方：

```
[采集] → [预处理] → [BPU 推理] → [后处理] → [显示/发布]
   ↑         ↑           ↑            ↑
 相机/USB   resize      BPU 计算     解码+NMS
           格式转换     DDR 搬运
```

任何一段出问题，端到端帧率都会掉，但**现象完全不同**。不分段测量就没法归因。

真实案例对比（同一个板子，两台机器，三组数字）：

| 案例 | BPU 推理 | CPU 侧 | 端到端 | 瓶颈 |
| --- | --- | --- | --- | --- |
| 34885 优化前 | 104ms | 182ms（含 148ms layout convert） | 286ms | CPU 侧 layout 转换 |
| 34885 优化后 | — | — | 55ms | 已达标 |
| 35149 | 3.3ms | 等待 52~106ms | 20~29 FPS | 线程同步等待 |
| 35444 优化后 | 4.4ms | 42.8ms | ~20 FPS | CPU 后处理 |

> 来源：社区帖 34885（https://forum.d-robotics.cc/t/topic/34885）
> 来源：社区帖 35149（https://forum.d-robotics.cc/t/topic/35149）
> 来源：社区帖 35444（https://forum.d-robotics.cc/t/topic/35444）

三行数据说明同一个道理：**BPU 推理耗时可能只占端到端的一小部分**。35149 那台机器 BPU 只花 3.3ms（对应 300+ FPS），端到端却只有 20 FPS —— BPU 有 94% 的时间在等。

### 3.5.1.2 官方工具给出的分段耗时

TROS 的 `dnn_node_example` 直接打印三段耗时，这是最省事的观测点：

```
[example-3] Sub img fps: 30.45, Smart fps: 30.45, pre process time ms: 2, infer time ms: 32, post process time ms: 3
```

三个字段分别是预处理、推理、后处理。上面这组数字里 `infer time ms: 32` 是 BPU 推理，占比 86%，属于「模型本身是瓶颈」；而下面这组就完全不同：

```
[example-3] Sub img fps: 35.19, Smart fps: 35.50, pre process time ms: 4, infer time ms: 28, post process time ms: 14
[example-3] Sub img fps: 30.33, Smart fps: 30.36, pre process time ms: 2, infer time ms: 32, post process time ms: 3
```

后处理在 3~14ms 之间跳，说明后处理有长尾（NMS 遇到密集目标时变慢），这类抖动靠平均值看不出来。

> 来源：社区帖 34523（https://forum.d-robotics.cc/t/topic/34523）

### 3.5.1.3 两个「性能」的定义必须分清

社区管理员对这两个概念给过一次非常清晰的界定：

> 「- 单线程延迟为单帧，单线程，单 BPU 核心的延迟，BPU 推理一个任务最理想的情况。
> - 多线程帧率为多个线程同时向 BPU 塞任务，每个 BPU 核心可以处理多个线程的任务，一般工程中 2 个线程可以控制单帧延迟较小，同时吃满所有 BPU 到 100%，在吞吐量（FPS）和帧延迟间得到一个较好的平衡。」

> 来源：社区帖 34885（https://forum.d-robotics.cc/t/topic/34885）

对应的测量方式：

| 你想知道 | 用什么参数测 | 含义 |
| --- | --- | --- |
| BPU 本身的极限 | `--thread_num 2` 或更高 | 多线程喂任务，测吞吐上限 |
| 单帧真实延迟 | `--thread_num 1` | 模拟实际单线程应用 |
| 瓶颈在 BPU 还是 CPU | 两者对比 | 差距大说明 CPU 侧是瓶颈 |

**这两个数字经常差 3 倍以上，报性能时必须说明用的是哪个。**「我的模型能跑 300 FPS」和「我的应用能跑 20 FPS」可以同时为真。

## 3.5.2 测量工具

### 3.5.2.1 hrt_model_exec：板端性能基准

`hrt_model_exec` 是板端执行 `.bin` 模型的命令行工具，官方说明是「用于在板端执行转换好的 `.bin` 模型，进行推理验证和性能测试」。

> 来源：官方文档 FAQ/toolchain（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）Q14

它的位置不固定，可能在 `/usr/bin`、`/opt/hobot/bin`，也可能需要从工具链包的 `ddk/package/board/<target_os>/bin/` 手动拷过来。官方原文：

> 「这些工具可能预装在 RDK 系统镜像的 `/usr/bin` 或 `/opt/hobot/bin` 等路径下。也可能包含在您下载的算法工具链包（解压后）的某个子目录中……您需要将这些工具手动拷贝到板卡的某个可执行路径下（如 `/usr/local/bin`）或直接在板卡上指定其完整路径运行。」

> 来源：官方文档 FAQ/toolchain（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）Q14

**三个最常用的子命令：**

```bash
# 1. 看模型结构（输入输出 shape / type / layout）
hrt_model_exec model_info --model_file /path/to/model.bin

# 2. 测性能（吞吐）
hrt_model_exec perf --model_file /path/to/model.bin --thread_num 2 --loop_num 100

# 3. 测性能并生成 profiler 报告
hrt_model_exec perf --model_file /path/to/model.bin --thread_num 1 --profile_path="."
```

`perf` 的参数里，`--thread_num`、`--core_id`、`--frame_count`（或 `--loop_num`）至少要显式给。社区里有一次「`hrt_model_exec perf` 卡住不动、无任何输出」的求助，官方答复是：

> 「Device 端 `hrt_model_exec perf` 命令行参数没有指定完整，在做性能评测时，除了指定 `model_file` 外，还需指定 `core_id`、`thread_num` 和 `frame_count`。建议使用 `./hrt_model_exec -h` 命令查看使用帮助。」

> 来源：社区帖 26372（https://forum.d-robotics.cc/t/topic/26372）

### 3.5.2.2 profiler.csv：定位算子落点

`--profile_path` 生成的 `profiler.csv` 是排查「哪些算子还在 CPU」的原始数据。社区给出的用法：

> 「生成的 profiler.csv 里有 `BPU_NodeName`、`CPUNodeType_NodeName` 和 `BPU_inference_time_cost` / `CPU_inference_time_cost`，能直接看出 Softmax 是否被留在 CPU。」

> 来源：社区帖 35833（https://forum.d-robotics.cc/t/topic/35833）

这个 csv 的价值在于：**转换阶段的 checker 是预测，profiler 是实测。** 两者不一致时以 profiler 为准。

另一种形式是 TROS 的 perf 日志，直接给出两段耗时：

```json
"processor_latency": {
  "BPU_inference_time_cost": { "avg_time": 4.428294, "max_time": 5.249, "min_time": 4.204 },
  "CPU_inference_time_cost": { "avg_time": 42.833678, "max_time": 78.157, "min_time": 33.877 }
},
"task_latency": {
  "TaskPendingTime": { "avg_time": 0.032966, "max_time": 0.182, "min_time": 0.021 },
  "TaskRunningTime": { "avg_time": 47.686092, "max_time": 70.312, "min_time": 39.089 }
}
```

> 来源：社区帖 35444（https://forum.d-robotics.cc/t/topic/35444）

读法：`BPU_inference_time_cost` 4.4ms、`CPU_inference_time_cost` 42.8ms —— CPU 侧是 BPU 的 10 倍，结论直接出来：**优化 yaml 没有任何用，要去改 CPU 侧代码**。

### 3.5.2.3 BPU 使用率：sysfs

```bash
# 单核使用率（0-100）
watch -n 1 'cat /sys/devices/system/bpu/bpu0/ratio'

# 当前使用 BPU 的进程及各自占用
cat /sys/devices/system/bpu/users

# 当前 BPU 频率
cat /sys/devices/system/bpu/bpu0/devfreq/devfreq*/cur_freq

# 支持的频率档位
cat /sys/devices/system/bpu/bpu0/devfreq/devfreq*/available_frequencies
```

> 来源：官方文档 Advanced_development/linux_development/driver_development/driver_bpu_sysfs_dev（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/driver_development/driver_bpu_sysfs_dev）

判断标准很简单：

| `ratio` | 含义 | 下一步 |
| --- | --- | --- |
| > 90% | BPU 满载 | 瓶颈在 BPU，优化模型或减负载 |
| 40~90% | 部分等待 | 看各段耗时找排队点 |
| < 20% | BPU 大部分空闲 | 瓶颈一定不在 BPU，查数据供给 |

社区帖 35342 的用户「跑了三个模型，bpu 撑死就 27 的使用率」，社区管理员的回答是：

> 「X5 BPU 为单核 一次只能推理一个模型，可以尝试增大 batch 和 使用更大尺寸的模型」

> 来源：社区帖 35342（https://forum.d-robotics.cc/t/topic/35342）

这句话解释了一个高频困惑：**多个模型同时跑不会提升 BPU 利用率，因为单核只能串行。** 27% 的利用率说明三个模型加起来也没喂满 BPU，要么模型太小，要么 CPU 侧供给跟不上。

## 3.5.3 归因流程：从现象到根因

### 3.5.3.1 场景一：BPU 推理耗时本身就大

**特征**：`infer time ms` 或 `BPU_inference_time_cost` 数值大（> 30ms），且 `ratio` 接近 100%。

三条优化路径，按有效性排序：

**路径 1：减少 CPU 算子与子图切分**

这是收益最大的一条。社区帖 34885 的完整过程：优化前 286ms，其中 `Layout Convert: 148ms`、`Less/Not/Cast: 8ms`、`Quantize/Dequantize: 22ms`。改用 `input_layout_rt: 'NHWC'` 并强制几个残留算子回 BPU 之后：

```yaml
node_info: {
  "Resize_220": {'ON': 'BPU', 'InputType': 'int8', 'OutputType': 'int8'},
  "Less_245":   {'ON': 'BPU', 'InputType': 'int8', 'OutputType': 'int8'},
  "Not_246":    {'ON': 'BPU', 'InputType': 'int8', 'OutputType': 'int8'},
  "Cast_247":   {'ON': 'BPU', 'InputType': 'int8', 'OutputType': 'int8'}
}
```

结果 286ms → 55ms，**5.2 倍**。

> 来源：社区帖 34885（https://forum.d-robotics.cc/t/topic/34885）

注意这里改的两处：`input_layout_rt` 从 `NCHW` 改成 `NHWC` 消除了 148ms 的 layout 转换；四个 CPU 算子强制上 BPU 消除了模型切分。两处都是「减少搬运」，不是「让计算变快」。

**路径 2：Softmax 上 BPU（int16）**

只对含 Attention 的模型有效。社区帖 33301 的 YOLOv11 案例，一个 Softmax 在 CPU 导致两个子图，7.67 FPS；改成：

```yaml
node_info: {
  "/model.10/m/m.0/attn/Softmax": {'ON': 'BPU', 'InputType': 'int16', 'OutputType': 'int16'}
}
```

关键日志的标志是：

```
Node: /model.10/m/m.0/attn/Softmax will be run on BPU with int16
Model has 1 BPU subgraph
```

从 2 个子图变成 1 个，性能到 40+ FPS。

> 来源：社区帖 33301（https://forum.d-robotics.cc/t/topic/33301）

**路径 3：模型本身瘦身**

- 降低输入分辨率（640 → 480）
- 换更小的骨干（YOLOv8n → YOLOv8n-pose 之类）
- 剪枝 / 蒸馏

这条路径不涉及工具链，属于算法侧决策。

### 3.5.3.2 场景二：BPU 很快，但端到端慢

**特征**：`BPU_inference_time_cost` 小（< 10ms），`ratio` 低，端到端 FPS 远低于 BPU 耗时换算值。

这时候优化 yaml 是**完全无效**的，必须去查 CPU 侧。社区帖 35444 的结论就是：

> 「瓶颈完全不在 BPU 模型推理本身，而在于 CPU 侧的数据搬运、预处理或后处理逻辑。`.yaml` 配置文件主要影响模型编译和量化，对 CPU 侧的运行时开销影响有限」

> 来源：社区帖 35444（https://forum.d-robotics.cc/t/topic/35444）

三个子场景，对应三种修法：

**子场景 2a：线程同步等待**

社区帖 35149 的日志是最干净的样本：

```
[USB] 接收:98.8 fps | 推理:20.0 fps | 队列:0 | CPU:15%
[耗时|线程0] 等待:83.5ms 预处理:0.0ms BPU:3.3ms 后处理:0.4ms
[耗时|线程1] 等待:106.7ms 预处理:0.0ms BPU:3.3ms 后处理:0.4ms
```

> 来源：社区帖 35149（https://forum.d-robotics.cc/t/topic/35149）

解构这组数字：USB 能收 98.8 FPS，BPU 只花 3.3ms（对应 300 FPS），预处理和后处理几乎为零，但「等待」占了 83.5~106.7ms。**80% 以上的时间花在等锁上。**

诊断要点：**队列为 0** 说明不是「生产快消费慢」的积压，而是「消费端在等锁」。如果队列持续增长，那是产能不足；队列为 0 而推理慢，那是同步点太多。

修法：无锁队列 / 双缓冲 / 把采集与推理彻底解耦。

**子场景 2b：预处理用 CPU 做重的格式转换**

BGR → NV12 在 Python 里做，一张 640×480 的图要几毫秒到十几毫秒。优化手段：

- 用硬件的 VSE / N2D 做 resize 和格式转换
- TROS 链路里用 `hobot_codec` 输出 NV12，送到 `/hbmem_img` 共享内存话题
- 或者干脆在模型转换时把 `input_type_rt` 配成 `nv12`，让 BPU 硬件做格式转换

第三种最省事，但需要模型支持 NV12 输入 —— 也就是 yaml 里 `input_type_rt: 'nv12'`。

**子场景 2c：后处理太重**

后处理包括 DFL 解码、置信度过滤、NMS、坐标还原。在 Python 里用循环写的 NMS 可能占掉几十毫秒。

优化方向：

- NMS 向量化（NumPy），或移植到 C++
- 降低 `nms_top_k`（例：从 5000 降到 300）
- 先按置信度粗筛再做 NMS

社区配置里 `nms_top_k: 5000` 是常见默认值，对实时场景明显偏大。

> 来源：社区帖 34523（https://forum.d-robotics.cc/t/topic/34523）配置文件示例

### 3.5.3.3 场景三：BPU 推理正常，但偶发卡顿

**特征**：平均帧率尚可，但帧率抖动大，`max_time` 远大于 `avg_time`。

从 35444 的 perf 日志就能看出这种分布：

```
"BPU_inference_time_cost": { "avg_time": 4.428, "max_time": 5.249, "min_time": 4.204 }
"CPU_inference_time_cost": { "avg_time": 42.83, "max_time": 78.157, "min_time": 33.877 }
```

BPU 的 max/avg 比是 1.19（稳定），CPU 的是 1.83（抖动大）。**抖动在 CPU 侧，不在 BPU。**

> 来源：社区帖 35444（https://forum.d-robotics.cc/t/topic/35444）

偶发卡顿的常见原因：

| 原因 | 特征 | 修法 |
| --- | --- | --- |
| NMS 遇到密集目标 | 后处理耗时某帧突增 | `nms_top_k` 下调、提前粗筛 |
| CPU 降频 | 全局变慢，温度高 | 设 performance governor（见下） |
| DDR 带宽争抢 | BPU 和 CPU 同时访问内存 | 减少 buffer 拷贝 |
| 内存回收/换页 | 周期性卡顿 | 减少 Python 对象分配 |
| 热降频 | 长时间跑后变慢 | 加散热 |

热降频这条有官方数据支撑：

> 「芯片最高结温：105°C；当芯片结温超过 95°C 时，系统将自动启动降频机制以降低温度，可能会影响性能表现。」

> 来源：官方文档 RDK（https://developer.d-robotics.cc/rdk_x_doc/RDK）

## 3.5.4 实测手段：系统侧调优

### 3.5.4.1 CPU 调频

默认 governor 可能是 `ondemand` 或 `schedutil`，频率随负载浮动。做性能测试前必须固定到最高频，否则测出来的数字不可重复：

```bash
# 查看当前 governor
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor

# 全部核切到 performance
echo performance | sudo tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor

# 确认频率
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_cur_freq
```

社区帖 33301 里还额外打开了 boost：

```bash
sudo bash -c "echo 1 > /sys/devices/system/cpu/cpufreq/boost"
```

> 来源：社区帖 33301（https://forum.d-robotics.cc/t/topic/33301）

测试时还要确认温度没到降频线：

```bash
# 温度，单位毫摄氏度
cat /sys/class/thermal/thermal_zone0/temp
```

### 3.5.4.2 BPU 调频

```bash
# 切 userspace 才能手动设频
echo userspace | sudo tee /sys/devices/system/bpu/bpu0/devfreq/devfreq*/governor

# 看支持的档位
cat /sys/devices/system/bpu/bpu0/devfreq/devfreq*/available_frequencies

# 设为最高档
echo 600000000 | sudo tee /sys/devices/system/bpu/bpu0/devfreq/devfreq*/userspace/set_freq

# 确认
cat /sys/devices/system/bpu/bpu0/devfreq/devfreq*/cur_freq
```

> 来源：官方文档 Advanced_development/linux_development/driver_development/driver_bpu_sysfs_dev（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/driver_development/driver_bpu_sysfs_dev）

还有更省事的方式，用 `power_level`：

```bash
# 0 = 性能优先，最高功耗
echo 0 > /sys/devices/system/bpu/bpu0/power_level
# 1 = linux dvf 动态调节
# <0 = 值越小功耗越低
```

> 来源：官方文档 Advanced_development/linux_development/driver_development/driver_bpu_sysfs_dev（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/driver_development/driver_bpu_sysfs_dev）

**这些设置重启后失效。** 要持久化得写 systemd service 或 `rc.local`。跑基准测试前临时设一下即可。

## 3.5.5 多线程：怎么用才对

### 3.5.5.1 两种「并行」的区分

| 类型 | 机制 | 效果 |
| --- | --- | --- |
| 硬件并发 | 多个模型同时在 BPU 上算 | **X5 不支持**（单核） |
| 时间分片 | 多线程快速交替喂任务 | 可以接近 100% 利用率 |

社区里有实测 4 模型 30fps 的案例，社区的解释是：

> 「[实现的] 应该是**时间分片 + 流水线**方案……yolov5nu 是超轻量模型，单模型推理耗时可能只有 5-8ms，4 个模型串行也才 20-32ms，可以达到 30fps。」

> 来源：社区帖 35342（https://forum.d-robotics.cc/t/topic/35342）

所以多线程的价值在于：**让 CPU 侧的预处理/后处理与 BPU 计算重叠**，而不是让 BPU 同时算两件事。

### 3.5.5.2 线程数怎么选

社区管理员给出的经验值：

> 「一般工程中 2 个线程可以控制单帧延迟较小，同时吃满所有 BPU 到 100%，在吞吐量（FPS）和帧延迟间得到一个较好的平衡。」

> 来源：社区帖 34885（https://forum.d-robotics.cc/t/topic/34885）

从 2 开始试，然后：

```bash
for n in 1 2 3 4; do
  echo "=== thread_num=$n ==="
  hrt_model_exec perf --model_file model.bin --thread_num $n --loop_num 100
done
```

画一张「thread_num → FPS」曲线。**在曲线上开始变平的地方停**，再往上加只会增加延迟、不增加吞吐。

### 3.5.5.3 一个典型的多线程骨架

```python
# 采集、推理、后处理三段流水线，三段各自独立线程
import queue, threading
import numpy as np
from hbm_runtime import HB_HBMRuntime

q_raw   = queue.Queue(maxsize=2)   # 故意设小，形成背压
q_infer = queue.Queue(maxsize=2)

def capture_loop(cap):
    while True:
        ok, frame = cap.read()
        if not ok:
            continue
        if q_raw.full():
            q_raw.get()          # 丢最旧的一帧，保证实时性
        q_raw.put(frame)

def infer_loop(model, input_name, shape):
    while True:
        frame = q_raw.get()
        nv12 = bgr_to_nv12(frame)          # 预处理
        out = model.run({input_name: nv12.reshape(shape)})
        q_infer.put((frame, out))

def post_loop(model_name):
    while True:
        frame, out = q_infer.get()
        dets = decode_and_nms(out[model_name])   # 后处理
        draw(frame, dets)
```

三个要点：

1. **队列设小（maxsize=2）**，形成背压，避免「采集疯狂堆积、推理永远追不上」。
2. **满了丢最旧帧**，实时场景宁可丢帧也不要延迟累积。
3. **每段一个线程**，不要在同一条线程里串行做三件事。

## 3.5.6 零拷贝：什么时候有用，怎么配

### 3.5.6.1 原理

普通的 ROS 话题传图像，发布者序列化、订阅者反序列化，中间会有多次内存拷贝。对 1080p 的图，一次拷贝就是几毫秒。零拷贝通过共享内存 + 借贷消息（Loaned Messages）消除这些拷贝。

### 3.5.6.2 TROS Humble 的配置

官方给出的四个环境变量：

```bash
# 1. 确保 RMW 是 Fast DDS
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp

# 2. 指定启用了共享内存的 Fast DDS 配置文件
export FASTRTPS_DEFAULT_PROFILES_FILE=/opt/tros/humble/lib/hobot_shm/config/shm_fastdds.xml

# 3. 强制从 XML 加载 QoS
export RMW_FASTRTPS_USE_QOS_FROM_XML=1

# 4. 启用借贷消息（零拷贝的关键）
export ROS_DISABLE_LOANED_MESSAGES=0
```

> 来源：官方文档 FAQ/applications_and_examples（https://developer.d-robotics.cc/rdk_x_doc/FAQ/applications_and_examples）Q15

四个都设了才生效，少一个就退化成普通传输。

### 3.5.6.3 验证是否真的启用了

官方给的检查方法：

```bash
# 看共享内存文件是否被创建
ls -lthr /dev/shm/fast_datasharing* /dev/shm/fastrtps_*

# 看哪些进程在用
sudo lsof /dev/shm/fast_datasharing*
```

> 来源：官方文档 FAQ/applications_and_examples（https://developer.d-robotics.cc/rdk_x_doc/FAQ/applications_and_examples）Q15

判据：有 `fast_datasharing_*` 文件、文件大小与图像帧大小相关、`lsof` 能看到发布者和订阅者进程。

### 3.5.6.4 三个必须同时满足的条件

官方特别强调：

> 「零拷贝的成功启用依赖于**发布者和订阅者两端**都正确支持和配置了借贷消息和共享内存传输。」

> 来源：官方文档 FAQ/applications_and_examples（https://developer.d-robotics.cc/rdk_x_doc/FAQ/applications_and_examples）Q15

再加上「配置的 XML 内容本身正确」，一共三条。缺一条就静默退化成拷贝模式 —— **不会报错，只是慢**。

### 3.5.6.5 需要禁用零拷贝的场景

调试时如果怀疑零拷贝导致数据异常，可以强关：

```bash
export ROS_DISABLE_LOANED_MESSAGES=1
```

这个变量优先级最高。官方说明是「如果因某些原因需要禁用零拷贝（例如调试或兼容性问题），可以通过设置以下环境变量来实现，它具有最高优先级」。

> 来源：官方文档 FAQ/applications_and_examples（https://developer.d-robotics.cc/rdk_x_doc/FAQ/applications_and_examples）Q15

### 3.5.6.6 实际链路的零拷贝示例

官方给出的 `hobot_codec` 用法：

```bash
ros2 launch hobot_codec hobot_codec.launch.py \
  codec_in_mode:=shared_mem \
  codec_in_format:=nv12 \
  codec_out_mode:=ros \
  codec_out_format:=jpeg \
  codec_sub_topic:=/hbmem_img \
  codec_pub_topic:=/image_jpeg
```

关键在 `codec_in_mode:=shared_mem` 和 `codec_sub_topic:=/hbmem_img` —— 订阅的是共享内存话题，不是普通图像话题。

> 来源：官方文档 FAQ/applications_and_examples（https://developer.d-robotics.cc/rdk_x_doc/FAQ/applications_and_examples）Q15

TROS 启动日志里能看到零拷贝相关的环境变量确实被设上了：

```
Hobot shm pkg enables zero-copy with fastrtps profiles file: /opt/tros/humble/lib/hobot_shm/config/shm_fastdds.xml
Hobot shm pkg sets RMW_FASTRTPS_USE_QOS_FROM_XML: 1
env of RMW_FASTRTPS_USE_QOS_FROM_XML is 1 , ignore env setting
```

> 来源：社区帖 34523（https://forum.d-robotics.cc/t/topic/34523）

注意最后那行 `ignore env setting` —— 说明 launch 文件里已经帮你设好了，你在外面再 export 会被忽略。排查时要看这条日志确认生效值。

## 3.5.7 VIO / BPU 直通：跳过 CPU 中转

### 3.5.7.1 概念

理想链路是「摄像头 → ISP/VSE → BPU」，全程在硬件内存里流转，不经过 CPU。X5 的 ION 内存体系就是为此设计的：

- `cma_reserved` → 多媒体系统（VIN/ISP/VSE/GDC/VPU/OSD/GPU/Display）
- `carveout` → **BPU 子系统**
- `ion_cma` → 备用

> 来源：官方文档 Advanced_development/linux_development/driver_development_x5/memory（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/driver_development_x5/memory）

当摄像头输出直接落在 ION 内存、BPU 直接从这块内存读，就不需要 CPU 参与搬运。

### 3.5.7.2 在 yaml 里控制输入来源

`input_source` 字段：

```yaml
compiler_parameters:
  input_source: {'images': 'pyramid'}
```

日志里能看到默认值和实际值：

```
input-source: {'images': 'pyramid', '_default_value': 'ddr'}
```

`pyramid` 是给 NV12 图像输入用的硬件通路（对应 VIO 的金字塔 buffer），`ddr` 是普通内存。图像输入用 `pyramid`、featuremap 输入用 `ddr`，这是工具链根据 `input_type_rt` 自动推断的。

> 来源：社区帖 35444（https://forum.d-robotics.cc/t/topic/35444）

**这一项不建议手动改。** 它是工具链根据输入类型推断的，改错了反而会让 BPU 走错通路。

### 3.5.7.3 Python 侧的直通

Python 的 `hbm_runtime` 接受 numpy 数组，天然需要一次拷贝。要做真正的零拷贝需要走 C++ 的 `hbDNNTensor` + `hbSysMem` 接口，或者用 TROS 的 `dnn_node` + `/hbmem_img` 话题。

这就是为什么「用 Python 跑实时应用」和「用 C++ 跑实时应用」的性能天花板差很多 —— Python 那一层必然有一次 CPU 内存到 BPU 内存的拷贝。

## 3.5.8 一个可复用的性能排查脚本

```bash
#!/bin/bash
# perf_triage.sh —— 板端性能初筛，依次输出四个关键量
MODEL="${1:?usage: perf_triage.sh <model.bin>}"

echo "===== 1. 系统与频率 ====="
echo "--- CPU governor ---"
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor
echo "--- CPU 当前频率 ---"
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_cur_freq
echo "--- BPU 频率 ---"
cat /sys/devices/system/bpu/bpu0/devfreq/devfreq*/cur_freq 2>/dev/null || echo "N/A"
echo "--- 温度(m°C) ---"
cat /sys/class/thermal/thermal_zone0/temp 2>/dev/null

echo
echo "===== 2. 模型结构 ====="
hrt_model_exec model_info --model_file "$MODEL"

echo
echo "===== 3. 单线程延迟（端到端视角）====="
hrt_model_exec perf --model_file "$MODEL" --thread_num 1 --loop_num 100

echo
echo "===== 4. 双线程吞吐（BPU 上限视角）====="
hrt_model_exec perf --model_file "$MODEL" --thread_num 2 --loop_num 100

echo
echo "===== 5. 推理期间的 BPU 利用率（另开终端观察）====="
echo "watch -n 1 'cat /sys/devices/system/bpu/bpu0/ratio'"
```

第 3 步和第 4 步的结果差异就是「CPU 侧开销 vs BPU 纯计算」的差距。差距大 → 去查 CPU 侧；差距小 → BPU 是瓶颈。

## 3.5.9 常见「性能不达预期」根因表

按出现频率排序，每条给出可验证的现象特征：

| # | 根因 | 现象特征 | 验证方法 |
| --- | --- | --- | --- |
| 1 | CPU↔BPU 数据搬运 / layout 转换 | `ratio` 低、CPU 耗远大 BPU | perf 日志对比两段耗时 |
| 2 | 线程同步等待 | 队列为 0 但推理慢 | 打印各阶段时间戳 |
| 3 | 算子回退 CPU 导致子图切分 | 转换日志 `Model has N subgraph`，N > 2 | `hb_mapper checker` + profiler.csv |
| 4 | 预处理用 CPU 做重格式转换 | `pre process time ms` > 10 | TROS perf 日志 |
| 5 | 后处理（NMS）过重 | `post process time ms` > 10 且抖动大 | 同上 |
| 6 | 输入分辨率过大 | BPU 耗时与分辨率近似平方关系 | 降分辨率重测 |
| 7 | CPU/BPU 降频 | 全局变慢、温度高 | 查 governor 与 thermal |
| 8 | 模型本身太大 | BPU 满载且耗时高 | `ratio` ≈ 100% |
| 9 | 零拷贝未真正启用 | TROS 链路帧率低但各段正常 | `/dev/shm` 检查 |
| 10 | 工具链版本与板端不匹配 | 加载时 `Inconsistency between the hbrt library version` | 对比编译日志版本号 |

第 10 条要特别提一下：版本不匹配的警告原文是

## 3.5.10 一次完整的性能优化实录

社区帖 34885 是本卷里最完整的一次优化，从 286ms 到 55ms，过程值得完整复盘。

### 3.5.10.1 初始状态

配置里 `input_layout_rt: 'NCHW'`（和 `input_layout_train` 一致）。性能 286ms。

profiler 拆解：

| 项 | 耗时 | 占比 |
| --- | --- | --- |
| BPU 推理 | 104.15ms | 36% |
| CPU 侧合计 | 181.88ms | **64%** |
| ├ Layout Convert | 148ms | 52% |
| ├ Less/Not/Cast | 8ms | 3% |
| └ Quantize/Dequantize | 22ms | 8% |

> 来源：社区帖 34885（https://forum.d-robotics.cc/t/topic/34885）

**一眼就看出问题：Layout Convert 148ms 占了一半以上。** 这一项来自「模型的训练 layout 是 NCHW，但 BPU 内部高效布局是 NHWC」，每次推理都要在两边转换。

### 3.5.10.2 三处改动

```yaml
# 改动一：input_layout_rt 从 NCHW 改成 NHWC
input_parameters:
  input_layout_train: 'NCHW'    # 训练是 NCHW，保持
  input_layout_rt: 'NHWC'       # 板端改成 NHWC

# 改动二：四个残留 CPU 算子强制上 BPU
node_info: {
  "Resize_220": {'ON': 'BPU', 'InputType': 'int8', 'OutputType': 'int8'},
  "Less_245":   {'ON': 'BPU', 'InputType': 'int8', 'OutputType': 'int8'},
  "Not_246":    {'ON': 'BPU', 'InputType': 'int8', 'OutputType': 'int8'},
  "Cast_247":   {'ON': 'BPU', 'InputType': 'int8', 'OutputType': 'int8'}
}

# 改动三：优化 ONNX 原始模型的算子结构（帖子作者的总结，具体改法未展开）
```

> 来源：社区帖 34885（https://forum.d-robotics.cc/t/topic/34885）

### 3.5.10.3 结果

| 指标 | 优化前 | 优化后 | 提升 |
| --- | --- | --- | --- |
| 推理延迟 | 286ms | **55ms** | 5.2× |
| FPS | 3.5 | 18 | 5.2× |
| Layout Convert | 148ms | ~0ms | 消除 |
| CPU 算子 | 182ms | ~0ms | 消除 |

> 来源：社区帖 34885（https://forum.d-robotics.cc/t/topic/34885）

**这个案例的可迁移结论**：

1. `input_layout_rt` 与 `input_layout_train` **不需要一致** —— 它们是两个独立的配置，分别描述「板端喂什么格式」和「训练时是什么格式」。工具会自动插入转换。
2. 改 `input_layout_rt` 到 NHWC 消除了 148ms，说明**原来的配置让工具做了多余的转换**。
3. 四个小算子（Resize/Less/Not/Cast）加起来的计算量微不足道，但它们造成的**子图切分**代价是 182ms。**判断一个算子该不该移 BPU，看的不是它的计算量，而是它造成的切分代价。**

## 常见误区

**误区一：只看总帧率，不看分段耗时。** 「我的模型只有 20 FPS」这句话没有诊断价值。社区里两个案例：一个 BPU 104ms、CPU 182ms（瓶颈在 CPU），另一个 BPU 3.3ms、CPU 等待 83ms（瓶颈在线程同步）。两者优化手段完全相反。

**误区二：认为优化 yaml 能解决所有性能问题。** yaml 影响的是「模型编译产物」，对运行时的 CPU 侧开销影响有限。当 `BPU_inference_time_cost` 只有 4.4ms 而 `CPU_inference_time_cost` 是 42.8ms 时，改 yaml 一点用都没有。

**误区三：认为多个模型同时跑能提升 BPU 利用率。** X5 的 BPU 是单核，一次只能推理一个模型。多模型「并行」本质是时间分片。BPU 利用率低说明 CPU 侧供给不足，不是「模型太少」。

**误区四：`thread_num` 越大越好。** 单线程测的是延迟，多线程测的是吞吐。工程上 2 个线程通常是吞吐与延迟的平衡点。继续加大只增加延迟，不增加吞吐。

**误区五：配了零拷贝环境变量就以为零拷贝生效了。** 必须「发布者支持借贷消息 + 订阅者支持 + XML 配置正确」三条同时满足。缺一条就静默退化成拷贝模式，不报错、只是慢。验证方法是看 `/dev/shm/fast_datasharing*` 是否存在。

**误区六：测性能前不固定频率。** 默认 governor 会在负载变化时动态调频，同一份代码两次测出来的数字可能差 20% 以上。测之前 `echo performance`，测完再切回去。

**误区七：认为「算子很少」就「影响很小」。** 社区案例里四个小算子（Resize/Less/Not/Cast）合计计算量不到 8ms，但它们把模型切成多个子图，带来的 CPU↔BPU 切换代价是 182ms。判断依据要看子图数量，不看算子数量。
