# 7.2 报错速查表：模型转换与推理

## 本章解决什么

模型转换（`hb_mapper`）与板端推理是 RDK X5 上最容易卡住的两个环节。官方 FAQ 已经沉淀了一大批错误码与标准解答，但它们混在 4.7 万字符的长文档里，出问题时要翻半天。

这一章把官方错误码按**阶段**和**关键词**重组，做成可以直接搜的表。每一条都给出：原文报错、根因、标准处置。原文报错**一字未改**，可以直接复制去搜索引擎或社区搜。

> 来源：官方文档 FAQ/toolchain（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）「模型量化错误及解决方法」章节

## 7.2.1 先定位卡在哪个阶段

工具链的标准流程是三段脚本：

| 阶段 | 脚本 | 干什么 | 典型报错前缀 |
| --- | --- | --- | --- |
| 模型验证 | `01_check.sh` | 检查 onnx 是否合法、算子是否支持 | `ERROR The shape of model input...`、`Unsupported op` |
| 量化校准 | `02_preprocess.sh` | 处理校准集 | `load cal data for input...` |
| 模型编译 | `03_build.sh` | 生成 `.bin` | `Layer ... will be executed on CPU`、`hbdk-cc compile ... failed` |

看懂自己卡在哪一段，再去下面找对应表格。脚本编号是官方 `hb_mapper` 的标准命名，社区教程里也这么叫。

## 7.2.2 01_check.sh 阶段的报错

### 7.2.2.1 动态 shape

```
ERROR The shape of model input:input is [xxx] which has dimensions of 0. Please specify input-shape parameter.
```

**根因**：模型输入是动态 shape（某一维为 0 或 -1）。

**处置**：显式指定输入 shape。

```bash
--input-shape input_name input_shape
```

> 来源：官方文档 FAQ/toolchain（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）

### 7.2.2.2 CPU 算子不支持

```
ERROR HorizonRT not support these cpu operators: {op_type}
```

**根因**：用到了地瓜不支持的 CPU 算子。

**处置**：按算子支持列表替换算子；若该算子为核心算子，需联系官方评估开发。

### 7.2.2.3 BPU 算子不支持

```
Unsupported op {op_type}
```

**根因**：用到了不支持的 BPU 算子。

**处置**：官方给了一条实用建议 —— **若模型整体性能可满足需要，可以忽略这条日志**；只有性能不达标时才需要替换算子。

这条很重要：`Unsupported op` 不一定是致命错误，可能只是某个算子回退到 CPU 执行。

### 7.2.2.4 自定义算子

```
ERROR nodes:['{op_type}'] are specified as domain:xxx, which are not supported by official onnx. Please check whether these ops are official onnx ops or defined by yourself
```

**根因**：用了自定义算子（非官方 onnx 算子）。

**处置**：按算子支持列表替换，或参考自定义算子开发完成 CPU 算子注册。

## 7.2.3 03_build.sh 阶段的报错

### 7.2.3.1 算子回退 CPU（两种形态）

```
Layer `{op_name}`
xxx expect data shape range:[[xxx][xxx]], but the data shape is [xxx]
Layer `{op_name}`
Tensor xxx expects be n dimensions, but m provided
```

**根因**：`{op_name}` 超出支持限制，被回退到 CPU 计算。

```
INFO： Layer `{op_name}` will be executed on CPU
```

**根因**：该算子 shape（CxHxW）**超过 8192**，被回退到 CPU。

**处置（两种形态通用）**：若回退的算子少、整体性能达标，可以不管；不达标就查算子支持列表，换成无 shape 限制的 BPU 算子。

**这条是性能问题的头号线索**。社区里「我的模型算子都在 BPU 上但性能很差」这类帖子，先 grep 转换日志里的 `will be executed on CPU`。

> 来源：社区帖 34885（https://forum.d-robotics.cc/t/topic/34885）

### 7.2.3.2 优化 pass 失败

```
ERROR There is an error in pass: `{op_name}`. Error message:xxx
```

**根因**：算子优化失败。

**处置**：收集模型 + `.log` 文件提交官方技术支持。自己无法解决。

### 7.2.3.3 constant_folding 失败

```
Error There is an error in pass:constant_folding. Error message: Could not find an implementation for the node `{op_name}`
```

**根因**：该算子 onnxruntime 暂不支持。

**处置**：按算子支持列表替换；核心算子需联系官方。

### 7.2.3.4 非四维输入

```
WARNING input shape [xxx] has length: n ERROR list index out of range
```

**根因**：模型输入不是四维。

**处置**：把输入改成四维，例如 `HxW` → `1x1xHxW`。

### 7.2.3.5 onnx 解析 core dump

```
Start to parse the onnx model
core dump
```

**根因**：**导出 onnx 时只给某一个 input/output 节点指定了 name**。

**处置**：重新导出 onnx。两种正确做法：

- 导出时**不指定**任何 input/output name
- 或**依次为每个** input/output 节点都指定名称

这是导出环节的经典坑，很多人只给部分节点命名就出这个问题。

### 7.2.3.6 量化/编译 core dump

```
Start to calibrate/quantize the model
core dump

Start to compile the model
core dump
```

**根因**：量化或编译失败，具体原因需要看日志。

**处置**：收集模型 + `.log` 提交官方。

### 7.2.3.7 shape 推断不一致

```
ERROR model conversion faild: Inferred shape and existing shape differ in dimension x: (n) vs (m)
```

**根因**：onnx 输入 shape 非法，或工具优化 pass 有问题。

**处置**：先验证 onnx 本身能正常推理；能推理就说明是工具侧问题，提交官方。

### 7.2.3.8 阈值异常警告

```
WARNING got unexpected input/output/sumin threshold on conv `{op_name}`! value: xxx
```

**根因**：数据预处理有误，或该节点 weight 值太小/太大。

**处置**：

1. 检查数据预处理是否正确
2. 官方建议**用 BN 算子优化数据分布**

### 7.2.3.9 编译失败

```
ERROR hbdk-cc compile hbir model failed with returncode -n
```

**根因**：模型编译失败。

**处置**：收集模型 + `.log` 提交官方。

### 7.2.3.10 非四维算子

```
ERROR {op_type} only support 4 dim input
```

**根因**：该 op 输入维度不是四维。

**处置**：调整为四维输入。

### 7.2.3.11 属性不支持

```
ERROR {op_type} Not support this attribute/mode=xxx
```

**根因**：工具链不支持该 op 的这个属性。

**处置**：按算子支持列表替换，或联系官方评估。

### 7.2.3.12 模型里没有可上 BPU 的节点

```
ERROR There is no node can execute on BPU in this model, please make sure the model has at least one conv node which is supported by BPU.
```

**根因**：模型里**没有任何一个能被 BPU 执行的 conv 节点**。

**处置**：确认模型有效性，确保至少有一个 BPU 支持的 conv。这是彻底无法部署的情况——说明模型结构与 BPU 架构完全不兼容。

### 7.2.3.13 opset 版本过高（两种写法）

```
ERROR [ONNXRuntimeError] : 9 : NOT_IMPLEMENTED : could not find a implementation for the node of `{op_name}`:{op_type}(opset)
```

```
ERROR The opset version of the onnx model is n, only model with opset_version 10/11 is supported
```

**根因**：opset 版本超出工具链支持范围。

**处置**：**重新导出 onnx，`opset_version` 设为 10 或 11**。

这是 pytorch 默认导出 opset 太新导致的，`torch.onnx.export(..., opset_version=11)` 就能解决。

### 7.2.3.14 run_on_bpu 用法错误

**根因**：`run_on_bpu` 目前能力有限——**仅支持**：

- 模型尾部的 `Relu` / `Softmax` / pooling（`maxpool`、`avgpool` 等）
- `CPU*+Transpose` 组合（通过声明 Transpose 节点名称，把 CPU* 与 Transpose 都放到 BPU 上；`CPU*` 特指 BPU 支持的 op）

**处置**：不符合上述条件就不要用 `run_on_bpu`，或联系官方评估。

### 7.2.3.15 输出节点超过 32 个

```
ERROR tool limits for max output num is 32
```

**根因**：工具链**最多支持 32 个输出节点**。

**处置**：把输出节点数控制在 32 以内。

分割类模型（如实例分割输出多个分支）容易踩这个限制。

### 7.2.3.16 环境文件缺失

```
ERROR xxx file parse failed.
ERROR xxx does not exist in xxx.
```

**根因**：环境配置不正确。

**处置**：**使用官方提供的 Docker 环境做量化**。这条官方回答很直接——不要在裸机上折腾工具链。

### 7.2.3.17 预处理导致 reshape 失败

```
ERROR exception in command: makertbin.
ERROR cannot reshape array of size xxx into shape xxx.
```

**根因**：数据预处理异常。

**处置**：对照文档检查预处理逻辑。

### 7.2.3.18 工具链版本不匹配

```
ERROR load cal data for input xxx error
ERROR cannot reshape array of size xxx into shape xxx
```

**根因**：工具链版本与 SDK 不匹配。

**处置**：**使用 SDK 中对应版本的工链**。注意这里报错文本和上一条几乎一样，但根因完全不同——区分线索是上面那行 `load cal data for input xxx error`。

### 7.2.3.19 CUDA 相关错误

```
ERROR [ONNXRuntimeError] : 1 : FAIL : Non-zero status code returned while running HzCalibration node.Name:'xxx'Status Message :CUDA error cudaErrorNoKernelImageForDevice:no kernel image is available for execution on the device
```

**根因**：Docker 加载方式错误。

**处置**：加载 Docker 时**换用 nvidia docker 加载命令**。

### 7.2.3.20 onnx 版本不匹配（量化预处理算子）

```
[ONNXRuntimeError] : 10 : INVALID_GRAPH : Load model from xxx.onnx failed:This is an invalid model. In Node, ("xxx", HzSQuantizedPreprocess, "", -1) : ("images": tensor(int8),"xxx": tensor(int8),"xxx": tensor(int32),"xxx": tensor(int8),) -> ("xxx": tensor(int8),) , Error No Op registered for HzSQuantizedPreprocess with domain_version of 11
```

**根因**：onnx 版本不匹配。

**处置**：**重新导出 opset10 版本，并用 opencv 方法做预处理**。

### 7.2.3.21 Resize 算子校准失败

```
[E:onnxruntime:, sequential_executor.cc:183 Execute] Non-zero status code returned while running Resize node. Name:'xxx' Status Message: upsample.h:299 void onnxruntime::UpsampleBase::ScalesValidation(const std::vector &, onnxruntime::UpsampleMode) const scales.size() == 2 || (scales.size() == 4 && scales[0] == 1 && scales[1] == 1) was false.
```

**根因**：onnxruntime 自身限制 —— 模型里有 Resize 时**不能批量校准，只能一次一张**。

**处置**：校准改为单张逐个送入，不要用 batch。

## 7.2.4 板端推理阶段的经典问题

### 7.2.4.1 YOLOv5 的 reshape 报错

```
can't reshape xxx in (84,84,3,85)
```

**根因**：模型输出结构与后处理期望不匹配。

**处置**：这类问题的完整排查见官方 FAQ Q7，核心是核对模型输出的三个特征图尺寸与后处理里写死的 anchor/stride 是否一致。

> 来源：官方文档 FAQ/toolchain（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）Q7

### 7.2.4.2 检测框异常的四类表现

官方 FAQ 把 YOLOv5 部署中的检测框异常单独归纳成了四条，按现象区分：

| 现象 | 官方 FAQ 编号 |
| --- | --- |
| 检测结果出现数量非常多且不规则的检测框 | Q8 |
| 检测结果出现有周期性排列规律的异常检测框 | Q9 |
| 检测框的位置出现整体偏移 | Q10 |
| 检测框都异常地聚集在图像的左上角 | Q11 |

「周期性排列」和「整体偏移」看起来都是「框不对」，但根因完全不同——前者通常是坐标解码/网格索引错了，后者通常是预处理与后处理的坐标变换不一致。

> 来源：官方文档 FAQ/toolchain（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）Q8-Q11

### 7.2.4.3 用自己的模型跑示例段错误

```
Segmentation fault
```

**场景**：运行 `/app/pydev_demo/07_yolov5_sample` 时换成自己的模型，报段错误。

**根因**：模型输出结构与示例代码里写死的后处理不匹配，越界访问。

**处置**：见官方 FAQ Q12。核心是**不要直接换成自己的模型就跑**，要先确认输出的 layer 数量、shape、量化类型与示例期望一致。

> 来源：官方文档 FAQ/toolchain（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）Q12

## 7.2.5 效果不好但没报错：Pipeline 检查流程

这是官方给出的**系统性排查法**，比盲目调参有效得多。按顺序查五个环节：

### 7.2.5.1 数据预处理

- **与训练时是否一致**：resize 方式、归一化参数、均值方差、颜色空间（RGB/BGR）、letterbox 的 padding 方式与颜色，**必须完全一致**
- **可视化中间结果**：把预处理后的图存下来，和训练时送进模型的数据对比
- **yaml 里的预处理参数**：`norm_type`、`mean_value`、`std_value` 要能正确「抵消」你在送校准集前做的预处理

官方原话：**「任何细微的差异都可能导致模型性能急剧下降」**。

### 7.2.5.2 模型转换过程

- 工具链版本
- yaml 配置：输入节点名、输出节点名、输入数据类型、输入布局、模型类型、BPU 架构
- 校准数据集质量与代表性
- 量化敏感层分析 → 混合精度量化或 QAT
- 完整转换日志里的 warning

### 7.2.5.3 BPU 推理与 Runtime

- 输入数据的 layout / dtype / shape 是否与转换时定义的一致
- 输入输出 Buffer 的分配与拷贝有无越界
- 板端 `libdnn.so` 版本与工具链版本是否兼容
- 推理 API 调用顺序与参数

### 7.2.5.4 后处理

- 与模型实际输出节点的格式、维度、含义是否匹配
- anchors、类别数、置信度阈值、NMS 阈值是否与训练一致
- 坐标映射回原图尺寸是否正确

### 7.2.5.5 端到端验证

- 用一组**已知正确答案**的样本跑完整 Pipeline，对比实际输出
- 把 Pipeline 拆成预处理 / 推理 / 后处理三段，逐段验证输入输出

> 来源：官方文档 FAQ/toolchain（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）Q13

**这个顺序很重要**：官方把「预处理一致」放在第一位，因为它是最高频根因。社区里大量「量化后精度崩了」的帖子，最后查出来是 BGR/RGB 弄反了或者归一化系数写错。

## 7.2.6 提问前先准备这些

官方 FAQ Q1 明确要求：提问算法工具链问题时必须提供以下信息，否则无法判断。

| 必提供项 | 获取方式 |
| --- | --- |
| 板卡型号 | `hrut_boardid` |
| 系统版本 | `cat /etc/version`、`rdkos_info` |
| 工具链版本 | Docker 镜像 tag |
| 完整转换日志 | `hb_mapper` 输出重定向到文件 |
| 模型信息 | 输入 shape、opset、算子清单 |
| 报错原文 | 不要只描述「报错了」，要贴原文 |

> 来源：官方文档 FAQ/toolchain（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）Q1

一条实用建议：转换时把日志完整存下来。

```bash
bash 03_build.sh 2>&1 | tee build_$(date +%Y%m%d_%H%M).log
```

## 常见误区

1. **看到 `Unsupported op` 就以为必须换模型** —— 官方明确说性能可接受时可以忽略。真正的性能杀手是 `will be executed on CPU`。
2. **`opset` 用默认值** —— PyTorch 新版默认导出 opset 很高，工具链只要 10/11，导出时必须显式指定。
3. **导出 onnx 时只给部分节点命名** —— 会导致 `Start to parse the onnx model` 后直接 core dump。
4. **`cannot reshape array of size xxx into shape xxx` 只有一种根因** —— 至少两种：预处理异常、工具链版本不匹配。要靠上下文（有没有 `load cal data for input xxx error`）区分。
5. **精度掉了就换模型** —— 先走官方的五步 Pipeline 检查。绝大多数是预处理不一致。
