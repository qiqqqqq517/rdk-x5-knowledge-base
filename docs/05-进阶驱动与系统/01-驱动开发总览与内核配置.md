# 5.1 驱动开发总览与内核配置

## 本章解决什么

当你在 RDK X5 上要接一个官方没支持的外设、要改一路总线的默认状态、要给内核打实时补丁、或者模型跑起来报 `ion_alloc` 失败时，问题已经不在应用层，而在 BSP（板级支持包）这一层。本章把 X5 的源码树结构、设备树分层、uboot/kernel 的配置与编译入口、内核头文件与模块开发、PREEMPT_RT 实时内核切换、以及 DDR 与 ION/BPU 保留内存的划分与调整方式讲清楚。

读完本章你应该能做到：拿到一块 X5，知道自己该改哪一层文件、改完走哪条命令编译、编译产物放到板子哪个目录、以及哪些改动必须重新烧录整机。

> 来源：官方文档 Advanced_development__linux_development__driver_development_x5__uboot_kernel_config（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/driver_development_x5/uboot_kernel_config）

## 5.1.1 BSP 源码树结构

RDK X5 的 SDK 与 X3 是**两套不同的仓库**，这是最容易踩的第一个坑：X3 的源码在 `rdk-gen`，X5 的在 `x5-rdk-gen`，两边的目录名、脚本名、defconfig 文件名都不一样，互相套用必然失败。

| 项目 | RDK X3 | RDK X5 |
| --- | --- | --- |
| 源码仓库 | `D-Robotics/rdk-gen` | `D-Robotics/x5-rdk-gen` |
| uboot 配置文件名 | 板级配置指定 | `board_x5_rdk_ubuntu_nand_sdcard_debug_config` |
| uboot defconfig | 板级指定 | `hobot_x5_rdk_nand_defconfig` |
| kernel defconfig | 板级指定 | `hobot_x5_rdk_ubuntu_defconfig` |
| 内核版本基线 | 4.14 / 5.10 系列 | Linux 6.1.83 |

X5 的 bootloader 目录结构如下，理解它才知道配置改在哪：

```text
source/bootloader/
├── build     # 编译系统代码目录，提供编译各功能模块的 shell 脚本与工具
├── device    # 板级配置目录，每种硬件一份配置文件，可设置编译选项与分区表
├── miniboot  # 生成包含 gpt、mbr、bl2、ddr、bl3x 一体的最小启动固件
├── out       # 编译输出目录
└── uboot     # Uboot 源代码
```

板级配置的实际取值，可以在 `./xbuild.sh lunch` 之后查看 `bootloader/device/.board_config.mk` 里的 `HR_UBOOT_CONFIG_FILE` 变量确认。**不要凭记忆假设自己用的是哪个 defconfig**，先 `lunch` 再看。

> 来源：官方文档 Advanced_development__linux_development__driver_development_x5__uboot_kernel_config（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/driver_development_x5/uboot_kernel_config）

## 5.1.2 设备树的分层结构

内核 DTS 位于 `x5-rdk-gen/source/kernel/arch/arm64/boot/dts/hobot/`。X5 的设备树不是一个大文件，而是分层包含的，改错层会导致「改了没效果」或者「整机起不来」。

| dts 文件 | 作用 | 是否建议修改 |
| --- | --- | --- |
| `pinmux-func.dtsi` | 定义各个 PIN 的功能组（uart2grp、i2c2grp 等） | 需要新增功能组时才改 |
| `pinmux-gpio.dtsi` | 定义 GPIO 组（lsio_gpio0_8 等） | 引脚要从 GPIO 改回外设时要改 |
| `x5.dtsi` | 声明 X5 平台上所有模块的默认配置，描述 SoC 共有特性 | **不建议修改** |
| `x5-rdk.dtsi` | 不同 SDK 硬件版本间的通用配置项，包含 `x5.dtsi` | 版本间共性差异时改 |
| `x5-<板级产品>.dts` | 板级设备树，完成功能模块启用/禁用与硬件强相关外设定义 | 主要改这里 |

调用关系是一条单向链：

```text
x5-板级产品.dts -> x5-rdk.dtsi -> x5.dtsi -> (pinmux-func.dtsi and pinmux-gpio.dtsi)
```

板级 dts 由 `board_id` 决定，`board_id` 可以用 `hrut_boardid` 命令读取，也可以看板卡丝印：

| 硬件编号 | board_id | dts 文件 |
| --- | --- | --- |
| RDK X5 V0.1 | 0x301 | `x5-rdk.dts` |
| RDK X5 V1.0 | 0x302 | `x5-rdk-v1p0.dts` |
| RDK X5 MD V0.1 | 0x501 | `x5-md-v0p1.dts` |
| RDK X5 MD V0.2 | 0x502 | `x5-md-v0p2.dts` |
| RDK X5 MD V0.3 | 0x503 | `x5-md-v0p2.dts` |
| RDK X5 MD V1.0 | 0x504 | `x5-md-v0p2.dts` |
| RDK X5 MD V1.1 | 0x505 | `x5-md-v0p2.dts` |

注意 MD V0.2 之后的几个版本**共用同一份 dts**，如果你手上是 MD V1.1 却去改 `x5-md-v0p3.dts`（不存在），那必然是无效改动。

```bash
# 确认当前板子的 board_id，改设备树之前先跑这条
sudo hrut_boardid
```

> 来源：官方文档 Advanced_development__linux_development__driver_development_x5__uboot_kernel_config（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/driver_development_x5/uboot_kernel_config）、Appendix__rdk-command-manual__cmd_hrut_boardid_rdkx5（https://developer.d-robotics.cc/rdk_x_doc/Appendix/rdk-command-manual/cmd_hrut_boardid_rdkx5）

### 5.1.2.1 编译设备树并生效

在内核源码目录 `x5-rdk-gen` 下执行：

```bash
cd x5-rdk-gen
sudo ./mk_kernel.sh
```

编译完成后 dtb 生成在 `x5-rdk-gen/deploy/kernel/dtb/`，把它拷到板端 `/boot/hobot/`，系统启动时会自动加载。也可以打成 deb 包安装：

```bash
sudo ./mk_debs.sh hobot-dtb
# 产物：x5-rdk-gen/deploy/deb_pkgs/hobot-dtb_version-data_arm64.deb
```

**前提说明**：改设备树属于 BSP 层改动，改完必须重新编译 dtb 并替换板端文件（或重打 deb 安装），然后**重启**才生效。只改源码不编译，板上不会有任何变化。

> 来源：官方文档 Advanced_development__linux_development__driver_development_x5__uboot_kernel_config（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/driver_development_x5/uboot_kernel_config）

## 5.1.3 uboot 选项配置

### 5.1.3.1 走 xbuild 交互式配置（推荐）

`build/xbuild.sh` 是主编译脚本，它自动使用板级配置里指定的 uboot 配置文件，配置完成后自动执行 `savedefconfig` 并回写：

```bash
cd source/bootloader
./xbuild.sh uboot menuconfig
```

退出时选 Yes/No 保存到 `.config`，脚本随后自动完成两步：

```bash
# 调用 savedefconfig 清理配置文件，保留必须项、删除被依赖项，生成 defconfig
make savedefconfig
# 用 defconfig 覆盖板级配置文件中设置的 uboot 配置文件
cp -f defconfig
```

### 5.1.3.2 手动配置

```bash
cd source/bootloader/uboot
make ARCH=arm64 hobot_x5_rdk_nand_defconfig
make ARCH=arm64 menuconfig
# 改完先对比差异，确认改动符合预期
diff .config configs/hobot_x5_rdk_nand_defconfig
# 确认无误后覆盖默认配置
cp .config configs/hobot_x5_rdk_nand_defconfig
```

最后**必须清理源码目录下的 `.config` 等文件**，否则下次全量编译会报错：

```text
xxx is not clean, please run 'make mrproper'
```

```bash
make distclean
# 或者
make mrproper
```

> 来源：官方文档 Advanced_development__linux_development__driver_development_x5__uboot_kernel_config（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/driver_development_x5/uboot_kernel_config）

## 5.1.4 kernel 选项配置

kernel 用的配置文件由 `mk_kernel.sh` 中的 `kernel_config_file` 变量决定，示例中为 `hobot_x5_rdk_ubuntu_defconfig`。

```bash
cd x5-rdk-gen
./mk_kernel.sh menuconfig
```

交互界面退出后同样自动 `make savedefconfig` + `cp defconfig`。手动流程：

```bash
cd boot/kernel
make ARCH=arm64 hobot_x5_rdk_ubuntu_defconfig
make ARCH=arm64 menuconfig
diff .config arch/arm64/configs/hobot_x5_rdk_ubuntu_defconfig
cp .config arch/arm64/configs/hobot_x5_rdk_ubuntu_defconfig
make distclean
```

**改完要重新编译内核并烧录**。单独改 `.config` 而不重新编译、不重新烧写，板上内核行为不会变。这一点和改 config.txt（uboot 阶段读取，重启即生效）有本质区别，别混淆。

> 来源：官方文档 Advanced_development__linux_development__driver_development_x5__uboot_kernel_config（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/driver_development_x5/uboot_kernel_config）

## 5.1.5 内核头文件与内核模块开发

要在板端编译内核模块，先装头文件：

```bash
sudo apt install hobot-kernel-headers
```

头文件装在 `/usr/src`：

```bash
ls /usr/src/linux-headers-*
# arch certs Documentation firmware include ipc kernel Makefile Module.symvers ...
```

### 5.1.5.1 Hello World 模块

`hello.c`：

```c
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>

MODULE_LICENSE("GPL");
MODULE_AUTHOR("xxx.xxx");
MODULE_DESCRIPTION("Hello World");

static int __init hello_init(void)
{
    printk(KERN_ERR "Hello, World!\n");
    return 0;
}
static void __exit hello_exit(void)
{
    printk(KERN_EMERG "Goodbye, World!\n");
}

module_init(hello_init);
module_exit(hello_exit);
```

`Makefile`：

```make
ifneq ($(KERNELRELEASE),)
obj-m := hello.o
else
PWD=$(shell pwd)
KDIR := /usr/src/linux-headers-$(shell uname -r)

all:
	make -C $(KDIR) M=$(PWD) modules
clean:
	rm -rf *.ko *.o *.mod.o *.mod.c *.symvers modul* .*.ko.cmd .*.o.cmd .tmp_versions
endif
```

编译、加载、卸载：

```bash
make
sudo insmod hello.ko
# [ 3104.480703] Hello, World!
sudo rmmod hello
# [ 3136.909409] Goodbye, World!
lsmod | grep hello
```

### 5.1.5.2 模块签名：X5 与 X3 的关键差异

| 平台 | 模块签名机制 | 说明 |
| --- | --- | --- |
| RDK X5 | **未启用** | 编译好的 `.ko` 可直接 `insmod` |
| RDK X3（3.0.1 及以后） | 已取消 | 可直接加载 |
| RDK X3（3.0.1 之前） | 需要签名 | 须 `hobot-sign-file hello.ko` |

旧版本 X3 上加载未签名模块会报：

```text
insmod: ERROR: could not insert module hello.ko: Required key not available
```

**X5 用户不用管签名这一步**。网上大量以 X3 旧系统为例的教程要求 `hobot-sign-file`，那是历史包袱，照抄只会多此一举。

### 5.1.5.3 开机自动加载

```bash
sudo cp -f hello.ko /lib/modules/`uname -r`
sudo depmod
sudo echo hello > /lib/modules-load.d/hello.conf
```

`hello.conf` 里写模块名（不带 `.ko`），一行一个。

> 来源：官方文档 Advanced_development__linux_development__kernel_headers（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/kernel_headers）

## 5.1.6 实时内核（PREEMPT_RT）切换

X5 和 X3 的实时内核启用**方式完全不同**，这是第二个高频误引点。

### 5.1.6.1 X5：改 boot.cmd，不装 deb 包

X5 官方镜像里已经预置了 `Image-rt`，切换靠改 uboot 启动脚本：

1. 编辑 `/boot/boot.cmd`，把 `imagefile="Image"` 改成 `imagefile="Image-rt"`。
2. 在 `/boot/` 目录下重新生成 boot.scr：

```bash
cd /boot
sudo mkimage -C none -A arm -T script -d boot.cmd boot.scr
```

3. 重启系统，`uname -a` 里应能看到 PREEMPT RT 字样。

切回标准内核就是把 `imagefile="Image-rt"` 改回 `imagefile="Image"`，其余步骤相同。

### 5.1.6.2 X3：装 ~rt 结尾的 deb 包

```bash
sudo apt update
sudo apt install hobot-kernel-headers=2.0.0-01~rt hobot-boot=2.0.2-01~rt hobot-bpu-drivers=2.0.0-01~rt
sudo reboot
```

**不要把这条命令用到 X5 上**。X5 的包版本号体系与 X3 不同，强行安装 `2.0.0-01~rt` 这类指定版本的包，轻则装不上，重则把 boot 包替换成不匹配版本导致无法启动。

### 5.1.6.3 风险提示与验证

官方对预编译实时内核的定位说得很明确：

- 它是**社区维护的衍生分支，非官方主线内核**；
- **未经过大规模工业应用验证**，稳定性与兼容性需自行评估；
- 建议仅在充分测试、可接受风险的场景部署。

Linux 默认内核不具备实时性，需要引入 PREEMPT-RT 补丁（如 `patch-6.1.83-rt28`）才能改造。

实时性用 `rt-tests` 里的 `cyclictest` 量化：

```bash
sudo apt install rt-tests
sudo cyclictest -l50000000 -m -S -p90 -i200 -h400
```

| 参数 | 含义 |
| --- | --- |
| `-l50000000` | 循环次数 |
| `-m` | 用 mlock 锁定内存，防止 swap 影响测试 |
| `-S` | 标准 SMP 架构测试，各线程使用相同 `-a -t -n` 与优先级 |
| `-p90` | 实时线程优先级 90 |
| `-i200` | 线程睡眠间隔（微秒） |
| `-h400` | 输出直方图，并统计延时小于 400 微秒的次数 |

输出字段：`T`（线程号）、`P`（优先级）、`I`（预期唤醒周期 us）、`C`（循环计数）、`Min`/`Act`/`Avg`/`Max`（最小/实际/平均/最大延迟 us）。**看 Max 而不是 Avg**——实时性翻车永远是最大延迟超标。

> 来源：官方文档 Advanced_development__linux_development__realtime_kernel（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/realtime_kernel）

## 5.1.7 DDR 内存布局与保留内存

这是本章最需要精确记忆的一张表。X5 的 Linux 可访问 DDR 范围是 `0x8400_0000` 到 `0x8000_0000 + DDR 容量`，但内核设备树里保留了相当大一块给专用模块：

| 内存划分 | 内存作用 | 内存区域 | 内存大小 |
| --- | --- | --- | --- |
| `kernel_ram` | 存放内核代码和数据 | `0x8000_0000..0x87FF_FFFF` | 128MB |
| `uboot_log_reserved` | 供内核获取启动日志 | `0x87FFC000..0x87FFFFFF` | 16KB |
| `cma_reserved` | CMA 内存分配 | `0x88000000..0x9FDFFFFF` | 382MB |
| `firewall_ddr_default` | 违反 firewall 访问时被导向的地址 | `0x9FE7F000..0x9FE7FFFF` | 4KB |
| `adsp_ddr` | ADSP 固件使用 | `0x9FE80000..0xA207FFFF` | 34MB |
| `ramoops_reserved` | ramoops 临时内存 | `0xA4080000..0xA40BFFFF` | 256KB |
| `ion_reserved` | ION 内存分配 | `0xA4100000..0xD40FFFFF` | 768MB |

保留地址空间定义在 `arch/arm64/boot/dts/hobot/x5-memory.dtsi`。保留内存总共约占 **1150MB**。

**关键推论**：`free` 命令显示的可用内存已经排除了这部分保留内存，只反映内核可实际使用的容量。所以你买 8GB 版本的 X5，`free -h` 看不到 8G 是正常的，不是内存坏了。

```bash
# 看真实的内存分配情况，比 free 更能说明问题
cat /proc/iomem
```

启动日志里也能看到这些区域被创建（真实板端输出）：

```text
[ 0.187427] Reserverd ion-pool MEM start 0xa4100000, size 0x14000000
[ 0.187453] Reserverd ion-carveout MEM start 0xb8100000, size 0x14000000
[ 0.187472] Reserverd shared-dma-pool MEM start 0x88000000, size 0x17e00000
[ 0.187562] Reserverd ion-cma MEM start 0xcc100000, size 0x8000000
```

> 来源：官方文档 Advanced_development__linux_development__driver_development_x5__memory（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/driver_development_x5/memory）、社区帖 28651（https://forum.d-robotics.cc/t/topic/28651）

### 5.1.7.1 ION 是什么、被谁用

ION 是 Linux 内核里管理设备间内存共享的子系统。X5 上 ION 内存主要被四类使用者占用：

- BPU 子系统
- HIFI 子系统（DSP）
- 开发者通过 `hbmem` 接口分配的 ION 内存
- 多媒体系统：VIN、ISP、VSE、GDC、VPU、OSD、GPU、Display

X5 主要使用 3 个 ION 区域：

| 区域 | 主要用途 | 空间不足时的行为 |
| --- | --- | --- |
| `cma_reserved` | 多媒体系统 | — |
| `carveout` | BPU 子系统 | — |
| `ion_cma` | 备用区域 | 上述两区无空间时，ION 自动从 `ion_cma` 申请 |

> 来源：官方文档 Advanced_development__linux_development__driver_development_x5__memory（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/driver_development_x5/memory）

### 5.1.7.2 三种调整 ION 的方式

**方式一：srpi-config（推荐普通用户）**

```bash
sudo srpi-config
# 进入 Performance Options -> ION memory
```

官方描述默认配置大小为 672MB。需要跑大模型、或多路视频同时编解码时按需调大。

**方式二：config.txt 的 ion 参数（X5 专用）**

通过 `ion_reserved_size`、`ion_carveout_size`、`ion_cma_size` 修改 boot 环境变量，进而改 ION 分区大小：

| boot 环境变量名 | dts 标签 | dts compatible 字符串 | 默认大小 |
| --- | --- | --- | --- |
| `ion_reserved_size` | `ion_reserved` | `ion-pool` | 320M |
| `ion_carveout_size` | `ion_carveout` | `ion-carveout` | 320M |
| `ion_cma_size` | `ion_cma` | `ion-cma` | 128M |

编辑 `/boot/config.txt`（需 root）：

```text
ion=ion_reserved_size=0x14000000
ion=ion_carveout_size=0x14000000
ion=ion_cma_size=0x08000000
```

验证：

```bash
dmesg | grep "Reserved ion"
# [ 0.207939] Reserved ion-pool MEM start 0xa4100000, size 0x14000000
# [ 0.207964] Reserved ion-carveout MEM start 0xb8100000, size 0x14000000
# [ 0.208068] Reserved ion-cma MEM start 0xcc100000, size 0x8000000
```

**方式三：设备树 dtoverlay**

X3 上用 `dtoverlay=ion_resize,size=0x40000000` 这类写法调 ION。X5 上这条 overlay 不适用，X5 的 ION 调整走上面的 `ion=` 参数，或者用 `dtoverlay=dtoverlay_spi5_spidev` 这类 X5 专用 overlay（后者用于增加 `/dev/spidev5.0`，与 CAN 二选一）。

**这是 X3 与 X5 config.txt 语法的高频混淆点**：X3 用 `dtoverlay=ion_resize,size=`，X5 用 `ion=ion_reserved_size=` 三条。写错不会报错，只会静默不生效。

> 来源：官方文档 System_configuration__config_txt（https://developer.d-robotics.cc/rdk_x_doc/System_configuration/config_txt）、System_configuration__srpi-config（https://developer.d-robotics.cc/rdk_x_doc/System_configuration/srpi-config）

### 5.1.7.3 BPU 保留内存的运行时调整

当 ION 选择 cma 作为内存池时，BPU mem 的空间从 cma 区域划分。该空间可在系统启动后改 sysfs 节点：

```bash
# 单位 Mbyte
echo 100 | sudo tee /sys/class/misc/ion/cma_carveout_size
```

约束条件要记牢：

- 只有当**没有用户使用 BPU_MEM** 时才能修改成功；
- 该空间是从 cma 中申请的**连续物理地址**，可申请到的最大大小达不到 cma 总大小；
- BPU_MEM 从这个空间申请不到足够内存时，系统会尝试从该空间之外的 cma 空间申请；
- 因为是从 cma 分配连续物理空间，设置**有可能失败**。设完再 `cat` 一次，成功就是设置的值，失败就是 0；
- 设 0 表示 BPU 只用 cma 动态分配；
- 多路场景下若 VIO 报 `ion_alloc` 错误，可适当**降低**这个值（最小可到 0），给多媒体系留出 cma；
- 若无此 sys 节点，说明该版本不支持这种配置方式。

```bash
# 设置后必须回读确认，不要假设成功
cat /sys/class/misc/ion/cma_carveout_size
```

> 来源：官方文档 Advanced_development__linux_development__driver_development__driver_bpu_mem_dev（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/driver_development/driver_bpu_mem_dev）

## 5.1.8 BPU 频率与核的 sysfs 控制

BPU 的调试接口在 `/sys/devices/system/bpu`，`bpu0`/`bpu1` 分别对应两个核。

```bash
# 关闭 BPU Core
echo 0 > /sys/devices/system/bpu/bpu0/power_enable

# 热拔插（不影响单核模型，不支持双核模型；启用后不会自动关闭）
echo 1 > /sys/devices/system/bpu/bpu0/hotplug
echo 0 > /sys/devices/system/bpu/bpu0/power_enable

# 降低功耗等级（不关闭核心，只降频/降功耗）
echo -2 > /sys/devices/system/bpu/bpu0/power_level

# 手动定频
echo userspace > /sys/devices/system/bpu/bpu0/devfreq/devfreq*/governor
cat /sys/devices/system/bpu/bpu0/devfreq/devfreq*/available_frequencies
echo 600000000 > /sys/devices/system/bpu/bpu0/devfreq/devfreq*/userspace/set_freq
cat /sys/devices/system/bpu/bpu0/devfreq/devfreq*/cur_freq
```

`power_level` 取值语义：`1` 为 Linux DVFS 动态调节；`0` 为性能优先、最高功耗；`< 0` 时在范围内值越小功耗等级越低。

另一条路径也可用，即 `/sys/class/devfreq/3a000000.bpu`，支持频点为 `500000000` 与 `1000000000` 两档，governor 支持 `userspace` / `performance` / `powersave`。

> 来源：官方文档 Advanced_development__linux_development__driver_development__driver_bpu_sysfs_dev（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/driver_development/driver_bpu_sysfs_dev）、Advanced_development__linux_development__driver_development_x5__driver_lowpower（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/driver_development_x5/driver_lowpower）

## 5.1.9 BSP 开发环境与编译流程

X5 的完整系统构建依赖 `x5-rdk-gen` 仓库。这个仓库不是一个普通的「源码包」，而是一套带 `lunch` 菜单的构建系统，它的作用是把你选的板型、镜像类型、文件系统类型组合成一组编译参数，再分发给 uboot、kernel、rootfs 各自的编译脚本。

搭建流程的入口在仓库 README，但要理解它做了什么：

```bash
# 1. 拉取源码
git clone https://github.com/D-Robotics/x5-rdk-gen.git
cd x5-rdk-gen

# 2. 安装构建环境（仓库 README 里有完整依赖列表，通常是 Docker 方案）
# 3. 选择板型与镜像配置
./xbuild.sh lunch

# 4. 全量编译
sudo ./xbuild.sh all
```

`lunch` 这一步写入的结果落在 `bootloader/device/.board_config.mk`，后续所有编译脚本都从这里读板级参数。所以出现「编译出来的镜像烧上去跑不起来」，第一步永远是确认 `lunch` 选对没有——选了 X5 V0.1 的配置烧到 X5 V1.0 的板子上，dtb 与实际硬件不匹配，表现就是外设全废或者直接起不来。

几个常用局部编译入口：

| 目标 | 命令 | 产物位置 |
| --- | --- | --- |
| 只编内核与 dtb | `sudo ./mk_kernel.sh` | `deploy/kernel/dtb/` |
| 只编 dtb 的 deb | `sudo ./mk_debs.sh hobot-dtb` | `deploy/deb_pkgs/` |
| uboot 配置 | `./xbuild.sh uboot menuconfig` | 回写板级 defconfig |
| 内核配置 | `./mk_kernel.sh menuconfig` | 回写板级 defconfig |

**交叉编译工具链**：X5 的内核用 `aarch64-none-linux-gnu-gcc` 11.2 系列构建，从板端启动日志能直接确认：

```text
Linux version 6.1.83 (root@hobot) (aarch64-none-linux-gnu-gcc
(GNU Toolchain for the Arm Architecture 11.2-2022.02 (arm-11.14)) 11.2.1 20220111 ...)
```

在板端编应用层测试程序时用的工具链版本不同（如 `arm-gnu-toolchain-11.3.rel1`），这不影响内核模块——**内核模块必须用与目标内核完全一致的工具链和头文件编译**，否则即使 `insmod` 成功，运行时也会因为结构体布局或符号版本不一致而出问题。

> 来源：官方文档 Advanced_development__linux_development__environment_build（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/environment_build）、社区帖 28651（https://forum.d-robotics.cc/t/topic/28651）

## 5.1.10 驱动调试的通用定位链路

不管调哪一路总线，X5 上的排查顺序是固定的。按这个顺序走，能避免「在应用层瞎改」的低效循环。

| 层级 | 确认什么 | 用什么命令 |
| --- | --- | --- |
| 硬件 | 供电、地、电平、接线 | 万用表、示波器、逻辑分析仪 |
| 引脚复用 | 这个物理脚当前被配成什么功能 | `hb_gpioinfo`、`/sys/kernel/debug/pinctrl/*/pinmux-pins` |
| 设备树 | 控制器节点 status 是否为 `okay` | `cat /sys/firmware/devicetree/base/model` 先确认 dtb 对不对 |
| 驱动加载 | 驱动模块是否在 | `lsmod`、`dmesg \| grep <驱动名>` |
| 字符设备 | `/dev/<节点>` 是否存在 | `ls /dev/` |
| 总线通信 | 总线上有没有器件应答 | `i2cdetect`、`candump`、回环测试 |
| 应用层 | 数据是否正确 | 官方 sample 程序 |

第一层「硬件」被跳过是新手最常见的浪费。特别是 40PIN：X5 的 40PIN GPIO 都是 3.3V 逻辑，**最大耐压 3.46V**，3.3V 最大输出 800mA、5V 最大输出 500mA，且在这个电流下要求输入适配器至少 25W 带载能力。用杜邦线接外设时必须先断电——带电接线导致的过压/过流/ESD 损伤是不可逆的。

第二层「引脚复用」是 X5 上独有的坑，因为 X5 有 308 个 IO 功能管脚，其中 129 个可配 GPIO，而每一路的复用关系分布在 `pinmux-func.dtsi`（功能组）和 `pinmux-gpio.dtsi`（GPIO 组）两个文件里，两边都声明同名引脚就会冲突。判断当前实际生效的是哪个，用 debugfs：

```bash
# X5 的 lsio 域 pinctrl 调试节点
ls /sys/kernel/debug/pinctrl/34180000.lsio_iomuxc/
# gpio-ranges pinconf-groups pinconf-pins pingroups pinmux-functions pinmux-pins pinmux-select pins

cat /sys/kernel/debug/pinctrl/34180000.lsio_iomuxc/pinmux-pins
```

输出里 `(MUX UNCLAIMED) (GPIO UNCLAIMED)` 表示这个脚既没被任何驱动用 pinctrl 领走、也没被当 GPIO 领走，就是空闲状态；出现 `341a0000.serial ... group uart5grp` 就说明被 uart5 占了。这一步能直接回答「我明明在 dts 里开了 uart2，为什么没波形」——多半是 dts 没编译进去，或者被同组的其他功能抢了。

> 来源：官方文档 Advanced_development__linux_development__driver_development_x5__driver_pinctrl_dev（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/driver_development_x5/driver_pinctrl_dev）、Basic_Application__01_40pin_user_sample__40pin_define（https://developer.d-robotics.cc/rdk_x_doc/Basic_Application/01_40pin_user_sample/40pin_define）

### 5.1.10.1 关于 `hb_gpioinfo`

X5 上 Linux 的 GPIO 序号是纯软件概念，会随软件改动而变化，与芯片 Pin 脚没有物理绑定。所以**不要记 GPIO 编号，要查**：

```bash
# 若板卡上还没有该工具，先更新 hobot-io
sudo apt update && sudo apt install --reinstall hobot-io
hb_gpioinfo
```

输出三列关键信息：

- `PinName`：SoC 上的管脚名字，与原理图上的 X5 SoC 管脚命名一致（如 `LSIO_UART3_RX`）；
- `PinNum`：X5 实际对应的 GPIO 编号（如 389）；
- `PinFunc`：设备树中已使用的复用功能名（如 `i2c5grp`）。**若显示 `Default`，表示设备树没用这个复用功能**，此时要去查 pinlist 里该脚的默认功能是什么。

这个「`Default` 不等于空闲」的细节很重要：一个脚显示 `Default` 但它默认功能可能是某个外设，直接当 GPIO 用会冲突。

> 来源：官方文档 Advanced_development__linux_development__driver_development_x5__driver_gpio_dev（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/driver_development_x5/driver_gpio_dev）

## 5.1.11 改 BSP 的风险边界

必须明确一件事：设备树和内核配置的修改权限很大，出错代价也很大。官方原文的警告值得完整引用一遍——

> DTS 文件用于描述硬件资源分配（如 GPIO、I²C、SPI、中断号、内存地址等）。错误修改可能导致设备无法启动、驱动加载失败，甚至造成硬件损坏。错误配置可能导致编译失败、系统无法正常引导，甚至需要重新刷写系统镜像恢复。

对应的工程纪律：

1. **改之前备份**。至少备份 `/boot/hobot/` 下原始 dtb，和源码树里原始 `.dts`。
2. **一次只改一处**，改完立即验证，不要攒一堆改动一起编译。
3. **`/boot/hobot/` 下的文件由 D-Robotics 软件包管理**，升级系统软件时用户改动会被重置为默认值。所以「改板端 dtb」这种做法只适合临时验证，正式方案必须改源码树里的 dts 并出 deb 包，否则一次 `apt upgrade` 就回到解放前。
4. **优先用 overlay 而不是改原文件**。X5 的 `config.txt` 支持 `dtoverlay`，能用 overlay 解决的（如加一个 spidev 节点）就不要动板级 dts。

> 来源：官方文档 Advanced_development__linux_development__driver_development_x5__uboot_kernel_config（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/driver_development_x5/uboot_kernel_config）、Advanced_development__linux_development__driver_development__driver_bpu_mem_dev（https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/linux_development/driver_development/driver_bpu_mem_dev）

排查驱动问题时，先把平台状态一次性抓全，比逐条猜要快得多。

| 命令 | 作用 |

## 常见误区

1. **把 X3 的 defconfig 名套到 X5 上**。X5 的 kernel defconfig 是 `hobot_x5_rdk_ubuntu_defconfig`，uboot 是 `hobot_x5_rdk_nand_defconfig`。文档里出现 `hobot_x5_soc_defconfig` 的地方（如 I2C/SPI 内核配置段）指的是 SoC 级配置，不是板级 defconfig——这两个是不同的文件层级，不要互相替换。改之前先在 `bootloader/device/.board_config.mk` 和 `mk_kernel.sh` 里确认实际取值。

2. **改完设备树/内核不重编译就期待生效**。改 `.dts` 必须 `sudo ./mk_kernel.sh` 重编 dtb 并替换到 `/boot/hobot/`（或装 deb）再重启；改 kernel `.config` 必须重编内核并重新烧录。只有 `/boot/config.txt` 是 uboot 阶段读取、重启即生效的。三者生效路径完全不同。

3. **用 `free` 判断 DDR 是否正常**。X5 默认保留约 1150MB 给 kernel_ram、cma、adsp、ion 等区域，`free` 只显示内核可实际使用的部分。要看全貌用 `cat /proc/iomem` 或启动日志里的 `Reserverd ... MEM start`。

4. **在 X5 上照抄 X3 的实时内核 apt 命令**。X3 是 `apt install hobot-kernel-headers=2.0.0-01~rt hobot-boot=2.0.2-01~rt hobot-bpu-drivers=2.0.0-01~rt`，X5 是改 `/boot/boot.cmd` 里的 `imagefile` 并用 `mkimage` 重生成 `boot.scr`。把 X3 的包版本号硬装到 X5 上有让系统起不来的风险。

5. **以为 X5 上还有 `dtoverlay=ion_resize`**。X5 的 ION 调整是 `config.txt` 里三条 `ion=ion_*_size=` 参数，或走 `srpi-config` 的 ION memory 选项。写 X3 的 overlay 名不会报错，只会静默不生效——这是最难发现的失败模式，因为它看起来「配置成功了」。
