# 1.2 系统镜像烧录

## 本章解决什么

RDK X5 的「装系统」包含两件互相独立的事：把 Ubuntu 系统镜像写进 Micro SD 卡（或 eMMC），以及把 miniboot / U-Boot 这类底层固件写进板载 NAND。前者决定你能不能进系统，后者决定板子能不能把 CPU 和内存在正确的参数下拉起来。混为一谈是新手最常犯的错误——镜像烧得很成功却起不来，八成是 miniboot 版本太旧；反过来，miniboot 刚升完却进不去系统，八成是卡上的镜像本身有问题。本章按「选镜像 → 校验 → 选工具 → 烧卡 → 升 miniboot → 选启动介质 → 排障」的顺序把这两条链路拆开讲清，并标明每一处在 RDKOS 3.0.0 到 3.5.0 之间的版本差异。

> 来源：官方文档 Quick_start/system-burn/overview（https://developer.d-robotics.cc/rdk_x_doc/Quick_start/system-burn/overview）

## 1.2.1 版本体系：先搞清自己该装哪个版本

选版本的硬规则：

- 新板先用最新版。官方明确「为确保使用最新版本的系统，建议完成最新版本系统镜像的烧录」。
- **X5 Module 只能使用 3.2.0 及其后续版本的系统**。这条是硬限制，烧 3.0.x/3.1.x 会直接起不来。
- 涉及 Python 推理代码的项目，3.5.0 是分水岭。3.5.0 之前是 `pyeasy_dnn` / `hobot_dnn`，3.5.0 起统一为 `hbm_runtime`，示例代码不能混用。
- 老项目锁版本时，3.3.3 与 3.4.1 都是长期验证过的稳定点；3.2.3 之后的版本才带 Uart7 与实时内核切换。

### 1.2.1.2 desktop 与 server 的取舍

官方镜像同时提供两个形态：

| 形态 | 内容 | 适用 |
| --- | --- | --- |
| desktop | 带桌面的 Ubuntu，可外接屏幕、鼠标操作 | 需要 GUI、跑 VNC、现场调试 |
| server | 无桌面，可通过串口、网络远程连接 | 无人值守、机器人本体、算力全给算法 |

server 版不是「desktop 删掉桌面」这么简单——FAQ 里明确说明：「RDK OS 的 Server 版和 Desktop 版在预装的软件包上存在显著差异……官方通常不提供或不推荐这种手动升级路径，并且不对通过此方式构建的 Desktop 系统的稳定性和功能完整性进行保证或测试」。所以 server 想变 desktop，正确做法是重烧 desktop 镜像，而不是 `apt install xfce4`。

> 来源：官方文档 Quick_start/system-burn/burn-sd-card（https://developer.d-robotics.cc/rdk_x_doc/Quick_start/system-burn/burn-sd-card）、官方文档 FAQ/hardware_and_system（https://developer.d-robotics.cc/rdk_x_doc/FAQ/hardware_and_system）

## 1.2.2 获取镜像与解压

官方下载入口是 `https://archive.d-robotics.cc/downloads/os_images/rdk_x5/`，进入后按版本号目录选择，再选 desktop 或 server。

解压规则有一条容易漏的版本差异，官方写得很清楚：

| 烧录工具 | 镜像文件形态 |
| --- | --- |
| XBurn | **必须解压为 `.img`** |
| RDK Studio | 可直接选择压缩包 |
| Rufus | 可直接选择压缩包 |

命名规律可以拿官方示例做参照：`rdk-x5-ubuntu22-preinstalled-desktop-3.3.3-arm64.img`。看到这个格式就知道是 X5、Ubuntu 22.04、desktop、3.3.3、arm64。

镜像完整性校验：官方没有在烧录章节给出统一的 SHA256 清单，FAQ 的建议是「尝试重新下载镜像文件，并校验其 MD5/SHA256 值（如果官方提供）以确保文件完整性」。实操上，下载目录页若提供校验值就用，没有的话至少确认文件大小与页面标注一致、且解压过程不报错。

> 来源：官方文档 Quick_start/system-burn/burn-sd-card（https://developer.d-robotics.cc/rdk_x_doc/Quick_start/system-burn/burn-sd-card）、官方文档 FAQ/hardware_and_system（https://developer.d-robotics.cc/rdk_x_doc/FAQ/hardware_and_system）

## 1.2.3 烧录工具选型

官方的工具选型表是本章最重要的一张表，因为它同时区分了「烧系统镜像」和「升级 miniboot」两种能力：

| 工具 | 烧录系统镜像 | 升级 miniboot | 平台 | 说明 |
| --- | --- | --- | --- | --- |
| Rufus | 支持 | 不支持 | Windows | 支持 SD 卡单独烧录、SD 卡在板烧录、eMMC 烧录 |
| RDK Studio | 支持 | 不支持 | Windows / Mac | 可在线下载或本地导入镜像 |
| XBurn | 支持 | 支持 | Windows / Linux / macOS | 两种都能烧 |
| rdk-miniboot-update | 不支持 | 支持 | 板端命令行 | 系统正常运行 + 联网时可用 |

这里有一处必须指出的官方文档矛盾：`system-burn/overview` 的工具表列出的是 Rufus / RDK Studio / XBurn / rdk-miniboot-update 四款，**balenaEtcher 并未出现在官方工具表中**；而 FAQ Q29 却写「使用烧录工具（如 balenaEtcher, Rufus）向 SD 卡烧录系统镜像时失败」——也就是 FAQ 把 balenaEtcher 当成了常规选项。社区侧的分歧更大：帖 32282 里有人建议「推荐使用rufus烧录sd卡，RDK 手册中有提供下载，Balenatcher是容易失败」，帖 34973 的自动回复又建议「用BalenaEtcher烧录3.3.3稳定版镜像」。

判断依据：以官方工具表为准，**首选 Rufus（Windows）或 RDK Studio**，XBurn 用于需要同时刷 miniboot 或刷 eMMC 的场景。balenaEtcher 可以作为备选，但遇到「烧录提示成功、上电不启动」时，第一件事就是换工具重烧——帖 32282 的提问者正是在 RDK Studio、闪连、balenaEtcher 三种方式都「提示成功」但板子不启动的情况下卡住的。

关于 RDK Studio 的成功率，帖 32282 里官方人员的回复是「RDK Studio烧录体验这一块目前还在优化中，目前版本不能保证百分百的成功率」。这句话应当作为选工具的权重依据。

> 来源：官方文档 Quick_start/system-burn/overview（https://developer.d-robotics.cc/rdk_x_doc/Quick_start/system-burn/overview）、官方文档 FAQ/hardware_and_system（https://developer.d-robotics.cc/rdk_x_doc/FAQ/hardware_and_system）、社区帖 32282（https://forum.d-robotics.cc/t/topic/32282）、社区帖 34973（https://forum.d-robotics.cc/t/topic/34973）

## 1.2.4 用 Rufus 烧 SD 卡

### 1.2.4.1 场景一：SD 卡单独烧录（读卡器）

这是最稳的方式，把卡从板子上取下来插读卡器：

1. 将 SD 卡插入读卡器，读卡器插入 PC。
2. 打开 Rufus，「设备」下拉框会自动识别到 Micro SD 卡。
3. 点「选择」按钮，选解压出来的 `.img` 文件。（官方原文这一处写的是「选择解压出来的 .img 文件」，与 2.2 节「Rufus 可直接选择压缩包」略有出入；实操上能选到 `.img` 就选 `.img`，最保险。）
4. 其他参数保持默认，点「开始」，等待完成。
5. 完成后关闭 Rufus 并取出存储卡。

关于「其他参数保持默认」这句，社区有不同意见。帖 34478 的排查建议给出了更具体的一套设置：分区类型 GPT（不是 MBR）、目标系统 UEFI（非 CSM）、写入模式选「DD 镜像模式」。该帖的理由是「RDK X5 需要 GPT 分区表，MBR 可能导致启动失败」。这条建议**没有官方文档背书**，官方原文只说「其他参数保持默认」。两种说法的适用边界是：如果默认设置烧完能启动，就不用动；如果反复卡在 `Starting kernel …`，再按社区这套 GPT + DD 模式试一次。

### 1.2.4.2 场景二：SD 卡在板烧录

不想拔卡时用这个方式，板子会被枚举成 U 盘：

1. 打开 Rufus。
2. SD 卡插入开发板，USB Type-C 接到 PC 端。
3. **按住 Sleep 按键不放，给开发板上电**，观察 Rufus「设备」下拉框，直到出现 Micro SD 卡后松开按键。
4. 其余步骤与单独烧录一致。

注意第 3 步的时序：是「按住 → 上电 → 等识别 → 松开」，不是「上电 → 按键」。这个顺序搞反了，Rufus 里什么也不会出现。

### 1.2.4.3 场景三：eMMC 烧录（仅 X5 Module）

SD 卡不在板时，USB 连 PC，eMMC 会被映射为 U 盘：

1. 打开 Rufus。
2. SD 卡不在板时，USB Type-C 接到 PC 端，按住 Sleep 按键不放，给开发板上电，观察「设备」下拉框直到出现对应盘符后松开按键。开发板自带的 eMMC 会被映射成 U 盘。
3. 其余步骤与单独烧录一致。

> 来源：官方文档 Quick_start/system-burn/burn-sd-card（https://developer.d-robotics.cc/rdk_x_doc/Quick_start/system-burn/burn-sd-card）、社区帖 34478（https://forum.d-robotics.cc/t/topic/34478）

## 1.2.5 用 XBurn 烧镜像

XBurn 的硬件连接、环境准备、烧录参数与烧 miniboot 完全一致，区别只是「镜像所在目录」选成解压出的镜像文件夹。因此本节与 2.6 节的 XBurn 部分是同一套操作，务必先按 2.6.2 装好驱动。

XBurn 烧 eMMC 时：SD 卡不在板，产品类型选 X5，**存储介质固定为 eMMC**，连接类型与下载模式和烧 miniboot 一致。

> 来源：官方文档 Quick_start/system-burn/burn-sd-card（https://developer.d-robotics.cc/rdk_x_doc/Quick_start/system-burn/burn-sd-card）

## 1.2.6 升级 miniboot

### 1.2.6.1 为什么必须升级

miniboot 是 RDK 硬件的最小启动镜像，包含 miniboot、U-Boot 等底层固件，负责设备上电后的初始化与引导加载。官方给了一条铁律：**设备出厂已预装与硬件匹配的最新固件，严禁降级刷入旧版本，否则可能无法启动。**

这句话在 3.3.1 版本之后有了工具层面的强制：该版本起「rdk-miniboot-update 限制烧录旧版本 miniboot」。而 RDK 总览页补充了一条更容易被忽略的机制：**自 `hobot-miniboot_3.0.3` 版本起，`rdk-miniboot-update` 工具自动显示当前 NAND 固件版本与目标升级版本**，以降低升级风险。

升级时机：官方在 Release Note 开头就写了「更新系统后，请使用 `rdk-miniboot-update` 命令更新 NAND 固件至最新版本」。也就是说，**每次 apt 升级完系统，都应该跟一次 miniboot 升级**。这不是可选项——3.2.3 的更新说明里明确写了「集成了最新版的 miniboot 固件，使用 rdk-miniboot-update 命令烧录 NAND 后，会释放更多内存给系统」，而 3.3.1 修的是「8G 板卡内存减少 2G 的问题，需要更新 miniboot」——不升 miniboot，这个修复不会生效。

### 1.2.6.2 方式一：rdk-miniboot-update（系统能启动且联网）

前提：系统正常运行且已连接网络。

```bash
# 更新为最新版本（需要 sudo）
sudo rdk-miniboot-update
```

```bash
# 使用指定镜像文件（需要 sudo）
sudo rdk-miniboot-update -f /userdata/miniboot.img
```

```bash
# 查看当前会使用哪个镜像文件（不需要 sudo）
rdk-miniboot-update -l
```

`-l` 的典型输出形如：

```
/lib/firmware/rdk/miniboot/default/disk_nand_minimum_boot_2GB_3V3_20230413.img
```

参数含义：

| 选项 | 作用 |
| --- | --- |
| `-f` | 安装指定的文件，而不是安装最新适用的更新 |
| `-h` | 显示帮助文本并退出 |
| `-l` | 返回最新可用 miniboot 镜像的完整路径 |
| `-s` | 不显示进度消息 |

不带任何选项时，`rdk-miniboot-update` 会使用最新版本的 miniboot 镜像完成升级更新。

> 来源：官方文档 Appendix/rdk-command-manual/cmd_rdk-miniboot-update（https://developer.d-robotics.cc/rdk_x_doc/Appendix/rdk-command-manual/cmd_rdk-miniboot-update）、官方文档 Quick_start/system-burn/upgrade-miniboot（https://developer.d-robotics.cc/rdk_x_doc/Quick_start/system-burn/upgrade-miniboot）

### 1.2.6.3 方式二：XBurn（系统起不来，或要从 PC 端刷）

XBurn 通过 USB 和串口连接开发板，把 miniboot 固件写入板载 NAND。系统能否启动均可使用——这是它相对 `rdk-miniboot-update` 的核心优势。

**第一步：装驱动与依赖。** 官方强调这一步「烧录前必须完成，否则 XBurn 无法识别设备」，并按操作系统分开给了文档入口（Windows / Linux / macOS 三套环境准备）。跳过这步的典型现象是设备管理器里什么都看不到。

**第二步：下载固件。** 从 `https://archive.d-robotics.cc/downloads/miniboot/rdk_x5/` 下载最新版压缩包（官方示例为 `product_20260408.zip`），解压待用。

**第三步：硬件连接。**

| 连接 | 线材 | 用途 |
| --- | --- | --- |
| 串口连 PC | Micro-USB | Xmodem 传输与日志 |
| 烧录口连 PC | USB Type-C | Fastboot 下发 |
| 电源 | USB Type-C，5V/5A 适配器 | 供电 |

注意这里要占用两个 Type-C/Micro-USB 口，加上电源——所以实际需要两个 USB 口 + 一个电源。官方再次警告：「开发板通过 USB Type-C 供电，须用 5V/5A 电源适配器，勿用电脑 USB 口」。

**第四步：烧录参数。**

| 参数 | 取值 |
| --- | --- |
| 产品类型 | RDK X5 |
| 存储介质 | 固定 NAND |
| 固件类型 | 固定 secure |
| 连接类型 | Serial+USB 或 USB（见下表） |

连接类型决定可用下载模式与串口填写位置：

| 连接类型 | 可用下载模式 | 串口/波特率 | 适用场景 |
| --- | --- | --- | --- |
| Serial+USB | xmodem_fastboot / fastboot | 在 XBurn 界面「板卡」处填写串口和波特率（RDK X5: 115200，RDK X5 Module: 921600） | 串口经 Xmodem 引导、USB 经 Fastboot 下发。空板或非空板均可，**设备无法正常启动时使用** |
| USB | fastboot | 选项不出现，需在 MobaXterm/minicom 看日志 | 要求设备 U-Boot 正常，手动进入 Fastboot（上电后长按空格进 U-Boot，输入 `fastboot 0`） |

选型的判据很清晰：**板子起不来就选 Serial+USB**，因为 Xmodem 走串口不依赖 U-Boot；板子还能进 U-Boot 才选纯 USB。

**第五步：开始升级。** 点「开始升级」，看到提示后插拔电源；若插拔电源后串口丢失，先不上电，看到提示后再给设备上电。上电后开始升级，等待完成。

可选配置两条：批量烧录时软件上限 8 台、推荐 ≤4 台，官方明确「设备越多失败概率越高，稳定性取决于线材、hub、供电等硬件环境，软件不保证」，并建议批量时关闭「烧录完成自动重启」；单台烧录可勾选「烧录完成自动重启」，省去手动断电再上电。

> 来源：官方文档 Quick_start/system-burn/upgrade-miniboot（https://developer.d-robotics.cc/rdk_x_doc/Quick_start/system-burn/upgrade-miniboot）

### 1.2.6.4 方式三：srpi-config（图形菜单）

FAQ 还给了第三条路径，适合已经在系统里、想用菜单操作的用户：

```bash
# 进入配置菜单（需要 sudo）
sudo srpi-config
```

路径是 `1 System Options` → `S7 Update MiniBoot`，按提示操作。该方式「通常需要 RDK X5 能够连接到互联网，以便下载最新的 MiniBoot 固件包」。升级完成后退出并重启，可在串口启动日志里看到新的 U-Boot 版本信息，形如 `U-Boot 2022.10+ (Dec 26 2024 - 16:58:41 +0800)`。

三条路径的关系：srpi-config 的 S7 本质上就是调用 `rdk-miniboot-update`，所以它同样要求系统能启动且联网；系统起不来时只有 XBurn 一条路。

> 来源：官方文档 FAQ/hardware_and_system（https://developer.d-robotics.cc/rdk_x_doc/FAQ/hardware_and_system）、社区帖 31315（https://forum.d-robotics.cc/t/topic/31315）

## 1.2.7 eMMC 与 NAND 启动选择

这三个名词经常被混用，先分清：

| 名称 | 是什么 | 存什么 | 谁可以改 |
| --- | --- | --- | --- |
| Micro SD 卡 | 可插拔存储卡 | Ubuntu 系统（X5 唯一启动介质） | 用户烧录 |
| eMMC | 板载存储芯片，**仅 X5 Module 有** | Ubuntu 系统（与 SD 卡二选一启动） | 用户烧录 |
| QSPI NAND | 板载小容量 flash（128 MiB） | miniboot、U-Boot、ubootenv | 只能由 miniboot 升级流程写 |

启动介质的选择规则：

- **全板载 RDK X5**：只有 Micro SD 卡一条路，没有 eMMC，也没有启动顺序可选。
- **RDK X5 Module**：板载 eMMC，支持 Micro SD 卡和 eMMC 两种启动介质。

Module 切换启动介质的入口在 `srpi-config` 的 `Advanced Options -> Boot Order`。官方原文：「RDK X3 Module 和 RDK X5 Module 支持从 eMMC 和 SD 卡两种模式启动系统，本选项用于切换启动模式。」

判断当前是从哪个介质启动的，看串口日志最直接。帖 31743 的日志里能看到 `Scanning mmc 1:2…`、`Found U-Boot script /boot/boot.scr`、`root=/dev/mmcblk1p2`——说明从 mmc1（SD 卡）的第二分区启动。如果换成 eMMC 启动，设备节点会不同。

还有一个「SD 卡拔了为什么起不来」的问题，FAQ 的解释是：「对于 RDK X3（标准版，通常从 SD 卡启动）……Micro SD 卡是作为操作系统和用户数据的唯一存储介质……如果拔下 SD 卡，系统自然无法找到引导文件和操作系统」。X5 全板载同理。只有配置为从 eMMC 启动的 Module，拔掉 SD 卡才不影响启动。

> 来源：官方文档 System_configuration/srpi-config（https://developer.d-robotics.cc/rdk_x_doc/System_configuration/srpi-config）、官方文档 FAQ/hardware_and_system（https://developer.d-robotics.cc/rdk_x_doc/FAQ/hardware_and_system）、社区帖 31743（https://forum.d-robotics.cc/t/topic/31743）

## 1.2.8 启动验证

官方给的验证标准是分形态的：

- Desktop 版本：通过 HDMI 连接显示器，出现 Ubuntu 系统桌面即启动成功。
- Server 版本：通过调试串口连接开发板，打开 MobaXterm，`Session > Serial`，选 PC 识别到的串口号，Speed 选 **115200（RDK X5）** 或 **921600（RDK X5 Module）**，点 OK，出现用户名登录界面即启动成功。

时间预期：官方明确「系统首次启动时会进行默认环境配置，整个过程持续 45 秒左右」。超过 2 分钟无输出，官方判据是「如果开发板上电后长时间没有显示输出（2 分钟以上），说明开发板启动异常，需要通过串口线进行调试」。

默认账号：

| 账户类型 | 用户名 | 密码 |
| --- | --- | --- |
| 普通用户 | `sunrise` | `sunrise` |
| 超级用户 | `root` | `root` |

FAQ 同时提示「具体默认账户和密码可能因您烧录的系统镜像版本和来源略有不同」。社区帖 34973 的自动回复里出现的「用户名：rdk 或 ubuntu，密码：rdk 或 ubuntu」是错误信息，**不要照抄**——那是把别的板卡的默认账号混进来了。以官方 FAQ 的 `sunrise` / `root` 为准。

> 来源：官方文档 Quick_start/system-burn/burn-sd-card（https://developer.d-robotics.cc/rdk_x_doc/Quick_start/system-burn/burn-sd-card）、官方文档 FAQ/hardware_and_system（https://developer.d-robotics.cc/rdk_x_doc/FAQ/hardware_and_system）、社区帖 34973（https://forum.d-robotics.cc/t/topic/34973）

## 1.2.9 烧录失败排查

### 1.2.9.1 案例 A：工具提示「烧录成功」，上电不启动，绿灯常亮

**现象**（帖 32282 原文）：「我在RDK studio中使用了闪连，TF卡烧录，在Balenatcher试了烧录镜像，每次RDK Studio都提示系统烧录成功，但是我上电接HDMI口系统就是不启动！灯一直亮绿色!」

**根因**：多因并存。该帖最终被归因为 SD 卡本身（第 11 楼：「我之前也有这样的问题，你可以打印下日志看看。不过最后解决方法就是我换了SD卡就没有失败过了。可能是SD卡的问题。」），第 12 楼补充「可能是minibot要更新一下」，第 9 楼官方人员提到「xz 后缀镜像需要解压后烧录」。也就是说，「提示成功」只代表写入动作没报错，不代表写进去的内容能被 U-Boot 正确读取。

**处置**（按顺序，需要 sudo 的在板端执行）：

```bash
# 1. 在 PC 端确认镜像已解压为 .img（.xz / .gz 不能直接喂给 XBurn）
# 2. 换 Rufus，重新烧录同一张卡，参数保持默认
# 3. 若仍不启动，换一张品牌高速卡（U3/A2）重烧
# 4. 用串口抓完整启动日志，判断卡在哪一步
```

```bash
# 5. 若串口显示 U-Boot 正常但内核不动，升级 miniboot 后重试（需要 sudo，需联网）
sudo rdk-miniboot-update
```

**预防**：烧完立刻在 PC 上看卡的分区结构。正常应有约 100–500MB 的 FAT32 启动分区（帖 34478 里给的判据是「CONFIG (~500MB, FAT32)」），里面能看到 `Image`、`extlinux`、`hobot` 等文件；「如果只有 hobot_config.sh 一个文件，说明烧录失败」。这一步能在插板子之前就拦住一半问题。

> 来源：社区帖 32282（https://forum.d-robotics.cc/t/topic/32282）、社区帖 34478（https://forum.d-robotics.cc/t/topic/34478）

### 1.2.9.2 案例 B：卡在 `Starting kernel …` 之后无输出

**现象**（帖 34478 原文）：串口日志里 BootROM → BL1/BL2 → DDR → BL31 → OP-TEE → U-Boot 全部正常，`Loading kernel: /boot/Image` 读取 23218184 字节成功，然后 `Starting kernel …` 之后一条输出都没有，反复重启。

**根因**：官方人员的结论是「miniboot没看到有问题，还是SD卡的问题」「板子出现问题概率比较低，不过也不是没有可能，建议先从SD卡排查一下」。机理是：内核镜像被 U-Boot 读进内存并跳转执行，但内核在初始化阶段从 SD 卡加载驱动/根文件系统时遇到读错误，直接 panic 且未能输出——所以「看到 Starting kernel 但后面空白」不等于内核没跑，而是内核跑起来后挂了。

**处置**：

```bash
# 方法一：换卡重烧（最有效）
# 方法二：换 Rufus 并按社区建议设置：GPT 分区表 / UEFI（非 CSM）/ DD 镜像模式
# 方法三：在 U-Boot 里确认卡上的文件确实可读
```

进入 U-Boot 后（上电时长按空格）验证文件系统：

```
fatls mmc 1:1
```

如果这里列不出完整文件列表，说明卡上的 FAT 分区本身有问题，问题在烧录环节而不在内核。

**预防**：优先用品牌高速卡；烧录后用 `fatls` 或 PC 端浏览确认文件齐全；不要在烧录完成后对卡做任何「格式化修复」操作。

> 来源：社区帖 34478（https://forum.d-robotics.cc/t/topic/34478）

### 1.2.9.3 案例 C：验证了所有镜像仍卡在内核

**现象**（帖 31743 原文）：串口日志在 `Kernel panic - not syncing: VFS: Unable to mount root fs on unknown-block(179,2)` 后 `Rebooting in 5 seconds..`，如此循环。

日志中前置的关键错误序列是：

```
[ 12.864561] mmc1: Card stuck being busy! __mmc_poll_for_busy
[ 14.229615] mmc1: card never left busy state
[ 14.233973] mmc1: tried to HW reset card, got error -110
[ 14.239357] mmcblk1: recovery failed!
[ 14.243171] I/O error, dev mmcblk1, sector 9183232 op 0x1:(WRITE) flags 0x9800
```

**根因**：官方回复「系统尝试从设备 mmcblk1p2 （即 SD 卡的第二个分区）加载根文件系统失败」「文件系统损坏或存储介质 I/O 异常（如卡死、写保护、硬件故障等）」。`error -110` 是 ETIMEDOUT，`card never left busy state` 说明卡在命令响应阶段就超时了——这不是文件系统层面的损坏，而是卡本身不响应或接触不良。

**处置**：

```bash
# 1. 断电，取出 SD 卡，用橡皮擦清洁金手指，重插并确认卡扣到位
# 2. 换卡重烧
# 3. 在 PC 端对卡做只读检测：读全卡看是否有坏块（Linux 下）
```

```bash
# Linux PC 端：确认设备名后做只读全盘读取，报错即说明卡有坏块
lsblk
sudo dd if=/dev/sdX of=/dev/null bs=4M status=progress
```

**预防**：官方 FAQ 给了这类问题的完整特征串，可以直接拿去搜日志：「`mmc0: card never left busy state`」「`mmc0: error -110 whilst initialising SD card`」「`mmc_rescan_try_freq: send_status error -110`」「`Card did not respond to voltage select! : -110`」「`eMMC or SD Card not detected on mmchost 0`」。看到其中任意一条，直接跳到换卡，不要在软件层浪费时间。

> 来源：社区帖 31743（https://forum.d-robotics.cc/t/topic/31743）、官方文档 FAQ/hardware_and_system（https://developer.d-robotics.cc/rdk_x_doc/FAQ/hardware_and_system）

### 1.2.9.4 案例 D：miniboot 烧录报 `Firmware training failed`

**现象**（帖 33685 原文）：「两块RDK X5 板子现象一样。烧录miniboot失败，报错 `Error: Firmware training failed.`」

**根因**：该帖提问者自述的背景是关键——「RDK X5搭载8GB ddr颗粒，在uboot下改了一次ddrsize后烧录不成功；再还原到官方miniboot版本后，系统就进不去了，ddr 识别异常（有时显示8GB，有时6GB/1GB/0GB）」。官方回复「有尝试过重新烧录镜像吗，我们不建议自行修改ddr的size」。也就是说，**DDR size 被手工改过之后，固件训练（training）阶段的时序参数与实际颗粒不匹配，训练无法收敛**。这不是烧录工具的问题。

**处置**：

```bash
# 1. 确认 boardid 是否正确（不要随意改，仅作核对）
sudo hrut_boardid g
```

官方对 `hrut_boardid` 的警告是「boardid 会影响到启动时硬件的初始化，请谨慎设置」。boardid 的字段里 bit[19:16] 是 DDR 容量、bit[27:24] 是 DDR 类型、bit[23:20] 是频率，手工写错任何一位都会导致初始化参数错误。

```bash
# 2. 用 XBurn 重新烧官方 miniboot（连接类型选 Serial+USB）
# 3. 换一条质量可靠的 Micro-USB 串口线重试
```

**预防**：不要改 DDR size。boardid 的 `auto detect` 位（bit[31]）设计意图就是让固件自己探测，把它关掉去硬写参数，等于放弃了官方的兼容性保证。

> 来源：社区帖 33685（https://forum.d-robotics.cc/t/topic/33685）、官方文档 Appendix/rdk-command-manual/cmd_hrut_boardid（https://developer.d-robotics.cc/rdk_x_doc/Appendix/rdk-command-manual/cmd_hrut_boardid）

### 1.2.9.5 案例 E：XBurn 报串口 Xmodem 下载失败

**现象**（帖 34988 原文）：

```
E[Burn thread-1][20:47:47] [ERROR] Uart xmodem download uart_usb/bl3x_all.bin failed
[Burn thread-1][20:47:47] [ERROR] Step 'xmodem_boot' failed
[Burn thread-1][20:47:47] [ERROR] Board-1, burn failed
[Burn thread-1][20:47:47] [ERROR] Board-1 [Storage: nand] Status: FAILED
```

**根因**：`xmodem_boot` 这一步是通过串口把 `bl3x_all.bin` 传给板端的 BL2。失败意味着串口链路在传输过程中丢字节或超时。常见原因有三类：串口线质量差/过长、波特率与板卡不匹配（X5 是 115200，X5 Module 是 921600，填错必然失败）、USB 口供电不稳导致板端复位。

**处置**：

```bash
# 1. 换一条短一点的优质 Micro-USB 数据线（注意必须是数据线，不是纯充电线）
# 2. 核对 XBurn 里填的波特率：RDK X5 = 115200，RDK X5 Module = 921600
# 3. 换 PC 的 USB 2.0 口（不要用前置面板口或 HUB）
# 4. 确认电源是 5V/5A 适配器，不是 PC USB 口
```

**预防**：XBurn 的批量烧录上限虽然是 8 台，官方也提示「设备越多失败概率越高，稳定性取决于线材、hub、供电等硬件环境，软件不保证」。单台调试阶段不要上批量。

> 来源：社区帖 34988（https://forum.d-robotics.cc/t/topic/34988）、官方文档 Quick_start/system-burn/upgrade-miniboot（https://developer.d-robotics.cc/rdk_x_doc/Quick_start/system-burn/upgrade-miniboot）

### 1.2.9.6 案例 F：烧录卡在固定百分比后失败

**现象**（帖 34762 原文）：「RDK X5系统烧录不成功怎么回事，卡在26%，显示失败」。帖内引用的报错片段是：

```
ERROR: Executing 'hobot_firmware_flash.exe' exited with code 0x2
```

**根因**：该帖的诊断是「典型的 Miniboot 版本过旧 导致的烧录失败。系统尝试执行固件烧录命令时失败，通常是因为板载的 Miniboot 引导程序版本太老，不支持当前镜像的烧录流程」。需要说明：这是社区诊断，不是官方结论；但机制上讲得通——烧录流程里有一段需要板端 BL2/U-Boot 配合执行固件写入，miniboot 太旧就没有这条通路。

帖 34558 提供了同一机理的另一种表现：XBurn 烧到 85% 时执行 MD5 校验失败。

```
Hobot>md5sum
Unknown command 'md5sum' - try 'help'
Unknown command 'md5sum' - try 'help'
[Burn thread-1][07:40:57] [ERROR] MD5 verification failed on device.
[Burn thread-1][07:40:57] [ERROR] Step 'xmodem_burn' failed
```

板端 bootloader 里根本没有 `md5sum` 这条命令——说明该板的 miniboot 版本与 XBurn 期望的校验接口不匹配。

**处置**：

```bash
# 先用 XBurn 单独把 miniboot 烧到最新，再回头烧系统镜像
# 顺序不能反：miniboot 是"烧录能力"的前提
```

**预防**：官方在 Release Note 里反复强调「更新系统后，请使用 rdk-miniboot-update 命令更新 NAND 固件至最新版本」。把 miniboot 更新当成系统更新的固定收尾动作，这类问题不会出现。

> 来源：社区帖 34762（https://forum.d-robotics.cc/t/topic/34762）、社区帖 34558（https://forum.d-robotics.cc/t/topic/34558）、官方文档 Release_Note/release_note（https://developer.d-robotics.cc/rdk_x_doc/Release_Note/release_note）

## 常见误区

**误区一：把「镜像烧录」和「miniboot 升级」当成同一件事。**
两者写的是不同介质、走的是不同工具链。镜像进 SD 卡/eMMC，miniboot 进板载 NAND。官方工具表明确标注 Rufus 和 RDK Studio **只能烧镜像、不能升 miniboot**，只有 XBurn 和 `rdk-miniboot-update` 能升 miniboot。反复重烧镜像解决不了 miniboot 过旧的问题。

**误区二：升级 miniboot 时「回退到上一个稳定版本更保险」。**
方向反了。官方原话是「设备出厂已预装与硬件匹配的最新固件，严禁降级刷入旧版本，否则可能无法启动」，并且从 3.3.1 起工具层面直接限制烧录旧版 miniboot。唯一的例外场景是硬件被改过（如换了 NAND 颗粒），那属于定制开发，不在官方支持范围内。

**误区三：认为 server 版可以 `apt install` 成 desktop 版。**
FAQ 说得很直白：「官方通常不提供或不推荐这种手动升级路径，并且不对通过此方式构建的 Desktop 系统的稳定性和功能完整性进行保证或测试」。要桌面就重烧 desktop 镜像。

**误区四：看到「绿灯常亮 + 橙灯闪烁」就认定系统起来了。**
社区帖 34973 的标题就是反例——灯的状态正常，但 HDMI、SSH、串口全无反应，根因是 SD 卡未被识别。判断启动成功只认两件事：HDMI 出现桌面（desktop）或串口出现登录提示符（server）。

**误区五：烧完卡顺手在 Windows 里点「格式化」消掉那个「无法识别」的弹窗。**
FAQ 专门警告过这一点：「在烧录过程中，Windows 系统可能会因为无法识别 SD 卡上的 Linux 分区而弹出『是否需要格式化』的对话框。请务必选择『否』或直接关闭该对话框，不要进行格式化操作，否则会中断烧录。」同理，烧完之后也不要「修复」那个分区。
