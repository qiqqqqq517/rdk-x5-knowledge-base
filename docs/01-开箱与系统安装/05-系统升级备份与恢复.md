# 1.5 系统升级、备份与恢复

## 本章解决什么

系统装好只是起点。后面会反复发生三类事：一是通过 `apt` 增量升级（装驱动、装 TROS、修 bug），二是把调好的整机状态备份成一个可烧录镜像以便批量部署或换卡，三是出问题后回退或救砖。这三件事的技术栈完全不同——`apt` 动的是 SD 卡上的根文件系统，`rdk-miniboot-update` 动的是板载 NAND，`rdk-backup` 是把整张卡打成镜像，而救砖往往只有 XBurn 一条路。本章按「升级 → 备份 → 还原 → 回退 → 救砖」的顺序讲，重点标出两处最容易失败的地方：`rdk-backup` 对目标文件系统的要求（社区大量「第二阶段报错」案例的根因都在这），以及升级后必须补做 miniboot 更新这条官方硬性要求。

> 来源：官方文档 System_configuration/network_bluetooth（https://developer.d-robotics.cc/rdk_x_doc/System_configuration/network_bluetooth）

## 1.5.1 apt 升级

### 1.5.1.1 标准流程

官方给的命令只有三条：

```bash
# 1. 更新软件包列表（需要 sudo）
sudo apt update

# 2. 升级所有已安装的软件包（需要 sudo）
sudo apt full-upgrade

# 3. 重启使更新生效（需要 sudo）
sudo reboot
```

官方特意强调了为什么用 `full-upgrade` 而不是 `upgrade`：「推荐使用 full-upgrade 而不是 upgrade 选项，这样当相关依赖发生变动时，也会同步更新依赖包。」这两个选项的差别在于，`upgrade` 遇到需要删除现有包才能解决的依赖冲突时会跳过该包，`full-upgrade` 则会真的删包以完成升级。对 RDK 这种包依赖链较深的系统，后者才能保证一致性。

### 1.5.1.2 磁盘空间

官方提醒：「当运行 `sudo apt full-upgrade` 命令时，系统会提示数据下载和磁盘占用大小，但是 apt 不会检查磁盘空间是否充足，建议用户通过 `df -h` 命令手动检查。」

```bash
# 检查根分区剩余空间（不需要 sudo）
df -h /

# 查看 apt 缓存占用（不需要 sudo）
du -sh /var/cache/apt/archives

# 清理缓存释放空间（需要 sudo）
sudo apt clean
```

这条提醒不是客套。官方同时指出「升级过程中下载的 deb 文件会保存在 `/var/cache/apt/archives` 目录中」——一次大规模 `full-upgrade` 可能占用几个 GB。16GB 卡装完系统后剩余空间本就不多，装完 TROS 全套之后更容易卡住。实践中的判断：升级前保证根分区至少 3GB 可用。

### 1.5.1.3 升级后必须做的事

这是本章最重要的一条，官方在两个地方重复强调：

**Release Note 开篇**：「更新系统后，请使用 `rdk-miniboot-update` 命令更新 NAND 固件至最新版本。」

**RDK 总览页的版本发布记录**：「固件升级指南：系统更新后，执行 `rdk-miniboot-update` 命令将系统镜像中的最新 miniboot 固件烧录至 NAND。」

原因在具体版本说明里能看得很清楚：

- 3.2.3：「集成最新版 miniboot 固件，使用 rdk-miniboot-update 命令烧录 NAND 后，会释放更多内存给系统。」
- 3.3.1：「修复 8G 板卡，内存减少 2G 的问题，需要更新 miniboot。」

也就是说，**只 `apt upgrade` 不 `rdk-miniboot-update`，某些修复不会生效**。8GB 板卡用户如果升完级发现可用内存只有 6GB 左右，八成就是漏了这步。

```bash
# 升级完系统后补做 miniboot 更新（需要 sudo，需要联网）
sudo rdk-miniboot-update
```

### 1.5.1.4 升级过程中的黑屏

这是 `apt full-upgrade` 最典型的翻车现场，官方 FAQ 与社区都有明确记录。按四段式展开。

#### 现象

官方 FAQ Q20 描述的是轻度形态：在图形桌面的终端里执行升级时，显示中断或 X Server 重启，屏幕黑一下再回来。

社区帖 28831 记录的是重度形态：「首先是upgrade之后就黑屏再亮屏，接着再upgrade之后，终端让我使用 `sudo dpkg configure -a`，然后就出现附件视频中的情况。于是我重新给X5上电，系统就打不开了，用串口查看数据发现系统启动的时候卡在下图位置。」

完整链条是：第一次 upgrade 黑屏再亮屏（X 重启，属正常）→ 第二次 upgrade → 系统提示 `sudo dpkg --configure -a` → 处理后重启 → 系统起不来。关键信号是那句 `sudo dpkg --configure -a` 提示，它意味着包管理器处于「配置未完成」状态。

#### 根因

`full-upgrade` 会替换 `xserver-xorg`、`lightdm`、显卡驱动这些**正在被桌面会话使用**的组件。在桌面里的终端执行时，这些包被替换的瞬间桌面进程就挂了，导致后续包配置步骤缺少运行环境而中断，`dpkg` 数据库停在半装状态。

官方 FAQ 的表述是「有时在升级桌面自身相关的包时可能会导致显示中断或 X Server 重启，从而造成黑屏现象」。而半装状态一旦被断电打断，下次启动时根文件系统上的关键包（包括显示管理器、initramfs 相关组件）就处于不一致状态，表现为起不来。

#### 处置

已经在半装状态、系统还能用串口进去时：

```bash
# 1. 用串口登录（此时 SSH 可能也不可用，见第 4 章）
# 2. 完成未完成的包配置（需要 sudo）
sudo dpkg --configure -a

# 3. 修复损坏的依赖（需要 sudo）
sudo apt --fix-broken install

# 4. 检查磁盘是否满了（不需要 sudo）
df -h /

# 5. 清理后重试（需要 sudo）
sudo apt clean
sudo apt update
```

若第 2 步报错说某个包缺依赖，按报错里的包名单独装：

```bash
# 装回报错提示的包（需要 sudo）
sudo apt install -y <包名>
```

如果串口也进不去、启动卡在 U-Boot 之后，说明根文件系统已经不可用，走 5.6 节的变砖恢复流程。

#### 预防

- **从 SSH 或串口里跑升级，不要在桌面的终端里跑**。官方原话就是「建议通过串口终端或 SSH 远程登录后，在纯字符界面的终端中执行系统更新命令」。
- **升级前单独跑一次 `sudo apt update`**，确认没有 GPG 密钥报错（见下节），避免升级中途因源不可用而中断。
- **升级后先别急着重启**，用下面这条确认没有半装状态的包：

```bash
# 列出所有非 ii（已正确安装）状态的包（不需要 sudo）
dpkg -l | grep -v '^ii' | head -20
```

- **看到 `dpkg --configure -a` 提示时立刻处理，不要断电**。这条提示本身就是中断信号，此时断电等于把半装状态固化下来。
- **大版本升级前先 `rdk-backup`**（见 5.3 节），这是唯一能在起不来时保住原有环境的办法。

> 来源：官方文档 System_configuration/network_bluetooth（https://developer.d-robotics.cc/rdk_x_doc/System_configuration/network_bluetooth）、官方文档 FAQ/hardware_and_system（https://developer.d-robotics.cc/rdk_x_doc/FAQ/hardware_and_system）、官方文档 Release_Note/release_note（https://developer.d-robotics.cc/rdk_x_doc/Release_Note/release_note）、社区帖 28831（https://forum.d-robotics.cc/t/topic/28831）

### 1.5.1.5 源与 GPG 密钥失效

FAQ Q10 把这类问题列得很全，是本章必须收录的内容。典型报错：

```
Clearsigned file isn't valid, got 'NOSPLIT'
The repository '...' is no longer signed.
Could not resolve 'archive.sunrisepi.tech' (或其他旧域名)
The following signatures couldn't be verified because the public key is not available: NO_PUBKEY ...
```

原因是「地瓜机器人官方软件源域名或 GPG 签名密钥发生变更，导致本地配置过期」。

先看当前源配置：

```bash
# 查看源配置（不需要 sudo）
cat /etc/apt/sources.list.d/sunrise.list
```

正确的配置形如：

```
deb [signed-by=/usr/share/keyrings/sunrise.gpg] http://archive.d-robotics.cc/ubuntu-rdk-s100 jammy main #RDK S100
# deb [signed-by=/usr/share/keyrings/sunrise.gpg] http://archive.d-robotics.cc/ubuntu-rdk-x5 jammy universe #RDK X5
# deb [signed-by=/usr/share/keyrings/sunrise.gpg] http://archive.d-robotics.cc/ubuntu-rdk jammy universe #RDK X3
```

注意这里 X5 对应的行是 `ubuntu-rdk-x5 jammy universe`。如果这一行被注释掉、或者指向了 `ubuntu-rdk`（X3 的源），装包时会找不到包或者装到错误的包。

修复旧域名：

```bash
# 替换旧域名（需要 sudo）
sudo sed -i 's/archive.sunrisepi.tech/archive.d-robotics.cc/g' /etc/apt/sources.list.d/sunrise.list

# 更新 GPG 密钥（需要 sudo）
sudo wget -O /usr/share/keyrings/sunrise.gpg http://archive.d-robotics.cc/keys/sunrise.gpg

# 重新更新（需要 sudo）
sudo apt update
```

ROS2 源的密钥是另一套，报错特征不同——`NO_PUBKEY F42ED6FBAB17C654`，来自 `http://packages.ros.org/ros2/ubuntu jammy`：

```bash
# 更新 ROS2 GPG 密钥（需要 sudo）
curl -sSL https://raw.githubusercontent.com/ros/rosdistro/master/ros.key | sudo tee /usr/share/keyrings/ros-archive-keyring.gpg > /dev/null

sudo apt update
```

3.2.3 版本说明里也有一条对应记录：「20250610 更新 ROS 仓库 GPG 签名密钥」。也就是说跑 3.2.3 之前的系统时，ROS 源密钥过期是预期内的，升级系统本身就能解决。

### 1.5.1.6 锁文件被占用

报错形态：

```
E: Could not get lock /var/lib/apt/lists/lock. It is held by process XXXX (apt-get)
N: Be aware that removing the lock file is not a solution and may break your system.
E: Unable to lock directory /var/lib/apt/lists/
```

官方的诊断是「系统可能正在后台自动运行更新检查或安装任务，或者上一次 apt 操作未正常结束导致锁文件未被释放」。

处置按风险从低到高：

```bash
# 1. 先确认到底有没有 apt/dpkg 在跑（不需要 sudo）
ps aux | grep -E "apt|dpkg" | grep -v grep

# 2. 如果确实有进程占着，杀掉它（需要 sudo，XXXX 换成实际 PID）
sudo kill XXXX

# 3. 等待一段时间再试（后台自动更新有时会自己结束）
```

官方对第 4 步给了明确的风险警告：「⚠️ 谨慎操作」「此操作有一定风险，可能破坏您的包管理系统，请务必谨慎」：

```bash
# 4. 确认没有任何 apt/dpkg 进程后再清理锁文件（需要 sudo）
sudo rm /var/lib/apt/lists/lock
sudo rm /var/cache/apt/archives/lock
sudo rm /var/lib/dpkg/lock
sudo rm /var/lib/dpkg/lock-frontend
sudo dpkg --configure -a
```

这四行必须按顺序执行，且必须在第 1 步确认无进程之后。跳过确认直接删锁，如果此时真有 `dpkg` 在写数据库，后果是包数据库损坏——那就要走救砖流程了。

> 来源：官方文档 FAQ/hardware_and_system（https://developer.d-robotics.cc/rdk_x_doc/FAQ/hardware_and_system）、官方文档 Release_Note/release_note（https://developer.d-robotics.cc/rdk_x_doc/Release_Note/release_note）

### 1.5.1.7 大项目编译内存不足

`apt` 本身不占多少内存，但装完 TROS 之后跑 `colcon build` 很容易 OOM。FAQ Q40 给的方案是加 Swap，这是 RDK 上最实用的一招：

```bash
# 1. 创建一个 4GB 的空文件（需要 sudo）
sudo fallocate -l 4G /swapfile

# 2. 设置权限（需要 sudo）
sudo chmod 600 /swapfile

# 3. 格式化为 swap（需要 sudo）
sudo mkswap /swapfile

# 4. 启用（需要 sudo）
sudo swapon /swapfile

# 5. 验证（不需要 sudo）
swapon --show
free -h
```

开机自动挂载，在 `/etc/fstab` 末尾加一行：

```
/swapfile none swap sw 0 0
```

不需要时关掉：

```bash
# 关闭并删除（需要 sudo）
sudo swapoff /swapfile
sudo rm /swapfile
# 同时从 /etc/fstab 中移除对应行
```

官方同时给了降低并行度的方案，两者可以叠加：

```bash
# 限制 colcon 并行包编译数量（不需要 sudo）
colcon build --parallel-workers 1

# 更保守：串行执行（不需要 sudo）
colcon build --executor sequential

# 两者结合
colcon build --executor sequential --parallel-workers 1

# 或用环境变量限制 make 并行度
export MAKEFLAGS="-j1"
```

需要说明 Swap 的代价：官方原文是「这可以缓解 OOM 问题，但性能会比物理内存慢很多」。SD 卡上的 swap 尤其慢。所以 Swap 是应急手段，长跑编译还是应该交叉编译（在 x86 上编译好再拷到板子）。

> 来源：官方文档 FAQ/hardware_and_system（https://developer.d-robotics.cc/rdk_x_doc/FAQ/hardware_and_system）

## 1.5.2 rdk-miniboot-update 再述

第 2 章已讲过 miniboot 的烧录流程，这一节从「版本管理」角度补充。

### 1.5.2.1 版本可见性

从 `hobot-miniboot_3.0.3` 起，`rdk-miniboot-update` 会自动显示「当前 NAND 固件版本与目标升级版本」。这个改动是 3.3.1「限制烧录旧版本 miniboot」的配套——先让你看见版本，再拦截降级。

查看当前会使用哪个镜像：

```bash
# 不需要 sudo
rdk-miniboot-update -l
```

输出形如 `/lib/firmware/rdk/miniboot/default/disk_nand_minimum_boot_2GB_3V3_20230413.img`。文件名里的日期就是固件版本，可以直接和官方下载页的最新包对比。

想确认板子上实际运行的 U-Boot 版本，看启动日志最准：

```bash
# 从内核日志里找 U-Boot 版本行（不需要 sudo，可能需要 dmesg 权限）
dmesg | grep -i "u-boot"
```

或者用 `rdkos_info` 一次性收集：

```bash
# 需要 sudo
sudo rdkos_info
```

它的输出里有专门的段：

```
[RDK Miniboot Version]:
U-Boot 2018.09-00012-g5e7d58f7-dirty (Nov 26 2023 - 18:47:14 +0800)
```

（上面这段是官方示例，来自 X3 平台，X5 的 U-Boot 版本号形如 `U-Boot 2022.10+ (Nov 22 2024 - 14:00:59 +0800)`，见社区帖 31743 的日志。）

### 1.5.2.2 升级失败的判断

`rdk-miniboot-update` 成功后不会自动重启。判据是：命令正常退出、无报错，然后重启看串口日志里 U-Boot 的编译日期是否变化。

如果升级后板子起不来，说明固件写入不完整，只能用 XBurn 重刷（详见 5.5 节）。

> 来源：官方文档 Appendix/rdk-command-manual/cmd_rdk-miniboot-update（https://developer.d-robotics.cc/rdk_x_doc/Appendix/rdk-command-manual/cmd_rdk-miniboot-update）、官方文档 Appendix/rdk-command-manual/cmd_rdkos_info（https://developer.d-robotics.cc/rdk_x_doc/Appendix/rdk-command-manual/cmd_rdkos_info）、官方文档 RDK（https://developer.d-robotics.cc/rdk_x_doc/RDK）

## 1.5.3 rdk-backup 备份

### 1.5.3.1 工具能力

`rdk-backup` 是 3.1.1 版本引入的，「全新 rdk-backup 工具，一键备份当前系统，轻松生成可烧录镜像」。官方命令手册的定位是「用于将当前系统备份成镜像」。

语法：

```
sudo rdk-backup [dir]
```

参数说明有两条关键信息：

- 参数为生成和挂载镜像的打包目录，**默认打包目录是 `/mnt`**。
- **打包目录在制作镜像时会被忽略**。

第二条的意思是：`rdk-backup /mnt` 时，`/mnt` 这个挂载点本身的内容不会被写进镜像——所以把一张额外的 SD 卡/U 盘挂在 `/mnt` 上作为输出目标是正确用法，不会造成递归。

### 1.5.3.2 两种用法

**用法一：输出到挂载的 U 盘/SD 卡**

适合系统盘快满了、需要外置介质承接的场景：

```bash
# 1. 插入 U 盘或读卡器，确认设备名（不需要 sudo）
lsblk

# 2. 挂载到 /mnt（需要 sudo，设备名以实际为准）
sudo mount /dev/sda1 /mnt

# 3. 执行备份（需要 sudo，需联网——工具会下载安装所需组件）
sudo rdk-backup /mnt

# 4. 完成后确认产物（不需要 sudo）
ls -lh /mnt/*.img

# 5. 卸载（需要 sudo）
sudo umount /mnt
```

执行完成后「在打包目录下得到备份的镜像文件 `rdk-时间和日期.img`」。

**用法二：输出到默认的 /mnt（本机空间充足时）**

```bash
# 需要 sudo，需联网
sudo rdk-backup
```

### 1.5.3.3 前提条件

官方明确写了一条：「使用前需要先联网，rdk-backup 执行过程中会下载安装所需的工具。」

这一条经常被忽略，结果是断网环境下执行到一半失败，报错看起来像权限问题或磁盘问题，实际是下载不到依赖。备份前先验证网络：

```bash
# 验证能解析并连通官方源（不需要 sudo）
curl -I http://archive.d-robotics.cc
```

### 1.5.3.4 输出介质的文件系统要求（关键）

这是 `rdk-backup` 失败率最高的一环，而官方命令手册完全没有提，证据全部来自社区。下面按四段式拆开。

#### 现象

帖 31315 的提问者描述：「我的SD卡是32G，已经用了29G，就不能再直接备份镜像了，所以我选择挂载了一张SD卡，命令如下：`sudo mount /dev/sdb1 /mnt`，然后我就开始在/mnt目录下进行备份了，但是到了第二阶段，它一直报错」。

帖 31345 里同一用户补充了完整过程与时间：

```
① 选一张128G的已格式化的SD卡，用读卡器把它插进RDKX5的USB口
   输入 sudo gparted，把SD卡的盘卸载，分卷为 /dev/sda1
② 改权限：su root，mount /dev/sda1 /mnt，sudo lsblk 确认挂载成功
③ sudo rdk-backup /mnt，命令运行成功，无报错，进入 part1，制作空镜像，制作时间长达 2 小时
④ 进入第二阶段，往镜像文件写入数据，等待一小时后，不停报错
```

三个可观察特征：命令本身不报错、第一阶段正常耗时、**只有第二阶段刷屏报错**。

#### 根因

官方人员的回复直接点出根因：

「您是如何格式化128G SD卡的？许多SD卡出厂时或在Windows/macOS上格式化时，默认的文件系统是 **exFAT 或 FAT32**。这些文件系统**不支持 Linux 的文件所有权（user/group）和精细的文件权限（rwx）**。当 `rdk-backup` 尝试将一个需要特定权限（例如 `-rwx--x--x`）或特定所有者（例如 `root:root`）的文件复制到挂载在 `/mnt` 的 exFAT 分区时，exFAT 文件系统无法保存这些元数据。`rdk_backup` 会因此报告大量 `Operation not supported` 或 `Permission denied` 类型的错误，导致备份进程中断或最终生成的镜像不完整、无法启动。」

这段解释同时说明了三个现象：

1. 为什么第一阶段（制作空镜像）能成功——那只是创建一个稀疏大文件，不涉及权限元数据。
2. 为什么只有第二阶段（写入数据）才报错——写文件时才需要复制权限与属主。
3. 为什么最终镜像「看起来生成了」但烧录后起不来——权限元数据丢失，系统文件的可执行位、属主全错。

#### 处置

输出介质必须格式化为 **ext4**（或其它支持 POSIX 元数据的 Linux 文件系统），不能用 exFAT / FAT32 / NTFS。

```bash
# 1. 先确认设备名，这一步不能省（不需要 sudo）
lsblk

# 2. 格式化为 ext4（需要 sudo，会清空该设备全部数据）
#    务必对照上一步的输出确认 /dev/sda1 确实是那张备份盘，写错设备名会毁掉系统盘
sudo mkfs.ext4 -L backup /dev/sda1

# 3. 重新挂载并备份（需要 sudo）
sudo mount /dev/sda1 /mnt
sudo rdk-backup /mnt
```

如果已经产生了不完整的镜像，不要尝试烧录验证——直接在 ext4 介质上重做一次。

#### 预防

- **备份前先验证输出介质的文件系统**：`lsblk -f` 或 `df -hT /mnt`，看到 `ext4` 才算合格。
- **格式化后不要用 Windows 去「检查并修复」那张盘**——Windows 无法识别 ext4，会提示格式化，点确认就前功尽弃。
- **估算时间与空间**：帖 31345 的记录是「part1，制作空镜像，制作时间长达 2 小时」「进入第二阶段……等待一小时」，合计约 3 小时。镜像大小约等于系统盘已用空间，输出介质要留出余量。
- **首次用新介质前先做小规模验证**：先备份到一个临时小目录，确认无 `Operation not supported` 报错，再正式跑完整备份。

> 来源：社区帖 31315（https://forum.d-robotics.cc/t/topic/31315）、社区帖 31345（https://forum.d-robotics.cc/t/topic/31345）、官方文档 Appendix/rdk-command-manual/cmd_rdk-backup（https://developer.d-robotics.cc/rdk_x_doc/Appendix/rdk-command-manual/cmd_rdk-backup）

### 1.5.3.5 空间估算

一次 32G 系统盘的备份，正常需要 3 小时左右（依据帖 31345 的实测时间记录）。规划和排期时按这个量级估算，不要指望十几分钟完事。

空间上，镜像大小约等于系统盘已用空间。32G 卡用 29G 的话，输出介质至少要 32G 以上可用空间，且留一些余量。

### 1.5.3.6 备份前该做的事

`rdk-backup` 是整盘镜像，会把所有垃圾一起打包。备份前清理能显著减小体积、缩短时间：

```bash
# 清理 apt 缓存（需要 sudo）
sudo apt clean

# 查看各目录占用，找出大户（不需要 sudo）
du -sh /var/* 2>/dev/null | sort -h | tail -10

# 清理日志（需要 sudo）
sudo journalctl --vacuum-size=50M
```

> 来源：官方文档 Appendix/rdk-command-manual/cmd_rdk-backup（https://developer.d-robotics.cc/rdk_x_doc/Appendix/rdk-command-manual/cmd_rdk-backup）、社区帖 31315（https://forum.d-robotics.cc/t/topic/31315）、社区帖 31345（https://forum.d-robotics.cc/t/topic/31345）、社区帖 31301（https://forum.d-robotics.cc/t/topic/31301）

## 1.5.4 镜像还原与容量扩展

### 1.5.4.1 还原

`rdk-backup` 生成的是标准 `.img`，还原方式与第 2 章烧录系统镜像完全一致——用 Rufus / RDK Studio / XBurn 写回 SD 卡即可。

### 1.5.4.2 容量扩展（还原到更大卡时必须做）

这是备份还原流程里最容易被忽略的一步。场景：从 32G 卡备份，还原到 128G 卡，系统只会用到前 32G，剩下 96G 空着。

官方在 `srpi-config` 的 `Expand Filesystem` 项里描述了这个场景：「如果系统是通过从另一张已经完成初始化配置的系统中复制而来的，那么系统的 TF 卡容量可能不会被自动调整为当前 TF 卡的容量。使用此功能可以方便地完成扩展。」

两种做法：

**方法一：srpi-config 菜单**

```bash
# 需要 sudo
sudo srpi-config
# Advanced Options -> Expand Filesystem -> Finish -> 重启
```

**方法二：命令行**

```bash
# 1. 看当前分区与文件系统（不需要 sudo）
lsblk
df -h /

# 2. 若分区本身没扩，先用 parted 扩分区（需要 sudo，以 mmcblk1p2 为例）
sudo parted /dev/mmcblk1 resizepart 2 100%

# 3. 扩文件系统（需要 sudo，ext4 支持在线扩容）
sudo resize2fs /dev/mmcblk1p2

# 4. 确认（不需要 sudo）
df -h /
```

第 2 步的 `resizepart` 在部分 `parted` 版本上需要交互确认，也可以改用 `growpart`：

```bash
# 更安全的写法：只扩分区不动数据（需要 sudo）
sudo growpart /dev/mmcblk1 2
sudo resize2fs /dev/mmcblk1p2
```

**风险提示**：`parted` 和 `growpart` 都是直接改分区表的操作，写错设备名会毁掉整盘数据。执行前一定用 `lsblk` 确认 `/dev/mmcblk1` 确实是 SD 卡而不是别的设备。

### 1.5.4.3 还原后的必查项

还原的镜像带着原机器的所有配置，包括主机名、IP、SSH 主机密钥、用户密码。部署多台设备时逐项处理：

```bash
# 1. 改主机名（需要 sudo）
sudo hostnamectl set-hostname rdkx5-002

# 2. 重新生成 SSH 主机密钥（需要 sudo，避免多台设备密钥相同）
sudo rm /etc/ssh/ssh_host_*
sudo dpkg-reconfigure openssh-server

# 3. 改 IP（见第 4 章 4.3 节，注意 3.3.0 前后的配置文件不同）
```

第 2 步在多机部署时是必须的——否则所有设备共用一份 SSH 主机密钥，你 PC 上的 `known_hosts` 会在切换设备时报警告，而且失去了主机身份校验的意义。

> 来源：官方文档 System_configuration/srpi-config（https://developer.d-robotics.cc/rdk_x_doc/System_configuration/srpi-config）、官方文档 Appendix/rdk-command-manual/cmd_rdk-backup（https://developer.d-robotics.cc/rdk_x_doc/Appendix/rdk-command-manual/cmd_rdk-backup）

## 1.5.5 版本回退

### 1.5.5.1 能回退什么、不能回退什么

先把边界划清：

| 对象 | 能否回退 | 方式 |
| --- | --- | --- |
| 系统镜像（RDKOS 版本） | 能 | 重烧旧版本镜像 |
| apt 包 | 部分能 | `apt install <pkg>=<version>` |
| miniboot | **不能** | 官方禁止降级，工具层面也拦截 |
| boardid / DDR 参数 | 不建议 | 会影响启动初始化 |

### 1.5.5.2 系统版本回退

RDKOS 没有内置的「回滚到上一个版本」机制。回退的唯一方式是把旧版本镜像重新烧到 SD 卡。

```bash
# 1. 在 PC 上下载目标版本镜像
#    https://archive.d-robotics.cc/downloads/os_images/rdk_x5/
# 2. 用 Rufus / RDK Studio 烧到 SD 卡（详见第 2 章）
# 3. 插卡上电
```

代价是用户数据全丢。如果不希望丢数据，正确做法是**升级前先 `rdk-backup`**，出问题时还原备份而不是重烧官方镜像。

这里有一条版本兼容性硬约束必须注意：**X5 Module 只能使用 3.2.0 及其后续版本的系统**。所以 Module 用户想回退到 3.0.x/3.1.x 是做不到的，最早只能到 3.2.0。

### 1.5.5.3 miniboot 不能回退

官方在硬件文档、miniboot 文档、RDK 总览页三处都写了同一条：

「设备出厂时已预装匹配的最新版 miniboot 固件，为保障硬件兼容性，**严禁降级刷入旧版本固件**；降级操作可能导致设备无法启动。」

工具层面从 3.3.1 起也落实了：「rdk-miniboot-update 限制烧录旧版本 miniboot」。

唯一的例外是定制硬件（如自行更换了 NAND 颗粒）。社区帖 35730 就是一个反面案例：用户把 NAND 从 1Gb 改成 2Gb（用支持列表里的 GD5F2GM7REYIG），结果「系统从 nand 无法启动」，串口日志显示：

```
NOTICE: Nand PAGE_SIZE_4K
NOTICE: Manufacturer ID 0xc8 Device ID 0x82c8
ERROR: boot mode 5 main bl2 fail and switch to bakeup1…
ERROR: boot mode 5 bakeup1 bl2 fail and switch to bakeup2…
```

注意 `PAGE_SIZE_4K` 与标准板的 `PAGE_SIZE_2K` 不同，`Device ID 0x82c8` 也与标准板的 `0x41c8` 不同——固件的 BL2 里没有这颗颗粒的参数，所以三条启动路径全 fail。这类改动属于定制开发，需要自行编译固件，不在官方支持范围内。

### 1.5.5.4 apt 包回退

单个包可以装回旧版本：

```bash
# 1. 查看可用版本（不需要 sudo）
apt policy <包名>

# 2. 安装指定版本（需要 sudo）
sudo apt install <包名>=<版本号>

# 3. 阻止后续自动升级（需要 sudo）
sudo apt-mark hold <包名>
```

`apt-mark hold` 这一条在「某个包升级后把功能搞坏了」的场景下很实用：钉住版本，后续 `full-upgrade` 不会再把它带上去。解除用 `sudo apt-mark unhold <包名>`。

注意 `apt policy` 只能看到当前配置的源里存在的版本。如果旧版本已经从源里撤掉，就装不回来了——这时只能靠提前备份的镜像。

### 1.5.5.5 一个具体的回退场景：3.1.0 的包冲突

Release Note 记录了一例必须手工处理的升级冲突：

「旧版本使用 `apt update && apt upgrade` 升级到该版本时，需要先卸载 `tros-humble-stereonet-model`，再安装 `tros-humble-hobot-stereonet` 包。」

```bash
# 按官方给出的顺序执行（均需要 sudo）
sudo apt-get remove tros-humble-stereonet-model
sudo dpkg --remove --force-all tros-humble-stereonet-model
sudo apt install -y tros-humble-hobot-stereonet
```

第 2 行的 `dpkg --remove --force-all` 是因为第 1 行可能因为依赖关系删不掉，需要用 dpkg 强删。这种「先删旧包再装新包」的处理方式在 TROS 大版本切换时还会遇到，值得记住这个模式。

> 来源：官方文档 Release_Note/release_note（https://developer.d-robotics.cc/rdk_x_doc/Release_Note/release_note）、官方文档 RDK（https://developer.d-robotics.cc/rdk_x_doc/RDK）、官方文档 Quick_start/system-burn/burn-sd-card（https://developer.d-robotics.cc/rdk_x_doc/Quick_start/system-burn/burn-sd-card）、社区帖 35730（https://forum.d-robotics.cc/t/topic/35730）

## 1.5.6 变砖恢复

「变砖」在 RDK X5 上分几个层级，处置方式完全不同。先按严重程度分级：

| 级别 | 现象 | 可恢复性 | 处置 |
| --- | --- | --- | --- |
| 一级 | 系统起不来，串口有 BL1/BL2/U-Boot 日志 | 高 | 重烧 SD 卡镜像 |
| 二级 | U-Boot 正常但内核 panic / 根文件系统挂载失败 | 高 | 重烧 SD 卡镜像 |
| 三级 | U-Boot 进不去，串口只到 BL2 就循环 | 中 | XBurn 重刷 miniboot |
| 四级 | 串口完全无输出，PC 不识别设备 | 低 | 检查供电/线材，最后才是硬件故障 |

### 1.5.6.1 一级与二级：重烧镜像即可

判据是串口日志能走到 U-Boot 之后。帖 31743 的日志就是典型二级：BL1/BL2/BL31/OP-TEE/U-Boot 全部正常，内核也起来了，最后 `Kernel panic - not syncing: VFS: Unable to mount root fs on unknown-block(179,2)`。处置是换卡重烧（详见第 2 章 2.9 节案例 C）。

帖 34478 的 `Starting kernel …` 之后无输出也属于这一级，官方人员判断「miniboot没看到有问题，还是SD卡的问题」。

### 1.5.6.2 三级：XBurn 重刷 miniboot

判据是串口日志停在 BL2 阶段、U-Boot 起不来，或者反复打印同一段 boot 日志。

社区帖 35783 提供了一个完整的恢复路径，虽然它的起因是自编译镜像，但恢复了分区表层面的损坏，方法可复用：

「失败点在分区表：`Writing 'boot' FAILED (remote: 'cannot find partition')` 加上前面的 `boot partition size: 0`，说明板子当前 fastboot 读不到有效的 GPT，单独烧 boot 分区自然找不到目标（多半是之前全镜像烧录失败把分区表弄坏了）。串口里 `ubootenv bad CRC, using default environment` 是正常现象（`ubootenv.img` 默认就是空的），不是问题原因。」

给出的恢复方法：

「1. 从 0 地址整体烧录（含分区表），不要单独烧 boot。串口进 U-Boot 命令行，执行 `fastboot 0`，然后在 PC 的 out/product 目录下：

```
fastboot flash addr:0x0 emmc_disk.simg
fastboot reboot
```

2. 用 xburn 重烧自编译全镜像时注意三点：
- 『镜像文件目录』要选整个 out/product 目录，工具靠里面的 `x5-soc-release-gpt.json` 获取分区表，只给单个 img 不行；
- 产物在网络共享上时，建议先把 out/product 完整拷到本地磁盘再烧，网络路径读取超时很容易导致烧录中途失败；
- 板子当前系统已不完整的话，下载模式别选纯 Fastboot（它要求非空板、镜像可正常启动），改用 `dfu_fastboot` 或 `xmodem_fastboot` 空板烧录模式，会用 `out/product/uart_usb` 里的固件先引导再写全镜像。

另外你串口日志里有 `SD Card detected, entering UMS update system on mmc 1`，烧 eMMC 时建议把 SD 卡拔掉，避免 U-Boot 走进 UMS 流程干扰烧录。」

对普通用户（不涉及自编译镜像），能落地的部分是这三条：

1. **下载模式必须选 Serial+USB / xmodem_fastboot**，因为系统已不完整，纯 Fastboot 模式要求 U-Boot 正常。
2. **烧 eMMC 时拔掉 SD 卡**，否则 U-Boot 可能进 UMS 流程。
3. **介质必须本地磁盘**，不要从网络共享路径直接烧。

需要说明的是：帖 35783 第 4 楼用户反馈「执行上面烧录命令后，板子烧成砖了」——说明 `fastboot flash addr:0x0` 这条命令用错了镜像会造成更严重的损坏。这条命令是给自编译 SDK 产物用的，普通用户不要执行。

### 1.5.6.3 四级：串口完全无输出

按这个顺序排查：

```bash
# 1. 换 5V/5A 适配器（不是 PC USB 口）
# 2. 换一条确认能传数据的 Micro-USB 线
# 3. 换 PC 的 USB 2.0 口（不用 HUB、不用前置面板口）
# 4. 确认串口波特率：X5 = 115200，Module = 921600
# 5. 换一台 PC 排除本机驱动问题
```

如果五步都排除，才考虑硬件故障。社区帖 34478 官方人员的判断可作参照：「您的板子 BootROM→U-Boot 都正常，硬件大概率没问题！」——只要串口能看到 `SNOTICE: Welcome to Horizon X5 ASIC BOOTROM` 这行，就说明芯片、DDR、串口链路都是好的，问题一定在软件层。

### 1.5.6.4 救砖的正确心态

社区帖 34193 是一个 20 回复的「刷机变砖」帖，虽然主体针对 X3，但它给出的思路对 X5 同样适用：变砖几乎总是可以恢复的，因为 BootROM 在芯片内部、不可破坏。真正的硬件故障概率极低。

该帖里 `RDK_Agent` 反复推荐的「最小启动固件」方法值得留个记录，但要注意它给出的下载地址是旧域名 `sunrise.horizon.cc`，且镜像文件名 `disk_nand_minimum_boot_2GB_3V3_20230413.img` 与 2023 年的 X3 固件对应。**X5 用户不要用这个地址**，正确的 X5 miniboot 下载入口是 `https://archive.d-robotics.cc/downloads/miniboot/rdk_x5/`（见第 2 章 2.6 节）。

> 来源：社区帖 35783（https://forum.d-robotics.cc/t/topic/35783）、社区帖 34478（https://forum.d-robotics.cc/t/topic/34478）、社区帖 31743（https://forum.d-robotics.cc/t/topic/31743）、社区帖 34193（https://forum.d-robotics.cc/t/topic/34193）、官方文档 Quick_start/system-burn/upgrade-miniboot（https://developer.d-robotics.cc/rdk_x_doc/Quick_start/system-burn/upgrade-miniboot）

## 1.5.7 一套可执行的维护节奏

把本章内容压成一个可执行的周期表：

| 时机 | 动作 | 命令 |
| --- | --- | --- |
| 装完系统首次 | 更新软件包列表 | `sudo apt update` |
| 装完系统首次 | 全面升级 | `sudo apt full-upgrade` |
| 每次 apt 升级后 | **补做 miniboot** | `sudo rdk-miniboot-update` |
| 每次 apt 升级后 | 重启 | `sudo reboot` |
| 重大改动前 | 系统备份 | `sudo rdk-backup /mnt` |
| 备份前 | 清理缓存与日志 | `sudo apt clean` |
| 还原到更大卡后 | 扩容量 | `sudo resize2fs /dev/mmcblk1p2` |
| 多机部署后 | 改主机名、重生成 SSH 密钥 | 见 5.4 节 |
| 出问题时 | 先抓 `rdkos_info` | `sudo rdkos_info` |

`rdkos_info` 这一项值得单独强调。它的定位是「一次性收集 RDK 系统的软件、硬件版本，驱动加载清单，RDK 软件包安装清单和最新的系统日志，方便用户快速获取当前系统的状态信息」。官方 FAQ 在「提问前预排查」一节要求：「在提问时，请一并提供通过 `rdkos_info`、`apt list --installed | grep hobot` 等命令获取的当前系统和软件包版本信息。」

输出模式：

| 选项 | 作用 |
| --- | --- |
| `-b` | 基础输出模式，不收集系统日志 |
| `-s` | 简洁输出模式（默认），输出 30 行最新系统日志 |
| `-d` | 详细输出模式，输出 300 行最新系统日志 |
| `-v` | 显示版本信息 |
| `-h` | 显示帮助信息 |

```bash
# 出问题时先抓这个（需要 sudo）
sudo rdkos_info -d > /home/sunrise/rdkos_info_$(date +%Y%m%d%H%M%S).txt
```

关键输出段：

```
[Hardware Model]:     板卡型号与 Board Id
[CPU And BPU Status]: 温度、CPU 频率、BPU 频率与负载
[Total Memory]:       总内存
[ION Memory Size]:    ION 预留大小
[RDK OS Version]:     系统版本
[RDK Kernel Version]: 内核版本
[RDK Miniboot Version]: U-Boot 版本
```

`[RDK Miniboot Version]` 这一行是判断「有没有做 miniboot 更新」的直接依据，比翻串口日志方便得多。

> 来源：官方文档 Appendix/rdk-command-manual/cmd_rdkos_info（https://developer.d-robotics.cc/rdk_x_doc/Appendix/rdk-command-manual/cmd_rdkos_info）、官方文档 FAQ/hardware_and_system（https://developer.d-robotics.cc/rdk_x_doc/FAQ/hardware_and_system）

## 常见误区

**误区一：`apt full-upgrade` 之后就完事了。**
官方两次强调「更新系统后，请使用 `rdk-miniboot-update` 命令更新 NAND 固件至最新版本」。漏掉这步，3.2.3 的内存释放优化和 3.3.1 的 8GB 板卡内存修复都不会生效。判断有没有漏，看 `rdkos_info` 的 `[RDK Miniboot Version]`。

**误区二：`rdk-backup` 输出到 exFAT/NTFS 的 U 盘。**
这是社区里「第二阶段一直报错」的根因。官方人员的解释是 exFAT/FAT32「不支持 Linux 的文件所有权和精细的文件权限」，导致 `Operation not supported` / `Permission denied` 刷屏，最终镜像不完整、烧录后起不来。输出介质必须格式化为 ext4。

**误区三：想在 32G 卡上备份 29G 系统，所以随便找张卡当输出。**
问题不在于容量而在于文件系统。而且 `rdk-backup` 默认打包目录是 `/mnt`，打包目录本身「在制作镜像时会被忽略」——所以挂在 `/mnt` 上的那张卡的数据不会被写进镜像，这点是安全的。

**误区四：降级 miniboot 以「回到稳定版本」。**
官方三处文档都写了「严禁降级刷入旧版本固件……降级操作可能导致设备无法启动」，而且 3.3.1 起工具直接拦截。miniboot 只能升不能降。

**误区五：从备份还原到更大容量的卡后就以为能用了。**
系统只会用到原卡容量，剩下空间空着。必须 `resize2fs`（必要时先 `growpart`）扩展，否则很快又会磁盘满。

**误区六：多台设备用同一份还原镜像部署，不改 SSH 主机密钥。**
所有设备共用一份主机密钥意味着失去主机身份校验能力，切换到另一台设备时 PC 会报 `Host key verification failed` 或安全警告。部署后应重生成。

**误区七：把 4 级「串口完全无输出」直接判为硬件报废。**
只要能看到 `SNOTICE: Welcome to Horizon X5 ASIC BOOTROM`，就说明芯片、DDR、串口链路都是好的，问题在软件层。先换电源、换线、换 USB 口、核对波特率（X5 115200 / Module 921600），四步走完再谈硬件。
