素材已经抓取到本地，写作时必须基于素材取证，不得凭记忆编造。

## 硬性写作要求

1. **全部中文**，技术术语保留英文原文（如 `hbm_runtime`、`BPU`、`VIO`、`hb_mapper`）。
2. **每条结论要有出处**。正文里对官方文档的事实，标注 `> 来源：官方文档 <slug>（<url>）`；对社区经验，标注 `> 来源：社区帖 <topicId>（<url>）`。出处行放在该小节末尾，可以合并多个来源。
3. **区分「官方说法」与「社区实测/踩坑」**。两者冲突时如实并列，并给出判断依据，不要和稀泥。
4. **版本必须显式**。RDKOS 版本跨度大（3.0.0 → 3.5.0），凡涉及 API 的段落必须写明适用版本。**关键分界：RDKOS V3.5.0（2026-04）起 Python 算法推理统一改为 `hbm_runtime` 接口**；3.5.0 之前是 `pyeasy_dnn` / `hobot_dnn`。写错版本口径是本仓库最容易犯的错。
5. **错误反思必须可落地**：每个问题写成四段式——
   - **现象**（用户看到的原文报错，报错文本要原样抄，不要改写）
   - **根因**（为什么会这样，讲清机制）
   - **处置**（可直接复制的命令/改动，标注需要 `sudo` 与否）
   - **预防**（下次怎么避免，或怎么快速定位）
6. **命令必须可复制**：用 ```bash / ```python / ```c++ 代码块，行内命令不要加 `$` 或 `#` 前缀，注释用中文简短说明。
7. **不要写营销话术**。不要「强大的」「一站式的」「轻松搞定」。直接陈述事实与步骤。
8. **表格优先**：参数、引脚、型号、错误码、版本差异都用表格。
9. **配图**：只引用官方图床绝对地址（`https://rdk-doc.oss-cn-beijing.aliyuncs.com/...`），不要编造图片路径，不要引用不存在的本地图片。
10. **每章开头写「本章解决什么」**（2-4 句），结尾写「常见误区」（2-4 条）。

## 文件与命名

- 每个分卷目录下，文件名用 `NN-主题.md`，编号两位，与目录一致。
- 每章第一行是 `# 章标题`（只用一个一级标题）。
- 章内层级从 `##` 开始。
- 所有章节必须被 `docs/SUMMARY.md` 索引到（由主控统一生成，你只写章节文件，不要改 SUMMARY.md）。

## 交叉链接

- 仓库内互链用相对路径，例如 `[烧录](../01-开箱与系统安装/02-系统烧录.md)`。
- 链接到官方文档用绝对 URL。

## 禁止事项

- 不要修改 `_work/` 下任何文件。
- 不要创建你负责范围之外的文件。
- 不要写「TODO」「待补充」「占位」。写不出证据的内容就删掉，不要留空壳。
- 不要编造社区帖 URL 或 topicId：只用你在 `_work/forum/` 里真实读到的。
