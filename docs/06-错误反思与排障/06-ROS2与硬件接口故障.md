# ROS2 与硬件接口故障

## 本章解决什么

TROS/ROS2 这一层的报错有个共同特征：**报错说的是「谁死了」，但不说「为什么死」**。`process has died [pid 44034, exit code -6]` 只告诉你某个节点终止了，真正的根因可能在它的上游（没有数据）、在它的初始化（硬件没就绪）、或者在它自己的后处理（越界访问）。

硬件接口层（CAN / UART / SPI / PWM / GPIO）则相反：报错很具体，但**经常是「你查的地方不是设备在的地方」**——串口节点存在但没使能、CAN 波特率设了但不生效、PWM 引脚没复用。

本章按「先分清 ROS 节点死亡的性质，再逐类硬件接口」排列。

## 一、ROS 节点死亡的四种性质（先做这一步）

看到 `process has died` 先别急着查代码，按退出码和上下文分类：

| 退出码 / 关键行 | 性质 | 判断依据 | 查哪里 |
| --- | --- | --- | --- |
| `exit code -6` + `terminate called after throwing` | C++ 未捕获异常 → abort | 初始化失败后继续用已失效的 context | 该节点**第一条** ERROR |
| `exit code -11` | 段错误（SIGSEGV） | 内存越界/空指针解引用 | 后处理、张量索引、模型替换 |
| `exit code -2` / 正常退出 | 被 Ctrl+C 或 launch 终止 | 有 `signal_handler(signum=2)` | 不是故障 |
| 节点活着但话题无数据 | 上游没发布 | `ros2 topic hz` 为 0 | 相机/codec/上游节点 |

另外两类高频「看起来像节点崩了」的情况：

- **`Hobot_Codec has not received image for more than 5 seconds!`** —— 这不是 codec 崩了，是**上游没有图像**。codec 只是等不到数据在喊。
- **`Websocket did not receive image data!`** —— 同理，websocket 等不到 codec 的输出。

**排查顺序必须从最上游往下**：camera → codec → websocket。绝大多数「网页不显示」的帖子，根因在最上游的相机。

## 二、ROS2 / TROS 故障条目

### 6.1 mipi_cam 启动时 cap capture init failture，随后 exit code -6

### 现象

```
[mipi_cam-1] [ERROR] [1775288859.875021645] [mipi_cam]: [init]->cap capture init failture.
[mipi_cam-1] [ERROR] [1775288859.875874227] [mipi_node]: [init]->mipinode init failure.
[mipi_cam-1] terminate called after throwing an instance of ‘rclcpp::exceptions::RCLError’
[ERROR] [mipi_cam-1]: process has died [pid 5748, exit code -6, cmd ‘/opt/tros/humble/lib/mipi_cam/mipi_cam --ros-args ...
```

随后 codec 与 websocket 也开始刷：

```
[hobot_codec_republish-2] [ERROR] [1775288862.646726889] [hobot_codec_encoder]: Hobot_Codec has not received image for more than 5 seconds! Please check whether the image publisher still exists by ‘ros2 topic info /hbmem_img’!
[websocket-4] [ERROR] [1775288863.040192167] [websocket]: Websocket did not receive image data! Please check whether the image publisher still exists by ‘ros2 topic info /image’!
[websocket-4] [ERROR] [1775288863.040440292] [websocket]: Websocket did not receive AI data! Please check whether the AI data publisher still exists by ‘ros2 topic info hobot_dnn_detection’!
```

> 来源：社区帖 34614（https://forum.d-robotics.cc/t/topic/34614）

### 根因

关键就是第一行：`cap capture init failture`（`failture` 是原始日志拼写）。

官方诊断：

> 原因：系统默认尝试使用 MIPI 相机，但你的板子没有连接 MIPI 相机或 MIPI 相机初始化失败。

> 来源：社区帖 34614

也就是说 **launch 默认用 MIPI 相机，但实际接的是 USB 相机**（或者压根没接）。后面的 `Hobot_Codec has not received image`、`Websocket did not receive image data` 全是**连带反应**——上游没图，下游只能干等。

这也解释了为什么用户「用官方模型也报错」：跟模型无关，是相机源选错了。

### 处置

指定实际的相机类型：

```bash
# 用 USB 相机
export CAM_TYPE=usb
ros2 launch origincar_bringup usb_websocket_display.launch.py

# 用 MIPI 相机
export CAM_TYPE=mipi
ros2 launch origincar_bringup mipi_websocket_display.launch.py
```

验证相机真的出图了再往下走：

```bash
ros2 topic list | grep -i image
ros2 topic hz /image        # 或 /hbmem_img
```

`ros2 topic hz` 有稳定输出，才说明相机链路通。

### 预防

**TROS 的 launch 通常靠 `CAM_TYPE` 环境变量或参数决定数据源**。换硬件后第一件事是确认这个变量，不要指望自动识别。

另外记住这条排查顺序：**camera → codec → websocket**。`has not received image` 这类报错永远往上游查。

### 6.2 推理节点 exit code -11，websocket 收不到 AI 数据

### 现象

```
[ERROR] [example-3]: process has died [pid 27264, exit code -11, cmd '/opt/tros/humble/lib/dnn_node_example/example --ros-args ...
[websocket-4] [ERROR] [1775280708.304688765] [websocket]: Websocket did not receive AI data! Please check whether the AI data publisher still exists by 'ros2 topic info hobot_dnn_detection'!
```

> 来源：社区帖 34614（https://forum.d-robotics.cc/t/topic/34614）

同一现象在另一帖也出现：`pid 13926, exit code -11`。

> 来源：社区帖 34523（https://forum.d-robotics.cc/t/topic/34523）

### 根因

`exit code -11` 是 SIGSEGV（段错误），含义是**进程访问了非法内存**。在推理节点里，三类原因占绝大多数：

1. **模型与代码不匹配**。用自己训练的 `.bin` 替换了示例自带的模型，但预处理尺寸、张量数量、后处理逻辑没跟着改。官方 FAQ 对这一条有明确说明（见 [AI 推理章 5.7](05-AI推理与模型精度故障.md)）。
2. **模型输出结构与 parser 预期不符**。比如 bbox 分支变成 int32 + `Layout: NONE`，parser 按错误维度索引越界。
3. **上游数据格式不对**。喂进来的图像是 640x480，而代码按 640x640 去索引。

用户自己也曾怀疑尺寸问题：

> 模型是640\*\*640,而我的相机拍照是640\*\*480，有影响吗

这个怀疑是对的——但在 TROS 的 `dnn_node_example` 里，**节点内部通常会自动 resize**，所以答案并非简单的「有影响」。真正致命的是配置文件里显式写了尺寸但相机不支持（见 6.3）。

### 处置

第一步，先确认不是模型的问题——**换回官方自带的 `.bin` 跑同一个示例**：

```bash
# 用官方模型验证链路
ros2 launch dnn_node_example dnn_node_example_feedback.launch.py \
  dnn_example_config_file:=/opt/tros/humble/lib/dnn_node_example/config/yolov8workconfig.json \
  dnn_example_image:=<一张测试图>
```

- 官方模型也崩 → 链路/环境问题（相机尺寸、TROS 版本、依赖）；
- 官方模型能跑 → 自己的模型有问题，去查导出与量化（见 AI 推理章 5.2、5.4）。

第二步，看崩之前最后几行日志——段错误的线索在**崩前的最后一行**，不在崩的那一行。

### 预防

**改模型必须同步改代码**，不能只替换 `.bin`。建立习惯：每换一次模型，都跑一遍「官方模型对照组」。

### 6.3 dnn_node_example 崩溃：配置文件里多写了 input_width/input_height

### 现象

用户按自己的配置文件跑 `dnn_example_config_file:=.../yolov8workconfig.json`，节点崩溃。

> 来源：社区帖 34614（https://forum.d-robotics.cc/t/topic/34614）

### 根因

这是「配置里多写了两个字段」引起的崩溃，很反直觉。社区给出的分析：

> 关键差异：官方模型的配置文件没有指定 input_width/input_height，让 dnn_node_example 节点自动处理 resize；而你的配置可能添加了这些字段导致冲突。

机制上：`dnn_node_example` 的工作流程是「相机输出 640×480 → 节点内部自动 resize 到模型需要的 640×640 → 推理 → 后处理把结果映射回 640×480」。一旦配置里显式指定 `input_width: 640, input_height: 640`，节点会尝试**强制相机输出这个尺寸**；相机不支持 640x640，初始化失败，随后空指针解引用崩溃。

也就是说：**这两个字段不是「告诉节点模型输入多大」，而是「要求相机输出多大」**。这是一个语义误解。

### 处置

从配置文件里删掉这两个字段：

```json
{
  "model_file_name": "yolov8.bin",
  "class_num": 80,
  "cls_names_list": "..."
  // 不要写 input_width / input_height
}
```

对比官方配置找差异：

```bash
cat /opt/tros/humble/lib/dnn_node_example/config/yolov8workconfig.json
diff /home/sunrise/.../yolov8workconfig.json \
     /opt/tros/humble/lib/dnn_node_example/config/yolov8workconfig.json
```

**不需要重新量化模型**——节点会自动 resize。

### 预防

**改配置前先 diff 官方配置**。TROS 的 json 配置字段语义不都是字面意思，多写字段往往比少写更危险。

### 6.4 VNC / SSH 里跑示例，摄像头画面不显示

### 现象

用户描述：「在VNC中执行示例代码无法显示摄像头画面」。

> 来源：社区帖 33658（https://forum.d-robotics.cc/t/topic/33658）

### 根因

这与章节 4.12 是同一个机制族：**RDK 的部分摄像头示例走的是硬件直出（HDMI 物理口 / 硬件 OSD），不是 `cv2.imshow()` 窗口**。

`cv2.imshow()` 需要 X server 的显示通路。通过 SSH 登录（无 X）时，`imshow` 根本没有可用的 display；通过 VNC 登录时，X 是有的，但示例如果是硬件直出，画面会出现在**板子物理 HDMI 口**上，VNC 里看不到。

官方 FAQ 说得明确：

> 这些特定示例的预期效果（包括正确的图像朝向和硬件 OSD）需要在关闭桌面环境后，通过 HDMI 物理端口直接观察。

> 来源：官方文档 FAQ/hardware_and_system Q32

### 处置

先判断示例属于哪一类：

| 示例类型 | 画面出现在哪 | 怎么验证 |
| --- | --- | --- |
| `cv2.imshow()` 窗口 | VNC/本地桌面 | VNC 里能看到窗口 |
| HDMI 硬件直出 | 板子物理 HDMI 口 | 必须关桌面 + 接显示器 |
| TROS 话题 + web 推流 | 浏览器访问板子 IP | `ros2 topic hz` + 浏览器 |

走 TROS 推流的方式最通用（不需要物理显示器）：

```bash
source /opt/tros/humble/setup.bash
ros2 launch mipi_cam mipi_cam_dual_channel_websocket.launch.py
# 浏览器访问 http://<板子IP>:8000
```

### 预防

**先确认示例的输出方式，再选验证环境**。想远程看图，一律用 TROS web 推流，不要指望 VNC 能看到所有示例的画面。

### 6.5 标定数据不存在告警：xxx does not exist!

### 现象

```
[hobot_usb_cam-1] [WARN] [1775280703.057999184] [hobot_usb_cam]: Camera calibration file: [/opt/tros/humble/lib/hobot_usb_cam/config/usb_camera_calibration.yaml] does not exist!
[hobot_usb_cam-1] If you need calibration msg, please make sure the calibration file path is correct and the calibration file exists!
```

> 来源：社区帖 34614（https://forum.d-robotics.cc/t/topic/34614）

### 根因

官方 FAQ 明确回答了这个问题：**这个提示本身通常是正常的，不一定代表摄像头无法工作**。

> 许多 ROS 节点的默认日志级别是 INFO 或 WARN。当摄像头节点启动时，它会尝试加载相机的内参标定文件（通常是一个 .yaml 文件，包含了相机的焦距、畸变系数等参数）。如果找不到这个文件，它会输出一个警告信息，但通常会继续使用一组默认的或无标定的参数来运行。

> 来源：官方文档 FAQ/tros_ros Q8（https://developer.d-robotics.cc/rdk_x_doc/FAQ/tros_ros）

**这是本章最需要强调的一条「假警报」**。很多用户看到 `does not exist!` 就以为摄像头坏了，顺着这条线排查半天。

什么时候才需要标定文件：做精确测量、三维重建、去畸变。做普通检测/分类时，缺标定文件影响很小。

### 处置

不需要处理，除非你要做需要精确内参的应用。

验证摄像头是否真的在工作，绕开这条告警：

```bash
ros2 topic list | grep -i image
ros2 topic hz /image_raw
ros2 topic echo /image_raw --once
```

有话题、有帧率、有数据 → 摄像头是好的。

需要标定时，把正确的 yaml 路径传进去：

```bash
ros2 launch hobot_usb_cam usb_cam.launch.py \
  camera_calibration_file_path:=/path/to/your_calib.yaml
```

### 预防

**把这条加进「无害告警清单」**。同类还有：`Cannot open file /sys/kernel/debug/...`、`Unsupported op`、`[W][DNN]... Inconsistency between the hbrt library version ... and the model build version`。

最后这条值得单独说，它是**版本不一致的提示，但不是错误**：

```
[W][DNN]bpu_model_info.cpp:491][Version](2000-01-01,08:02:01.236.886) Model: fcos_efficientnetb0_512x512_nv12. Inconsistency between the hbrt library version 3.15.55.0 and the model build version 3.15.47.0 detected, in order to ensure correct model results, it is recommended to use compilation tools and the BPU SDK from the same OpenExplorer package.
```

它是 `[W]`（Warning）级别。含义是「模型编译版本比运行时旧」，可能影响结果正确性但不阻塞运行。要么忽略，要么按 5.1 对齐版本。

> 来源：社区帖 29003（https://forum.d-robotics.cc/t/topic/29003）

### 6.6 浏览器打不开 TROS 的 web 可视化页面 / 只有图像没有检测框

### 现象

两类：

- 浏览器访问 `http://<板子IP>:<端口>` 页面打开失败；
- 页面能打开、能看到摄像头画面，但**没有检测框 / 骨骼点**。

> 来源：官方文档 FAQ/applications_and_examples Q13、Q14（https://developer.d-robotics.cc/rdk_x_doc/FAQ/applications_and_examples）、FAQ/tros_ros Q9

### 根因

按官方 FAQ 给的清单，页面打不开的常见原因：

1. **相关节点没起** —— 图像发布节点（`mipi_cam`/`usb_cam`）、AI 推理节点、websocket 节点三者缺一不可；
2. **IP 不对** —— 浏览器里必须填板子的**实际 IP**（`eth0`/`wlan0`/`usb0` 三张网卡地址不同，见网络章 3.1）；
3. **代理干扰** —— PC 配了代理时，对局域网 IP 的访问可能被代理拦截；
4. **在板子本地开浏览器** —— 板卡 CPU 同时承担 ROS 节点 + websocket + 桌面 + 浏览器渲染，容易卡死；
5. **浏览器缓存/兼容性**。

「只有图像没有 AI 结果」的根因更具体：

> hobot_websocket 节点在启动时，如果其参数 only_show_image 设置为 False（即期望同时显示图像和 AI 结果），它可能需要接收到第一个 AI 结果消息 (ai_msg) 后，才能开始同步图像和 AI 数据并进行渲染。

也就是说：**它在等第一帧 AI 结果**。如果推理节点一直没输出（比如没检测到任何目标），页面就只显示图像。

### 处置

按顺序验证三层：

```bash
# 1. 节点都在吗
ros2 node list
ros2 topic list

# 2. 图像话题有帧吗
ros2 topic hz /image_combine_jpeg

# 3. AI 话题有帧吗
ros2 topic hz /hobot_dnn_detection
```

第 3 步为 0 就是根因。

再看 websocket 参数：

```bash
ros2 param get /websocket only_show_image
```

若为 `False` 而 AI 话题确实没数据，先解决推理侧。

### 预防

**在板子上开浏览器看自己的推流是最差的做法**。官方建议「通常建议在另一台 PC 上打开浏览器来访问 RDK 上的 WebSocket 服务」。

### 6.7 编译 ROS2 包报 pyparsing 没有 operatorPrecedence

### 现象

```
AttributeError: module 'pyparsing' has no attribute 'operatorPrecedence'
```

> 来源：官方文档 FAQ/applications_and_examples Q10（https://developer.d-robotics.cc/rdk_x_doc/FAQ/applications_and_examples）

### 根因

`python3-catkin-pkg`（解析 `package.xml` 的库）版本过低，它依赖的 `pyparsing` 版本与其不兼容。`operatorPrecedence` 在 pyparsing 3.x 中被移除/改名，旧版 catkin-pkg 还在用它。

### 处置

加 ROS 官方源并升级 `python3-catkin-pkg`（**需要 sudo**）：

```bash
sudo apt update && sudo apt install curl gnupg2 lsb-release
sudo curl -sSL https://raw.githubusercontent.com/ros/rosdistro/master/ros.key \
  -o /usr/share/keyrings/ros-archive-keyring.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/ros-archive-keyring.gpg] http://packages.ros.org/ros2/ubuntu $(source /etc/os-release && echo $UBUNTU_CODENAME) main" \
  | sudo tee /etc/apt/sources.list.d/ros2.list > /dev/null

sudo apt remove python3-catkin-pkg
sudo apt update
sudo apt install python3-catkin-pkg
```

若仍不行，检查 pyparsing 版本：

```bash
pip show pyparsing
```

### 预防

板卡上同时装 TROS 和从源码装的 ROS 包时，Python 依赖容易打架。**优先用 apt 装 ROS 相关包，不要用 pip 混装。**

### 6.8 rviz2 启动报 libOgreMain.so.1.12.1 找不到

### 现象

```
rviz2: error while loading shared libraries: libOgreMain.so.1.12.1: cannot open shared object file: No such file or directory
```

> 来源：社区帖 32238（https://forum.d-robotics.cc/t/topic/32238）

### 根因

动态链接器找不到 `libOgreMain.so.1.12.1`。rviz2 依赖 Ogre 渲染引擎，这个库属于 `libogre-1.12` 包。缺失的可能原因：

1. 该包未安装；
2. 装了但版本不同（如 1.9 或 1.13）；
3. 库在但不在 `ld.so` 的搜索路径里。

### 处置

```bash
# 查是不是装了但找不到
ldconfig -p | grep -i ogre
find / -name "libOgreMain.so*" 2>/dev/null

# 没装就装（需要 sudo）
sudo apt install libogre-1.12 libogre-1.12-dev

# 装了但路径没登记
sudo ldconfig
```

### 预防

官方 FAQ 明确不建议在 RDK 这类嵌入式终端上直接跑 rviz2——CPU 与 GPU 资源不够，即使装上也卡。**推荐在 PC 上看板子发出来的话题**：

> 为什么不建议在 RDK 这种嵌入式终端设备上直接运行 Rviz 或 Gazebo？推荐的做法是什么？

> 来源：官方文档 FAQ/tros_ros Q11

## 三、硬件接口故障条目

### 6.9 CAN 波特率设置后实际不符 / 接收卡死

### 现象

**现象 A（波特率不符）**：设置 2M，实际逻辑分析仪收到 1M。用户补充「2块X5均出现该情况，另一块为3.0.1镜像版本」。

> 来源：社区帖 28135（https://forum.d-robotics.cc/t/topic/28135）

**现象 B（接收卡死）**：波特率 500K，刚开始正常接收，接收 1 分钟左右卡死；查看 can 状态发现接收错误导致无法继续接收；`down`/`up` 重启接口后无法接收；重启 RDK X5 后内核初始化 can 失败；**关机断电重启 can 初始化成功**。

> 来源：社区帖 28919（https://forum.d-robotics.cc/t/topic/28919）

**现象 C（接收中断）**：can0 口 1000kbps、总线电阻 60Ω、系统 3.2.3、Miniboot 最新，定周期发送 1000 个 can 帧，「接收数据报错，无法继续接收数据，波特率改为500kbps，且增大『接收缓冲区大小』会改善运行效果，但问题依旧存在」，且「关闭并重新打开canSocket对象，可继续运行，但很快出现以上问题，多次后需要重启系统」。

> 来源：社区帖 31754（https://forum.d-robotics.cc/t/topic/31754）

### 根因

三条现象指向同一类问题：**CAN 控制器在 3.2.3 之前的系统上有驱动缺陷**。

官方对 28135 和 28919 给出了同一句回答：

> CAN的问题在3.2.3的系统中已经修复，可以在社区的上方的"资料"栏目来下载最新的系统。

> 来源：社区帖 28135、28919

具体机制上：

- 波特率不符 → 时钟分频计算错误，设定的位时序没有正确写入控制器；
- 接收卡死后必须断电 → 控制器进入 bus-off 错误状态且驱动未能正确恢复，软件层 `down`/`up` 复位不掉控制器状态，只有掉电才能清；
- 增大接收缓冲区能缓解 → 应用层来不及取走帧导致溢出，属于「症状缓解」而非「根因修复」。

### 处置

**升级系统到 3.2.3 或更新**是唯一根本处置。升级顺序按官方建议：

```bash
# 1. 先进系统升级 Miniboot（需要 sudo + 联网）
sudo rdk-miniboot-update

# 2. 烧录最新系统镜像

# 3. 在新系统里再升级一次 Miniboot
sudo rdk-miniboot-update
```

升级前可先做临时缓解（不是修复）：

```bash
# 需要 sudo：提高接收缓冲区
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 500000 \
  restart-ms 100 \
  rcvbuf 4194304
sudo ip link set can0 up

# 查看错误统计
ip -details -statistics link show can0
candump can0
```

`restart-ms` 让控制器 bus-off 后自动重启，比手动 `down/up` 可靠。

### 预防

- **买板子第一件事就是确认系统版本 ≥3.2.3**；
- 应用层必须处理 bus-off（`restart-ms` + 监听错误帧）；
- 高负载 CAN 场景（1000 帧/秒级别）必须验证长时稳定性，不能只看「能发出去」。

### 6.10 CAN-FD 接收错误、卡死

### 现象

与 6.9 现象 B 相同（500K 波特率、1 分钟后卡死、断电才能恢复）。

> 来源：社区帖 28919（https://forum.d-robotics.cc/t/topic/28919）

### 根因

同上，驱动层缺陷。**CAN 与 CAN-FD 在 3.2.3 之前的系统上都有问题**，官方回复没有区分两者，统一指向系统版本。

补充一个常被忽略的点：CAN-FD 需要**总线上所有节点都支持 FD**，且数据段波特率（`dbitrate`）要单独设。只设 `bitrate` 会让 FD 帧在数据段出错。

### 处置

```bash
# 需要 sudo
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 500000 dbitrate 2000000 fd on
sudo ip link set can0 up
ip -details link show can0
```

确认 `fd on` 与两个波特率都生效后，再升级系统到 3.2.3+。

### 预防

FD 场景下**必须同时验证仲裁段与数据段**。用逻辑分析仪看两段的实际速率，不要只信 `ip link` 的回显。

### 6.11 串口 ttyS2 / ttyS3 收不到数据，只有 ttyS1 正常

### 现象

用户描述：系统 3.1.1，「使用例程test_serial.py，测试ttyS2(将15脚和22脚连接起来)和ttyS3(将3脚和5脚连接起来)，没有返回数据」，并强调「我测试了只有串口1是正常，其他串口都不行」。

> 来源：社区帖 28415（https://forum.d-robotics.cc/t/topic/28415）

同类：`/dev/ttyS7` 存在但无法访问；`srpi-config` 里找不到 serial7，回环测试失败。

> 来源：社区帖 31310、28811

### 根因

**串口节点存在 ≠ 串口已使能**。在 RDK 上，`/dev/ttyS*` 的设备节点由设备树生成，但**引脚复用（pinmux）需要显式打开**，否则引脚还挂在别的功能上（GPIO / PWM / 其他外设），数据根本到不了 UART 控制器。

社区官方在回复中给的关键提示有两条：

> 你好，我这边srpi-config命令里面所有能开的串口都测试过，目前看系统镜像是最新的了，srpi-config命令中也打开了对应的设置，需要注意的是涉及硬件的部分需要使用root用户或者sudo来运行脚本。

> 你好，我这边是成功的，如果有问题的话，还有一个可能的点是需要升级miniboot，这个也是在srpi-config命令中升级

> 来源：社区帖 28415

即：**① 引脚复用必须开；② 必须用 sudo 跑；③ Miniboot 也要匹配**。

另一类原因：40PIN 上标注的「串口」脚位与内核里的 `ttyS*` 编号不是一一对应，用户按引脚号去猜 `ttyS` 编号，测的根本不是同一路。

### 处置

第一步，用 `srpi-config` 打开引脚复用（**需要 sudo**）：

```bash
sudo srpi-config
# 3 Interface Options → I3 Peripheral bus config → 打开对应 UART
```

第二步，确认实际设备与引脚映射：

```bash
ls -l /dev/ttyS*
cat /proc/device-tree/soc/serial@*/status 2>/dev/null
dmesg | grep -i ttyS
```

第三步，做**自环测试**（把该路的 TX 与 RX 短接），确认硬件通路：

```bash
# 需要 sudo 访问串口设备
sudo python3 -c "
import serial, time
s = serial.Serial('/dev/ttyS2', 115200, timeout=1)
s.write(b'hello')
time.sleep(0.2)
print(s.read(10))
"
```

若自环能收到 → 串口功能正常，之前失败是接线/引脚号搞错；若自环收不到 → 引脚复用没开或该路硬件不通。

第四步，升级 Miniboot（见 2.7 的顺序）。

### 预防

- **不要按 40PIN 引脚号猜 ttyS 编号**，用 `dmesg | grep -i ttyS` 看实际注册情况；
- 自环测试是最快的硬件通路验证手段，接线问题时先自环；
- 串口操作一律加 `sudo`。

### 6.12 PWM 控制舵机不出波形

### 现象

用户描述：「RDK X5板驱动独立电源的舵机云台，但是代码没有问题，电源也没有问题，但是在示波器上无法输出正常的PWM波」，后续补充「我用示波器分别测试了一下板子的PWM波输出，板子只能输出一条噪声特别大的没有正常形状的波形」。

代码使用 `Hobot.GPIO`，舵机参数 `SERVO_FREQ = 50`、脉冲 0.5~2.5ms。

> 来源：社区帖 31643（https://forum.d-robotics.cc/t/topic/31643）

### 根因

「示波器上只有噪声、没有正常方波」这条信息很关键——它排除了「代码逻辑算错占空比」，指向**引脚上根本没有 PWM 信号**。

两种可能：

1. **引脚没有复用成 PWM 功能**。默认该引脚可能是 GPIO 或其他功能，写占空比不会产生任何 PWM 波形。
2. **频率超出硬件 PWM 能力**。社区另一帖问「x5怎么输出10khz的pwm信号」，官方回复指出「输出10khz的信号需要配置周期为 100us」——说明频率可配，但需要显式设周期。

50Hz 舵机信号对硬件来说是很低的频率，通常不是能力问题；所以 1 更可能。

### 处置

第一步，确认驱动与引脚复用：

```bash
ls /sys/class/pwm/
cat /sys/kernel/debug/pwm   # 需要 sudo
```

第二步，用 sysfs 直接测（绕开 Python 库，**需要 sudo**），确认引脚本身能出波：

```bash
# 以 pwmchip0 的 channel 0 为例
echo 0 | sudo tee /sys/class/pwm/pwmchip0/export
echo 20000000 | sudo tee /sys/class/pwm/pwmchip0/pwm0/period     # 20ms = 50Hz
echo 1500000  | sudo tee /sys/class/pwm/pwmchip0/pwm0/duty_cycle # 1.5ms 中位
echo 1 | sudo tee /sys/class/pwm/pwmchip0/pwm0/enable
```

第三步，示波器测该引脚。sysfs 能出波而 Python 库不能 → 库或复用配置问题；sysfs 也出不了 → 引脚未复用成 PWM。

第四步，确认 PWM 引脚复用配置（参考 `config.txt` 与 PWM 驱动调试指南，见 [srpi-config 与 config.txt](../05-进阶驱动与系统/04-srpi-config与config.txt与Thermal频率管理.md)）。

### 预防

**调试 PWM 先用 sysfs 打底，再套库**。这一步能把「库的问题」和「硬件/复用的问题」分开，省掉大量猜代码的时间。

另一条：舵机必须**独立供电并与板子共地**。只接信号线不共地，示波器上看到的也是噪声。

### 6.13 SPI slave 模式下工作不正常

### 现象

用户按官方驱动文档修改 SPI2 的 DTS 以支持 slave 功能后，工作不正常；同时想改 SPI4 做 master，但「没找到 SPI 4 在哪儿，也没有从手册上找到，在购买时也是看见了官网上2组SPI的介绍」。

> 来源：社区帖 28638（https://forum.d-robotics.cc/t/topic/28638）

### 根因

两个独立问题叠加：

1. **SPI slave 的设备树配置有额外要求**。仅加 `spi-slave;` 属性不够，还需要正确的 `compatible`、`reg`、`spi-max-frequency`，以及从机的 DMA/中断配置。
2. **SPI4 可能不存在**。用户是「看到官网上写 2 组 SPI」才去找 SPI4 的——**官网宣传的「组数」与内核里的 SPI 控制器编号不是一回事**，编号可能跳号（SPI0/SPI2 有，SPI1/SPI3 没有）。

### 处置

先确认板子上到底有哪些 SPI 控制器：

```bash
ls /dev/spidev*
ls /sys/class/spi_master/
cat /proc/device-tree/soc/spi@*/status 2>/dev/null
dmesg | grep -i spi
```

只对**实际存在**的控制器改 DTS。slave 模式的完整配置示例（以 spi2 为例）：

```dts
&spi2 {
    status = "okay";
    pinctrl-names = "default";
    pinctrl-0 = <&spi2_pins>;
    spi-slave;

    slave@0 {
        compatible = "dr,x5-spidev";
        spi-max-frequency = <10000000>;
        reg = <0>;
    };
};
```

改完重新编译 dtb 并重启，用 `dmesg | grep -i spi` 确认 probe 成功。

### 预防

**不要按宣传的「几组 SPI」去猜控制器编号**。先 `ls /sys/class/spi_master/` 拿到真实列表，再改对应的 DTS 节点。

### 6.14 srpi-config 打开 UART2 时提示 Unsupport board type

### 现象

用户操作路径：`sudo srpi-config` → `3 Interface Options` → `I3 Peripheral bus config` → 回车后提示：

```
Unsupport board type!!
```

（`Unsupport` 为原始提示拼写。）用户尝试 Update、Update MiniBoot、重启后依然不行。

> 来源：社区帖 31755（https://forum.d-robotics.cc/t/topic/31755）

### 根因

`srpi-config` 需要读板卡型号来决定「这块板子有哪些外设可配」。读到不认识的 Board 类型时，直接拒绝执行外设配置。

`Unsupport board type` 出现在 **RDK X5 Module** 上——Module 版与标准版 X5 的板卡 ID 不同，如果 `srpi-config` 版本偏旧、不认识该 ID，就会报这个错。

### 处置

第一步，确认板卡 ID：

```bash
hrut_boardid
sudo rdkos_info | head -20
```

第二步，升级 `srpi-config` 与 Miniboot：

```bash
sudo apt update && sudo apt upgrade
sudo rdk-miniboot-update
```

第三步，若仍不支持，绕开菜单直接改 `config.txt`（`srpi-config` 最终也是改这个文件）：

```bash
sudo nano /boot/config.txt
# 加入对应外设使能项，保存后重启
sudo reboot
```

第四步，仍不行则联系官方确认该 Module 型号的支持状态。

### 预防

**Module 版与标准版的差异比想象中大**。买 Module 前先确认当前系统版本是否已支持该板卡 ID；升级顺序仍然是「先升 Miniboot → 刷系统 → 再升 Miniboot」。

### 6.15 用 USB 转 TTL 时收发速率不一致、乱码

### 现象

用户描述：「RDK X3 module USB转串口在921600通信速率下，收发速率不一致,乱码（linux 端使用cutecom，windows端使用sscom ），但是debug口的双向通信波特率是正常的」。用户还给出了示波器测量：「cutecom 发送的一位的时间大概1.161us, sscom发送的一位时间 大概1.084us」。

> 来源：社区帖 28777（https://forum.d-robotics.cc/t/topic/28777）

### 根因

用户的测量数据直接点破了根因：**两端实际波特率不一致**。

- `1.161us` 对应约 `1/1.161e-6 ≈ 861,000 bps`
- `1.084us` 对应约 `1/1.084e-6 ≈ 922,500 bps`

即一端实际跑在约 861k、另一端约 922k，相差约 7%。UART 是异步通信，累积误差超过约 2~3% 就会出现采样点偏移导致的乱码。两端都「设成 921600」但实际晶振/分频不同，就是这个结果。

「debug 口双向通信正常」这条补充说明：板卡本身的 UART 没问题，问题在**USB 转串口模块的波特率精度**——很多 CH340/CP210x 模块在高波特率下的实际速率偏差很大。

### 处置

1. **降低波特率**。921600 对廉价 USB 转串口模块要求太高，降到 115200 或 460800 通常就稳定了。
2. 换用带高精度晶振的模块（FT232 系列通常比 CH340 稳）。
3. 两侧都确认实际波特率：

```bash
# Linux 侧
stty -F /dev/ttyUSB0 -a
```

### 预防

**921600 是「能用但不一定稳」的速率**。日常调试用 115200 足够；只有在烧录/大量日志时才有必要上高波特率，且应使用质量可靠的模块。

### 6.16 40PIN GPIO 的 C/C++ 操作与供电边界

### 现象

社区里反复出现的问题：「RDK X5有没有办法用C/C++来驱动GPIO」「40pin c++库有吗？」「RDK X5的排针处串口电平多少？」「40pin口复用」。

> 来源：社区帖 28025、28501、28360、28402

### 根因

社区官方给出的现状是：**C/C++ 侧的 GPIO 库当时「未来会释放，目前以 Python 为主」**。另一位官方人员在另一帖补了具体路径：Python 走 40pin 用户指南，C/C++ 走社区维护的 WiringPi 仓库（gitee 上的 `WiringPi-`）。

> 你好，相关材料未来会释放，请留意手册和系统更新，目前以Python为主
>
> 关于RDK X5的GPIO应用开发——Python：40pin_user_guide/40pin_define；C/C++：https://gitee.com/xin03liu/WiringPi-

> 来源：社区帖 28025（https://forum.d-robotics.cc/t/topic/28025）、社区帖 28501（https://forum.d-robotics.cc/t/topic/28501）

所以「找不到 C++ 库」这件事本身不是配置错误，而是官方支持面当时的真实状态。

另外两个必须记住的硬件边界：

1. **电平是 3.3V，不是 5V**。官方对此的回答只有一个字：3.3V。
2. **40PIN 的 VDD_5V 不应作为主供电输入**。官方 FAQ 对旭日 X3 派明确「不可以」；对 RDK X3 的某些版本「可以但不推荐」，并强调通过非推荐方式供电存在电流不足、电压不稳、缺乏保护电路等风险，损坏后果自负。

> 来源：社区帖 28360（https://forum.d-robotics.cc/t/topic/28360）、官方文档 FAQ/hardware_and_system Q28「旭日 X3 派如何从 40pin GPIO 给板卡供电？RDK X3 呢？」

### 处置

C/C++ 走社区 WiringPi 仓库：

```bash
git clone https://gitee.com/xin03liu/WiringPi-.git
cd WiringPi-
./build
```

Python 走官方 `Hobot.GPIO`，路径见 40pin 用户指南。

> 关于 libgpiod / `/dev/gpiochip*`：这是 Linux 通用的 GPIO 字符设备接口，本库素材中未见官方对其在 RDK X5 上的支持说明或验证记录，因此不在此断言可用性。若你倾向用通用方案，需自行在板端实测 `gpiodetect` 是否能列出 gpiochip，再决定是否采用。

电平确认：

```bash
# 用万用表测目标引脚对 GND 的电压，应为 3.3V 逻辑
```

### 预防

- **信号电平一律按 3.3V 设计**，接 5V 器件必须加电平转换；
- 供电只用 Type-C + 合规适配器，不要从 40PIN 取电；
- 涉及硬件寄存器/引脚的操作必须 `sudo`；
- C/C++ GPIO 属于社区方案而非官方主推路径，长期项目建议先确认该库与当前系统版本的兼容性。

## 四、常见误区

1. **「`process has died` 就是那个节点的问题」**。`exit code -6` 是初始化失败的连带崩溃，根因在第一条 ERROR；`Hobot_Codec has not received image` 是上游没数据，根因在相机。
2. **「`xxx does not exist!` 是错误」**。标定文件缺失是**正常的 WARN**，摄像头照样工作。
3. **「`/dev/ttyS*` 存在就能用」**。引脚复用没开，节点存在也收不到数据。
4. **「CAN 设了波特率就生效了」**。3.2.3 之前有驱动缺陷，且 FD 需要单独设数据段波特率。
5. **「示波器有噪声说明代码算错了」**。只有噪声通常意味着引脚上根本没有 PWM 信号——是复用问题，不是代码问题。
6. **「921600 一定比 115200 好」**。廉价 USB 转串口模块在 921600 下误差可达 7%，比低速率更容易乱码。
