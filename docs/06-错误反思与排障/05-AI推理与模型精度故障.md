# 6.5 AI 推理与模型精度故障

## 本章解决什么

模型这一层的问题有个特点：**同一个报错可能来自四个完全不同的环节**——导出 ONNX 时改错了结构、量化时校准数据不对、上板时代码与模型不匹配、或者干脆是 API 版本不兼容。

本章按「模型生命周期」排列故障：转换期（`hb_mapper`）→ 上板期（TROS / Python 推理）→ 精度期（能跑但结果不对）→ 性能期（跑得慢）。每个条目都尽量给出**「先切一刀分出是哪一段」**的方法，因为在这一层盲试参数的代价极高（一轮量化要几十分钟）。

**版本红线先记住**：RDKOS V3.5.0 起，Python 算法推理统一改为 `hbm_runtime` 接口；3.5.0 之前是 `pyeasy_dnn` / `hobot_dnn`，中间还有一段用 `bpu_infer_lib` 的写法。三者不兼容，照错版本的文档写代码会全线报错。

## 6.5.1 先定位卡在哪一段

| 段 | 判据 | 典型报错前缀 |
| --- | --- | --- |
| 导出 | ONNX 能在 PC 上正常推理吗 | 改模型结构引入的错误 |
| 验证 | `01_check.sh` 通过了吗 | `ERROR The shape of model input...`、`Unsupported op` |
| 量化 | `02_preprocess.sh` / `03_build.sh` 走到哪 | `load cal data for input...`、`hbdk-cc compile ... failed` |
| 上板加载 | 模型能 load 吗 | `Incompatible Platform!!`、`hb_bpu_core_set_fc_prio failed` |
| 上板推理 | 节点跑起来了吗 | `process has died`、`Inlvaid parser: 0` |
| 精度 | 数字对不对 | 检测框乱飞 / 全无 / 置信度无意义 |
| 性能 | 帧率达不达标 | 算子回退 CPU、子图过多 |

## 6.5.2 故障条目

### 6.5.2.1 bpu_infer_lib 报 Incompatible Platform!!，模型加载成功但推理必失败

### 现象

```
[BPU_PLAT]BPU Platform Version(1.3.6)!
[HBRT] set log level as 0. version = 3.15.55.0
[DNN] Runtime version = 1.24.5_(3.15.55 HBRT)
...
------------ Done Load Model ----------------
load: True
...
[BPU_PLAT]Make sure inst Suport (X5) Platform!!
[BPU_PLAT]Incompatible Platform!!
[BPU_PLAT]FC Parse error!
[BPU_PLAT]Calloc fc space failed!
[BPU_PLAT]core mask[0x1] write fc to hw failed[-2]!!
[E][DNN][funccall_handle.cpp:141][Schedule](2026-04-21,21:44:10.779.322) hb_bpu_core_set_fc_prio failed! error code: -2
forward ret: None
```

> 来源：社区帖 34823（https://forum.d-robotics.cc/t/topic/34823）

### 根因

关键在于 **`load: True` 而 `forward` 失败**：模型文件能被解析、能读出输入输出张量，但 BPU 在执行阶段拒绝了它。

官方回复直接点名根因：

> 由于 bpu_infer_lib 已停止维护，新模型及推理流程全面迁移至 hbm_runtime 库，请更新 rdk 系统版本到 3.5.0 以上

用户的系统版本是 `RDK OS Version` 3.0.0。也就是说：**3.0.0 的运行时库不认识新工具链产出的 `.bin`**，加载阶段只做结构解析（所以通过），执行阶段才发现平台的 FC（function call）描述对不上，于是 `Incompatible Platform!!`。

这解释了为什么用户「前后又重新量化了一次模型，还是报同样的错」——重量化不解决问题，因为瓶颈在**板端运行时版本**，不在模型。

### 处置

先确认版本：

```bash
sudo rdkos_info
cat /etc/version
```

若低于 3.5.0，按官方给的路径升级：

```bash
sudo apt update
sudo apt upgrade
sudo reboot
sudo rdkos_info
```

升级后把代码从 `bpu_infer_lib` 迁到 `hbm_runtime`：

```python
# RDKOS >= 3.5.0 的写法（示意，具体以对应版本文档为准）
from hbm_runtime import HBM
# RDKOS <  3.5.0 的旧写法（已停止维护）
# from bpu_infer_lib import Infer
```

### 预防

**版本三件套必须对齐：工具链（OpenExplorer / hb_mapper）版本 = 板端运行时（libdnn / HBRT）版本 = 文档版本。** 三者错一个就会出现这类「加载成功、执行失败」的诡异现象。

板端运行时版本可以从日志第一屏读到：

```
[HBRT] set log level as 0. version = 3.15.55.0
[DNN] Runtime version = 1.24.5_(3.15.55 HBRT)
```

把它和转换时 `hb_mapper` 打印的版本对一下：

```
hbdk version 3.49.15
horizon_nn version 1.1.0
hb_mapper version 1.24.3
```

对不上就说明版本错配。

### 6.5.2.2 模型输出 bbox 分支变成 int32，TROS 报 Inlvaid parser: 0

### 现象

模型信息打印出来是这样：

```
[example-1] [output]
[example-1] - (0) Layout: NHWC, Shape: [1, 80, 80, 5], Type: HB_DNN_TENSOR_TYPE_F32.
[example-1] - (1) Layout: NONE, Shape: [1, 80, 80, 64], Type: HB_DNN_TENSOR_TYPE_S32.
[example-1] - (2) Layout: NHWC, Shape: [1, 40, 40, 5], Type: HB_DNN_TENSOR_TYPE_F32.
[example-1] - (3) Layout: NONE, Shape: [1, 40, 40, 64], Type: HB_DNN_TENSOR_TYPE_S32.
[example-1] - (4) Layout: NHWC, Shape: [1, 20, 20, 5], Type: HB_DNN_TENSOR_TYPE_F32.
[example-1] - (5) Layout: NONE, Shape: [1, 20, 20, 64], Type: HB_DNN_TENSOR_TYPE_S32.
```

随后：

```
[example-1] [ERROR] [1776571665.384396239] [dnn_example_node]: Inlvaid parser: 0
```

（`Inlvaid` 是原始日志里的拼写，检索时按原样搜。）

> 来源：社区帖 34784（https://forum.d-robotics.cc/t/topic/34784）

### 根因

模型输出分成了两组：`Shape: [1, H, W, 5]` 的 F32（这是 cls 分支）和 `Shape: [1, H, W, 64]` 的 **S32 + `Layout: NONE`**（这是 bbox 分支）。

两个致命点：

1. **类型是 S32（int32）而不是 F32**。TROS 的 YOLOv8 parser 期望两个分支都是 F32 或都有量化参数（quanti type），拿到纯 int32 且没有 scale/zero_point 就没法反量化。
2. **`Layout: NONE`**。parser 靠 layout 判断张量维度顺序，NONE 意味着无法判断。

根因在导出脚本里：

```python
# 用户自己写的导出代码（问题所在）
bbox = (bbox * 255.0).to(torch.int32)   # ← 在 PyTorch 导出阶段就转成了 int32
```

官方诊断：

> 你的猜测 2 是正确的：在 export_yolo26_detect_bpu.py 中提前将 bbox 转换为 int32，导致 hb_mapper 无法识别这是需要量化的浮点输出，最终 quanti type 显示为 NONE。

> 关键错误点：ONNX 导出时不应手动转 int32 —— 量化应该在 hb_mapper 阶段完成，而不是在 PyTorch 导出时；输出顺序错误 —— TROS 的 YOLOv8 parser 期望先 cls 后 bbox（与你当前代码相反）

> 来源：社区帖 34784

也就是说这里同时踩了两个坑：**提前 int32 化**（破坏了量化链路）和**输出顺序反了**（cls/bbox 顺序与 parser 期望相反）。

### 处置

第一步，改导出脚本，**导出时保持 float32，不要手动 `.to(torch.int32)`**：

```python
def bpu_detect_forward(self, x):
    result = []
    for i in range(self.nl):
        cls = self.cv3[i](x[i]).permute(0, 2, 3, 1)   # 先 cls
        bbox = self.cv2[i](x[i]).permute(0, 2, 3, 1)  # 再 bbox
        result.append(cls)      # 顺序：先 cls
        result.append(bbox)     # 再 bbox
    return result
```

第二步，重新走一遍 `hb_mapper`，然后确认输出类型：

```bash
# 板端看模型信息
hrt_model_exec model_info --model_file cow5.bin
```

期望看到两个分支都是 `F32`，且 layout 是 `NHWC` 或 `NCHW`（不是 `NONE`）。

第三步，若确认是量化节点处理问题，用 `hb_model_modifier` 检查/补回量化节点（见 5.3）。

### 预防

**量化只在 `hb_mapper` 阶段做，不要在 PyTorch 导出时手工插入类型转换。** 导出脚本的唯一职责是「产出结构正确的 float ONNX」。任何 `to(torch.int32)`、手工 `* 255` 这类操作，都会破坏 hb_mapper 的量化推导。

另外：**输出顺序是硬约定**。TROS 的 YOLOv8 parser 期望「先 cls 后 bbox」，写反了即使类型对也会解析错。

### 6.5.2.3 删除 Dequantize 节点后，int32 累加器值无法还原成 logit

### 现象

用户的模型第三版做了这样的改动：

> 浮点模型 → hb_mapper INT8 量化 → hb_model_modifier 删除了所有 10 个 Dequantize 节点 → 输出纯 int32 累加器值

结果：

- 输出格式变成「10 路分离 int32，NCHW 布局」；
- 值域异常：`cls 约 [-300000, -8000]`；
- 直接 sigmoid：极端负值 → sigmoid≈0 被过滤；接近 0 的值 → sigmoid≈0.5 成噪声；
- `CONF_THRES` 从 0.25 提到 0.50 才能勉强过滤噪声；
- **Scale 乘回去也不行**：「scale 值是对的（与日志匹配），但乘完后值在 [-60, -1.6]，sigmoid 全 0，一个都检不出」。

> 来源：社区帖 35445（https://forum.d-robotics.cc/t/topic/35445）

### 根因

删掉了 Dequantize 节点，就删掉了**反量化所需的 scale 和 zero_point**：

> 删除 Dequantize 后，量化参数（scale/zero_point）丢失，int32 值无法正确还原为 logit。

> 来源：社区帖 35445

这是整章最值得记住的一条机制：**量化模型的输出不是「数字」，而是「数字 + 怎么解释这个数字」**。Dequantize 节点承载的就是后半部分。删了它：

- 硬件仍然吐出 int32 累加器值（它们是「定点数」，隐含 scale 和 zero_point）；
- 但软件侧不知道这个 scale/zero_point，只能当成裸整数；
- 用户「手动乘 scale」时乘的是**日志里打印的 scale**，而那个 scale 未必是累加器到 logit 的那一层——于是乘完仍然全负。

用户的困境本质是：**想用「治标」（调 CONF_THRES）换性能，代价是置信度失去物理意义**。

> 方案 A 是"治标不治本"：调高 CONF_THRES 只能过滤噪声，但置信度失去物理意义，且无法解决值域偏移的根本问题

### 处置

**正确地保留 Dequantize**：量化后不要跑 `hb_model_modifier` 删节点，让 BPU 在推理时自动反量化，输出正常的 float32 logit。

```bash
# 量化流程正常走完即可，不要额外删除 Dequantize
bash 03_build.sh
```

若手头只有已经删掉节点的模型，正确做法是**重新导出并重新量化**，而不是继续在 int32 值域上试参数。

对照检查模型输出类型：

```bash
hrt_model_exec model_info --model_file yolov5_best_quant.bin
```

期望输出类型是 `F32`；若仍是 `S32`，说明 Dequantize 缺失。

### 预防

- **性能问题不要用删除量化节点来解决**。要提速，走「算子是否都在 BPU」「子图数量」「`core_num`」「`optimize_level`」这几条正规路径（见 5.6）。
- 量化参数（scale/zero_point）是模型的一部分，任何「删节点」的动作都会破坏它。
- 保留一份未删节点的基线模型，用于 A/B 对比。

### 6.5.2.4 hb_mapper 报 Unsupported datatype settings for march bayes: int32

### 现象

```
2026-04-19 11:27:55,267 ERROR *** ERROR-OCCUR-DURING {horizon_nn.build_onnx} ***, error message: Unsupported datatype settings for march bayes: int32:326,345,364
```

> 来源：社区帖 34784（https://forum.d-robotics.cc/t/topic/34784）

### 根因

`march bayes` 是 RDK X5 的 BPU 架构代号。报错说：**该架构不支持这些节点输出 int32**。后面那串 `326,345,364` 是 ONNX 的节点编号。

触发原因与本帖的 5.2 同源——导出时把 bbox 分支强行转成了 int32。hb_mapper 在 build 阶段发现这些节点的输出类型是 int32，而 bayes 架构的 BPU 输出只支持有限的几种类型（F32 / int8 等），于是直接拒绝。

注意这条报错是**在 `build_onnx` 阶段**，比 5.2 的 parser 报错更早——也就是说同一个错误根因，会在两个不同阶段各报一次。

### 处置

和 5.2 一样，改导出脚本去掉手工 int32 转换后重新导出。验证方式：

```bash
# 用 netron 或 python 查看 onnx 输出类型
python3 -c "
import onnx
m = onnx.load('model.onnx')
for o in m.graph.output:
    print(o.name, o.type.tensor_type.elem_type)
"
# elem_type 1 = float32, 6 = int32
```

三个输出都应该是 `1`（float32）。

### 预防

**导出 ONNX 后、跑 hb_mapper 之前，先检查输出类型**。这一步能在几秒钟内发现类型问题，省掉几十分钟的无效量化。

### 6.5.2.5 检测框数量异常多 / 周期性排列 / 整体偏移 / 全挤在左上角

### 现象

官方的四类精度异常描述：

- 检测结果出现**数量非常多且不规则的检测框**；
- 检测结果出现**有周期性排列规律的异常检测框**；
- 检测框的**位置出现整体偏移**；
- 检测框都**异常地聚集在图像的左上角**。

> 来源：官方文档 FAQ/toolchain Q8、Q9、Q10、Q11（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）

### 根因

四种现象，四个不同的根因，官方给的解释很清晰：

**（1）框多且不规则**：ONNX 输出头结构与板端后处理不匹配。高版本 YOLOv5 导出的 ONNX 可能已经把解码（decode）部分包含进去了，或者没有把大/中/小三个特征图分开输出。RDK BPU 要求输出是**原始特征图，且三个特征图是独立输出节点**。

**（2）周期性排列的异常框**：输出维度与后处理不匹配。某些版本的 ONNX 输出头是 5 维（`[batch, num_anchors, grid_h, grid_w, (x,y,w,h,conf+classes)]`），工具链编译时可能截断某个维度，后处理再按错的维度解码，就出现周期性规律。

**（3）整体偏移**：两个可能——渲染尺寸与原始图像尺寸不匹配（后处理算出的坐标是相对 640x640 的，直接画在别的尺寸画布上就偏了），或者 anchors 与训练时不一致。

**（4）全挤在左上角**：3.0.0 及以上版本示例使用 CPython 封装的后处理库，如果类别数等关键参数没有正确传递，解码逻辑会整体出错。

### 处置

按现象对号：

```bash
# 先拿到模型的真实输出结构
hrt_model_exec model_info --model_file your.bin
```

**对（1）**：修改导出脚本，移除末尾的检测头（decode、NMS），把 P3/P4/P5 三个特征图作为独立输出。不要错误地在输出后加 Sigmoid，除非后处理明确需要。

**对（2）**：把输出转成明确的四维张量，推荐 NHWC：

```
[batch, grid_h, grid_w, num_anchors*(5+num_classes)]
```

后处理按这个布局解析。

**对（3）**：渲染前把坐标映射回原始图像尺寸：

```python
scale_x = orig_w / model_w
scale_y = orig_h / model_h
x1, x2 = x1 * scale_x, x2 * scale_x
y1, y2 = y1 * scale_y, y2 * scale_y
```

若预处理做了 letterbox padding，反算时要去掉 padding 偏移。

**对（4）**：换成 RDK Model Zoo 的后处理实现，它把类别数、输入分辨率、anchors、阈值都作为构造参数。

> 官方明确推荐：对于 YOLOv5 等模型的验证和部署，强烈建议参考或直接使用 [RDK Model Zoo](https://github.com/D-Robotics/rdk_model_zoo) 中提供的后处理代码。

### 预防

**四个现象对应四个根因表，先查表再动手**。这四类问题最容易犯的错是「看到框不对就去调阈值」——阈值只影响过滤，不会修正坐标、不会修正维度顺序、更不会修正 anchors。

### 6.5.2.6 所有算子都在 BPU，模型也不复杂，但实测不到 2Hz

### 现象

用户标题即问题：「所有算子都是运行在BPU上，模型也不是很复杂，但是实测出来的模型性能不到2hz」。模型是 LRASPP 分割网络，输入 `1x5x360x640`（5 通道 featuremap）。

> 来源：社区帖 34885（https://forum.d-robotics.cc/t/topic/34885）

### 根因

用户的前提「所有算子都在 BPU」本身需要验证——**算子分布不等于子图数量**。BPU 上的算子如果被切成了很多个子图（每个子图之间都要走 DDR 搬运数据），性能会塌方式下降。

这类模型的典型问题：

1. **CPU 算子把图切断**。`Less`、`Not`、`Cast` 这类控制流/布尔算子落在 CPU 上，每个 CPU 算子都会在 BPU 图里切一刀，两侧都要做一次 DDR→BPU→DDR 的往返。
2. **非四维输入或特殊输入类型**。`input_type_train: featuremap` + 5 通道，这类输入本来就走 DDR，没有走 pyramid。
3. **算子 shape 超限回退 CPU**。官方 FAQ 写明：算子由于 shape（C×H×W）超过 8192 会被回退到 CPU。

官方 FAQ 也提醒过一条容易被忽略的话：

> 若 CPU 算子带来的性能损耗您可接受，则无需关注该信息；若性能不能达到您的要求，您可以根据我们提供的算子支持列表中的内容将该 op 修改至 BPU 可支持的范围。

### 处置

第一步，看子图数量（这是最快的一刀）：

```bash
hrt_model_exec model_info --model_file lraspp_performance_2.bin
```

子图数量远大于 1，就说明图被切碎了。

第二步，开 profiling 看时间花在哪：

```bash
export HB_PROFILER=1
hrt_model_exec perf --model_file lraspp_performance_2.bin --loop_num 100
cat profiler_*.log | grep -E "CPU|BPU|DDR"
```

第三步，把能搬的 CPU 算子搬到 BPU：

```yaml
model_parameters:
  node_info: {
    "Resize_220": {'ON': 'BPU', 'InputType': 'int8', 'OutputType': 'int8'},
    "Less_245": {'ON': 'BPU', 'InputType': 'int8', 'OutputType': 'int8'},
    "Not_246": {'ON': 'BPU', 'InputType': 'int8', 'OutputType': 'int8'},
    "Cast_247": {'ON': 'BPU', 'InputType': 'int8', 'OutputType': 'int8'}
  }
```

这一步需要逐个验证这些算子在 BPU 上是否真的支持；不支持时 hb_mapper 会报错。

第四步，编译器侧调优：

```yaml
compiler_parameters:
  compile_mode: 'latency'
  core_num: 1        # X5 仅支持 1
  optimize_level: 'O3'
  debug: False
  input_source: {'input': 'ddr'}
```

第五步，确认 CPU 没在降频拖后腿：

```bash
echo performance | sudo tee /sys/devices/system/cpu/cpufreq/policy0/scaling_governor
cat /sys/devices/system/cpu/cpufreq/policy0/scaling_cur_freq
```

### 预防

**「算子都在 BPU」不等于「性能好」**。评价指标应该是子图数量与 DDR 搬运量，不是算子分布。量化完成后立刻跑一次 `hrt_model_exec model_info` 看子图数，比跑完整应用再怀疑人生要高效得多。

### 6.5.2.7 换用自己的模型跑官方 demo，Segmentation fault

### 现象

用户描述：运行 `/app/pydev_demo/07_yolov5_sample`，把自己训练的模型替换掉示例自带的 `.bin` 后报 `Segmentation fault (段错误)`。

> 来源：官方文档 FAQ/toolchain Q12（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）

### 根因

官方解释得非常直接：

> 板载的官方示例程序（如 07_yolov5_sample）通常是针对其自带的预转换好的 .bin 模型进行适配和测试的。这个示例的预处理、模型加载、BPU 推理调用以及后处理逻辑，都是围绕那个特定的自带模型设计的。

> 如果您用自己的（可能结构、输入输出、后处理逻辑都不同的）YOLOv5 模型替换了示例中的 .bin 文件，而没有相应地修改示例代码中的预处理、后处理或模型参数部分，就非常容易因为数据格式不匹配、内存访问越界等原因导致 Segmentation fault。

关键机制：段错误的本质是**访问了不属于自己的内存**。当后处理按「输出张量有 3 个」去索引，而实际模型有 6 个输出时，越界读就会崩；当输入 buffer 按 512x512 分配而模型要 640x640 时，写越界也会崩。

### 处置

**不要只替换 `.bin`。** 两个正确做法：

**做法 A（推荐）**：用 RDK Model Zoo 里对应模型的完整示例，它把预处理/后处理与模型绑定好。

**做法 B**：自己核对三件事：

```bash
# 1. 看自己模型的真实输入输出
hrt_model_exec model_info --model_file your_model.bin

# 2. 逐项对比示例代码里写死的常量
#    - 输入尺寸（示例里可能是 512x512）
#    - 输入 layout（NCHW / NHWC）
#    - 输出张量数量与顺序
#    - 类别数 num_classes

# 3. 预处理必须完全一致
#    - resize 方式（bilinear / letterbox）
#    - 归一化参数（mean / std）
#    - 颜色空间（BGR / RGB）
```

### 预防

**「替换 bin 就能用」是一个长期的误解**。判断一个示例能不能直接换模型，看它的后处理里有没有写死的常量——有，就必须改代码。

### 6.5.2.8 模型转换报 can't reshape xxx in (84,84,3,85)

### 现象

```
can't reshape xxx in (84,84,3,85)
```

> 来源：官方文档 FAQ/toolchain Q7

### 根因

后处理代码里预设的类别数（`num_classes`）与实际模型不一致。

`85` 的含义是 `4 + 1 + 80`：`(x, y, w, h, confidence + num_classes)`。COCO 80 类时是 85；如果训练的是自定义 10 类，应该是 `4 + 1 + 10 = 15`。

也就是说：**后处理以为你是 COCO 80 类，实际你只有 10 类**，维度对不上，reshape 直接失败。

### 处置

找到后处理代码里定义类别数的位置，改成实际值：

```python
# 常见写法
NUM_CLASSES = 10          # 原来是 80
OUT_CHANNELS = 5 + NUM_CLASSES   # 15，原来是 85
```

### 预防

训练完模型后把三个数字写在一张便签上：**输入尺寸、类别数、anchors**。这三个是后处理必须匹配的常量，任何一项不对都会出问题。

### 6.5.2.9 模型转换报 opset version 不支持

### 现象

```
ERROR [ONNXRuntimeError] : 9 : NOT_IMPLEMENTED : could not find a implementation for the node of `{op_name}`:{op_type}(opset)
ERROR The opset version of the onnx model is n, only model with opset_version 10/11 is supported
```

> 来源：官方文档 FAQ/toolchain（https://developer.d-robotics.cc/rdk_x_doc/FAQ/toolchain）

### 根因

工具链只支持 `opset_version` 10 或 11。PyTorch 新版 `torch.onnx.export` 默认可能导出 opset 13/17，超出支持范围。

### 处置

导出时显式指定：

```python
torch.onnx.export(
    model, dummy_input, "model.onnx",
    opset_version=11,     # 必须显式指定 10 或 11
    input_names=["images"],
    output_names=["output0"],
)
```

### 预防

把 `opset_version=11` 写进导出脚本模板，不要依赖默认值。

### 6.5.2.10 模型转换报 There is no node can execute on BPU in this model

### 现象

```
ERROR There is no node can execute on BPU in this model, please make sure the model has at least one conv node which is supported by BPU.
```

> 来源：官方文档 FAQ/toolchain

### 根因

模型里没有任何可量化到 BPU 的节点。最常见的原因是：模型里没有卷积（比如纯 Transformer、纯全连接网络），或者所有卷积的 shape/属性都不在 BPU 支持范围内。

官方给出的最低要求是：

> 请您确保 onnx 模型的有效性，且模型中至少使用了一个 conv

### 处置

- 若是纯 MLP/Transformer，需要引入至少一个 BPU 可支持的 conv，或接受全 CPU 运行（性能会很差）；
- 若模型有 conv 但仍然报这个错，检查这些 conv 的输入维度是否为四维、shape 是否超限（C×H×W > 8192 会回退 CPU）；
- 把模型和 `.log` 一起提交给官方分析。

### 预防

转换前先确认模型架构里有标准卷积。**纯非卷积网络在 RDK X5 上没有加速价值**，这一点要在选型阶段就判断，不要等转换失败才发现。

### 6.5.2.11 运行官方 demo 内存相关报错（部署 yolov8 时）

### 现象

用户描述：「rdkx5部署yolov8时出现以下报错（跟我bin文件无关）」，并补充「我将摄像头的帧数改成了15fps还是会报错，摄像头读取数据改成640x480也会报错」，附了截图与代码。

> 来源：社区帖 29125（https://forum.d-robotics.cc/t/topic/29125）

### 根因

社区帖中为截图，报错文本未以文字形式给出，因此无法原样引用。但从「改帧率、改分辨率都无效」这一现象可以推断：

如果降低数据产生速率（15fps）和降低单帧体积（640x480）都不能缓解，说明**瓶颈不在数据流入速率，而在推理侧的某个固定开销**。常见两类：

1. **ION 内存不足**。BPU 推理需要连续的 ION 保留内存，多个模型/多路输入同时申请时会被耗尽。`rdkos_info` 会打印 `[ION Memory Size]`，可用于核对。
2. **多次重复申请未释放**。在循环里反复 `load model` 而不复用，内存会持续增长直到 OOM。

### 处置

先看内存与 ION 余量：

```bash
sudo rdkos_info | grep -iE "Memory|ION"
free -h
```

再确认模型只加载一次（不要放在循环里）：

```python
# 错误：在循环里反复加载
# while True:
#     models = dnn.load('model.bin')

# 正确：加载一次，循环只做推理
models = dnn.load('model.bin')
while True:
    outputs = models[0].forward(input_tensor)
```

若确认是内存压力，加 Swap 只能缓解系统内存，**缓解不了 ION**——ION 是预留的连续物理内存，需要在设备树/启动参数层面调整。

### 预防

**排查这类问题要「一次只改一个变量」**：先只降分辨率、再只降帧率、再只改模型。用户同时改了两个都没效果，反而让「到底哪个变量相关」变得不清楚。

另外，遇到截图报错时，**请把文本贴出来**——截图无法被检索，也无法被复制进命令，是求助效率最低的形式。

### 6.5.2.12 RDKOS 3.4.1 升到 3.5.0 后老代码跑不起来

### 现象

用户提问：「系统版本从3.4.1更新到3.5.0会不会出现不兼容的情况，会不会导致使用之前的接口开发的应用无法运行」。

> 来源：社区帖 35476（https://forum.d-robotics.cc/t/topic/35476）

### 根因

会有影响，且是**设计上的破坏性变更**，不是 bug。3.5.0 的核心变更：

- 算法推理接口从 `hobot_dnn` / `bpu_infer_lib` 迁移到 `hbm_runtime`；
- `/app/pydev_demo/` 下所有示例基于新接口**全量重写**；
- 底层 SDK 同步更新。

官方 Release Note 原文：

> 自 3.5.0 版本起，Python 算法推理、目标检测、语义分段等模块统一升级为 hbm_runtime 接口。该接口基于 pybind11 实现，提供对 libdnn C++ 库的高效访问，支持高性能模型加载与神经网络推理。

> 基于新版 hbm_runtime 接口，对 /app/pydev_demo/ 下所有示例完成全量重写，确保接口统一、性能最优、使用更简洁。

> 来源：官方文档 Release_Note（https://developer.d-robotics.cc/rdk_x_doc/Release_Note/release_note）

### 处置

接口对照表：

| 版本区间 | Python 推理接口 | 状态 |
| --- | --- | --- |
| < 3.5.0（3.0.0 / 3.2.3 / 3.4.1） | `pyeasy_dnn` / `hobot_dnn` | 可用，但示例与文档停留在旧版 |
| 过渡期 | `bpu_infer_lib` | 已停止维护 |
| ≥ 3.5.0 | `hbm_runtime` | 当前唯一支持路径 |

迁移步骤：

```bash
# 1. 确认版本
cat /etc/version

# 2. 备份现有应用
cp -r ~/my_app ~/my_app.bak

# 3. 参考新版示例重写推理部分
ls /app/pydev_demo/
```

### 预防

**升级前先读 Release Note 的「不兼容变更」章节**。跨大版本升级（3.4→3.5）在嵌入式平台上从来不是「无感」的，尤其涉及推理接口时。

生产设备锁版本，不要随手 `apt upgrade`。

## 三、常见误区

1. **「重新量化一次就好了」**。若根因在板端运行时版本（如 5.1），重量化一百次也没用。先对齐版本三件套。
2. **「调 CONF_THRES 能解决精度问题」**。阈值只影响过滤。删了 Dequantize 之后调阈值，代价是置信度失去物理意义——治标不治本。
3. **「所有算子都在 BPU 所以性能应该好」**。要看子图数量与 DDR 搬运量，不是算子分布。
4. **「替换 .bin 就能复用官方示例」**。预处理、后处理、张量数量只要有一处不匹配就段错误。
5. **「导出时手工转 int32 能控制类型」**。这恰好会破坏 hb_mapper 的量化推导，导致 `quanti type: NONE` 和 `Unsupported datatype settings`。
