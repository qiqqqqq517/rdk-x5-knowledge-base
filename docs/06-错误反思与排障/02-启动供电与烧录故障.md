# 启动供电与烧录故障

## 本章解决什么

「上电没反应」「一直重启」「烧录提示成功但起不来」——这三类问题占了社区启动类求助的绝大多数，而它们的根因分布极广：可能是电源电流不够，可能是 SD 卡文件系统坏了，可能是 NAND 里的 Miniboot 与芯片型号不匹配，也可能真的就是板子坏了。

本章按**启动链的先后**排列故障，每一条都给出判断「走没走过这一层」的具体证据。核心方法是：**先接串口，看启动日志停在哪个阶段**，再对号入座。不带证据的重刷，只会把可诊断状态刷成不可诊断状态。

## 一、先建立启动链的心智模型

RDK X5 的启动是一条固化在硬件里的链，每一环失败时的日志形态完全不同：

| 阶段 | 由什么执行 | 成功标志 | 失败时的典型输出 |
| --- | --- | --- | --- |
| BootROM | 芯片内部固化 | `SNOTICE: Welcome to Horizon X5 ASIC BOOTROM - V4.1` | 完全无输出 |
| BL1 | Trusted Firmware | `NOTICE: BL1: Booting BL2` | `ERROR: plat_error_handler -2` |
| BL2 | Trusted Firmware | `NOTICE: BL2: ...` → `NOTICE: ddr ready` | `ERROR: boot mode 5 main bl2 fail and switch to bakeup1…` |
| U-Boot（Miniboot） | 板载 NAND | `U-Boot 2022.10+ (日期)` → `Hit key to stop autoboot in 1s` | 停在 `hobot>` 提示符 |
| Kernel | SD 卡/eMMC 上的 `/boot/Image` | `Starting kernel …` → `Booting Linux on physical CPU 0x0000000000` | `Kernel panic - not syncing: VFS: ...` |
| rootfs | SD 卡第二分区 | 登录提示符 `ubuntu login:` | `Unable to mount root fs` |

**这张表就是本章的目录。** 你的串口日志打到哪一行停住，问题就在那一行的下一层。

## 二、故障条目

### 2.1 上电后间歇性进不了 Ubuntu，运行一段时间卡死、网络断开

### 现象

```
[ 15.233738] Unable to handle kernel paging request at virtual address 0000000000100108
[ 15.287630] Internal error: Oops: 0000000096000004 [ #1 ] PREEMPT SMP
[ 15.390509] pc : update_load_avg+0x7c/0x5e0
```

用户原始描述：「上电后，有时候能进入到Ubuntu界面，然后过一段时间就会卡住，然后手机热点连接也会断掉，大部分时候重新插拔电源会重新连上网络但是进不去ubuntu界面」

> 来源：社区帖 35112（https://forum.d-robotics.cc/t/topic/35112）

### 根因

这一条的关键判据不是报错内容，而是**故障点的漂移**。同一块板子、同一个镜像，崩溃位置每次都不一样——帖子里前后两次日志，一次崩在调度器 `update_load_avg`，一次崩在设备驱动探测链 `__device_attach_driver → bus_for_each_drv → deferred_probe_work_func`。

软件 bug 引起的崩溃点通常是**固定**的（同一行、同一函数、同一调用栈）。崩溃点随机漂移，说明是**内存/供电层面的不稳定**，代码本身没变，是给它供电/供数据的条件在变。这类故障会伪装成网络问题（网卡掉线）、存储问题（文件系统报错）、驱动问题（`vs-dc ... Failed to get aux devices`、`aicbsp: sdio_err: : bus down`），看起来像三个不同的 bug。

供电为什么会导致内核 panic：电压跌落时 DDR 的读写时序裕量被吃掉，某些位会翻转，于是内核读到的是被破坏的指针/链表——最终必然表现为 `Unable to handle kernel paging request` 这类「随机地址访问失败」。

**分歧点如实记录**：官方 FAQ 只对 RDK X3 给出了明确电源规格（至少 5V/2A，建议 5V/3A）；对 X5，社区帖里的官方助手回复给出的要求是「必须使用 5V/5A（最低 5V/3A）Type-C 电源适配器，不能用电脑 USB 口供电（仅 0.5A-0.9A），不能用 12V 电源」。前者是官方文档口径，后者是社区回复口径，两者对 X5 的电流要求不完全一致——**取更保守的 5V/5A** 更安全。

> 来源：官方文档 FAQ/hardware_and_system Q8「RDK X3 对供电有什么具体要求？」；社区帖 35112

### 处置

第一步，把外部负载全部摘掉，做最小系统测试（**不需要 sudo**）：

```bash
# 登录后看 USB 设备负载
lsusb

# 关 WiFi、只用网线
sudo nmcli radio wifi off
```

物理上拔掉所有非必要 USB 设备（摄像头、雷达、键盘、USB Hub），只留电源 + 网线 + 串口，用 5V/5A 电源重测。

第二步，抓死机前的日志。**卡死并重新上电后立刻执行**（不需要 sudo，`-b -1` 需要读 journal）：

```bash
journalctl -b -1 -n 100 --no-pager
dmesg | grep -iE "error|fail|watchdog|reset|power" --color
journalctl -b -1 | grep -iE "watchdog|eth0|regulator" --color
```

重点看三件事：有没有 watchdog 超时复位、`eth0` 有没有 link down、有没有 OOM 或电压异常。

第三步，排除看门狗与节能策略的干扰（**需要 sudo**）：

```bash
sudo systemctl stop watchdog
sudo systemctl disable watchdog
sudo systemctl mask sleep.target suspend.target hibernate.target hybrid-sleep.target
```

第四步，查温度（**需要 sudo**）：

```bash
sudo hrut_somstatus
```

### 预防

**先用「最小系统 + 足额电源」跑 30 分钟**，跑得住再逐步加外设。加一个外设观察一次，这样能精确定位是哪个外设把电流吃穿了。

判断口诀：**崩溃点漂移 = 供电/内存不稳；崩溃点固定 = 软件 bug。** 这一条能省掉大量「反复重刷镜像」的时间。

### 2.2 上电后一直重启，日志末尾是 VFS 挂不上根文件系统

### 现象

```
[ 14.589720] Kernel panic - not syncing: VFS: Unable to mount root fs on unknown-block(179,2)
[ 14.598171] SMP: stopping secondary CPUs
[ 14.621176] Rebooting in 5 seconds..
```

紧接着又是 `SNOTICE: Welcome to Horizon X5 ASIC BOOTROM - V4.1`，如此循环。

> 来源：社区帖 31743（https://forum.d-robotics.cc/t/topic/31743）

### 根因

`unknown-block(179,2)` 里的 `179` 是 MMC 块设备主设备号，`2` 是分区号——即系统在尝试从 `mmcblk1p2`（SD 卡的第二个分区）挂载根文件系统时失败。启动链本身是走通的（BL1/BL2/U-Boot 全部通过，内核也起来了），**坏的是最后一环：rootfs 读不出来**。

三种原因：

1. SD 卡第二分区的 ext4 文件系统损坏（拔卡未卸载、写盘过程中断电）；
2. SD 卡本身出现坏块或接触不良，读 I/O 超时；
3. 镜像烧录不完整，分区表对但数据不全。

同一份日志里能看到 `mmcblk1` 与 `mmcblk1p1`、`mmcblk1p2` 都被枚举出来了（`b300 61071360 mmcblk1`、`b302 60805120 mmcblk1p2`），说明**卡被识别了**，问题在分区内容而非卡槽物理接触。这个细节很重要——它把「换卡槽/清金手指」这条路径排除了。

### 处置

先尝试在能读卡的环境里检查文件系统（把卡插到 Linux 主机上，**需要 sudo**）：

```bash
sudo fsck.ext4 -f /dev/sdX2
```

板子本身起不来时这条做不了，所以实际处置就是**重新烧录**：

- 用 Rufus 或 balenaEtcher 重新烧录**最新**官方镜像；
- 烧录前确认镜像是从压缩包**完全解压**出来的 `.img`，不是压缩包本身；
- 烧完先在 PC 上确认分区结构正常，再插板。

若重刷后仍在同一位置 panic，换一张卡——优先选 Class 10 / U1 以上的品牌卡（SanDisk、Samsung、Kingston）。

> 来源：官方文档 FAQ/hardware_and_system Q29「镜像烧录失败的常见原因有哪些？」、Q9「RDK X3 是否有推荐的 SD 卡品牌或规格？」

### 预防

- 断电前先 `sudo shutdown -h now`，不要直接拔电源——这是 ext4 损坏最常见的原因；
- 烧录完成后 Windows 可能弹出「是否需要格式化」，**必须选「否」**，格式化会破坏刚写入的 Linux 分区；
- 卡的使用寿命有限，反复烧录的旧卡优先怀疑。

### 2.3 上电后一直重启，日志是 main bl2 fail（换了 NAND 芯片）

### 现象

```
NOTICE: Enter SPI NAND-FLASH Mode…
NOTICE: Nand PAGE_SIZE_4K
NOTICE: Nand is_dummy = true
NOTICE: Nand CLK_12M
NOTICE: SPI baudrate is set to 12000000Hz
NOTICE: Nand reset
NOTICE: reg_status should = 0x18
NOTICE: SPI Nand flash buffer mode set PASS
NOTICE: Manufacturer ID 0xc8 Device ID 0x82c8
NOTICE: Enter media_source_select process(5).
NOTICE: SPI Nand flash set quad PASS
ERROR: boot mode 5 main bl2 fail and switch to bakeup1…
NOTICE: Enter media_source_select process(5).
ERROR: boot mode 5 bakeup1 bl2 fail and switch to bakeup2…
NOTICE: Enter media_source_select process(5).
ERROR: boot mode 5 bakeup2 bl2 fail and switch to bakeup3…
NOTICE: Enter media_source_select process(5).
ERROR: boot mode 5 bakeup3 bl2 fail and cold reset…
ERROR: plat_error_handler -2
```

（`bakeup` 是原始日志里的拼写，非笔误，检索时按原样搜。）

> 来源：社区帖 35730（https://forum.d-robotics.cc/t/topic/35730）

### 根因

这条日志的信息密度极高，逐行读：

- `Manufacturer ID 0xc8 Device ID 0x82c8` —— NAND 被**正确识别**了，芯片在、SPI 通、ID 匹配；
- `Nand PAGE_SIZE_4K` —— 这颗芯片的页大小是 4K（对比标配 1Gb 芯片日志里是 `Nand PAGE_SIZE_2K`）；
- `main bl2 fail` → `bakeup1/2/3 bl2 fail` —— BL1 按**四个备份偏移**逐个去读 BL2，全部读不到有效内容；
- `plat_error_handler -2` —— 所有备份都失败，只能冷复位，于是形成重启循环。

根因是**布局不匹配**：官方 RDK Miniboot 的 NAND 布局（页/块 geometry、BL2 备份偏移、分区表）是按标配 1Gb 芯片生成的。换成 2Gb 的 GD5F2GM7REYIG 后，BL1 仍按旧偏移去读，读到的位置没有有效 BL2。**芯片是好的，烧录内容也是对的，只是「地址算错了」。**

判断依据可以直接对比两帖的日志：35112 与 31743 的标配板日志里是 `Nand PAGE_SIZE_2K`，本贴是 `PAGE_SIZE_4K`——**页大小变了，所有偏移量都必须重算**。

另有一条容易误判的连带错误：后续用 XBurn 烧录时报

```
Set storage type failed
```

以及 `img_files parameter validation failed`，根因是命令里写了 `--storage_type emmc`——板子是 X5 + 板载 NAND，介质类型必须与目标存储一致。**介质选错会导致后面所有文件校验连带失败，那不是镜像的问题。**

### 处置

**这不是改参数能解决的。** 社区给出的结论是：

> 最可能原因：官方 RDK miniboot 的 NAND 布局（页/块 geometry、BL2 备份偏移、分区表）是按标配 1Gb 芯片生成的，换成 2Gb 的 GD5F2GM7REYIG 后参数对不上，BL1 按旧偏移读不到有效 BL2，报的就是你日志里的 main bl2 fail。

需要按新芯片参数**重新生成 miniboot 和分区表**，属于私有硬件的板级 bring-up，官方没有公开的 2Gb 替换验证流程。

如果只是介质类型写错（`Set storage type failed`），按实际存储改回：

```bash
# XBurn 命令行示例：板载 NAND 就必须写 nand，不能写 emmc
--storage_type nand
```

XBurn 的串口 + USB fastboot 组合建议串口波特率填 `921600`。

**不要先做整片 NAND 擦除**——XBurn 烧写 Bootloader 时会按镜像配置覆盖所需区域，先整片擦除只会把目前还能用于恢复的内容清掉。

> 来源：社区帖 35730

### 预防

- 自换 NAND 前先对照两颗芯片 datasheet 确认 **page size / block size / dummy cycle** 三项，任何一项不同都要重算布局；
- 换芯片后不要沿用旧烧录包，必须用 SDK 重新生成 product 包；
- 保留原芯片的备份，便于对比。

### 2.4 绿灯常亮橙灯不亮、进不了桌面，串口日志有 DTOVERLAY 报错

### 现象

```
DTOVERLAY[error]: can’t load config file(/boot/config.txt)
```

用户描述：「rdk x5 绿灯一直亮 橙色灯不亮 换了内存卡可以 原来的内存卡能正常登录串口」

> 来源：社区帖 28400（https://forum.d-robotics.cc/t/topic/28400）

### 根因

`/boot/config.txt` 是设备树 overlay 的配置文件（对应 `srpi-config` 里的各类硬件功能开关）。它位于 **SD 卡的第一个分区（`/boot`）**，而不是根文件系统分区。

日志里 U-Boot 阶段已经出现过：

```
Found U-Boot script /boot/boot.scr
```

说明 `/boot` 分区**能被读到**，`boot.scr` 也在；但紧接着的 `DTOVERLAY` 读 `config.txt` 失败。这通常意味着该分区的文件系统有局部损坏，或 `config.txt` 被误删/截断。

关键判据是用户的补充：**换一张卡就正常，原卡还能串口登录**。这同时说明三件事——板子没问题、卡槽没问题、原卡的**根文件系统分区基本可用**，坏的是 `/boot` 分区里的这个文件。这是典型的「局部损坏」，不是「镜像全废」。

注意：这个报错在很多能正常进系统的板子上也会出现（属于 overlay 加载不到配置时的降级提示），**只有当它伴随启动失败时才值得追**。

### 处置

能从串口登录就说明系统进去了，直接在板上修（**需要 sudo**）：

```bash
# 确认 /boot 是否挂上、有没有 config.txt
ls -l /boot/config.txt
mount | grep /boot

# 若文件缺失，尝试从官方镜像对应位置恢复；或直接重建一个空配置
sudo touch /boot/config.txt
```

若 `/boot` 分区本身损坏（`ls` 报 I/O 错误），只能重刷。重刷前把用户数据备份出来（用另一张卡启动，挂载原卡的根分区拷数据）。

`config.txt` 的具体配置项（PWM、UART、I2C 等外设使能）见 [srpi-config 与 config.txt](../05-进阶驱动与系统/04-srpi-config与config.txt与Thermal频率管理.md)。

> 来源：社区帖 28400

### 预防

- 改 `config.txt` 前先 `sudo cp /boot/config.txt /boot/config.txt.bak`；
- 用 `srpi-config` 改配置，不要手写整份文件；
- 关机用 `sudo shutdown -h now`，避免 `/boot` 在写入中被断电。

### 2.5 烧录卡在 6%，串口也连不上

### 现象

社区帖中为截图，用户的文字描述是：「串口连不上，烧固件也烧不了，卡6%」，后续补充「6%要断电重启，正常烧录了」。

> 来源：社区帖 32853（https://forum.d-robotics.cc/t/topic/32853）

### 根因

「卡在 6%」是烧录工具在写入 Bootloader/Miniboot 阶段失败。此时：

- 板子还停在 BootROM/烧录模式，**Linux 没起来，所以串口不会有任何 shell 输出**——这是「串口连不上」的直接原因，不是串口坏了；
- 烧录停在低位百分比，通常是 USB 链路中断、线材质量差、或供电在写入瞬间跌落。

用户最后的处置是「断电重启」后重烧成功，说明这是一次**瞬态失败**而非硬件损坏。

### 处置

```bash
# 1. 关闭烧录工具，拔掉 USB 线
# 2. 板子完全断电（拔电源，等 10 秒）
# 3. 按住 BOOT 相关按键再上电，进入烧录模式
# 4. 换一根质量好的 USB 数据线（不是充电线）
# 5. 重新烧录
```

烧录用 Micro-USB 连接时注意：**RDK X5 的 Micro-USB 接口同时是 Debug UART 接口**，一根线要同时承担烧录与串口，线材质量要求更高。

### 预防

- 烧录阶段不要接其他外设，减少供电竞争；
- 用带屏蔽的短数据线，避免劣质线在大电流写入时压降过大；
- 烧录失败先断电重启再重试一次，**不要连续重试**——连续失败往往是同一个物理原因。

### 2.6 烧录工具提示成功，但上电不启动、HDMI 无信号、绿灯常亮

### 现象

「每次RDK Studio都提示系统烧录成功，但是我上电接HDMI口系统就是不启动！灯一直亮绿色!」

> 来源：社区帖 32282（https://forum.d-robotics.cc/t/topic/32282）

### 根因

「烧录成功」是**烧录工具自己的判定**，它只验证了「数据写完了」，不验证「写进去的东西能被板子引导」。所以这条提示不能当作成功证据。

社区官方人员的回复很直接：

> 推荐使用rufus烧录sd卡，RDK 手册中有提供下载，Balenatcher是容易失败

也就是说，同一张卡、同一个镜像，换 Rufus 就能成功——问题在**烧录工具与卡的组合**，不在板子。

> 来源：社区帖 32282

### 处置

换工具重烧：

1. 下载 Rufus（Windows）；
2. 选**完全解压后的 `.img`**，不是 `.zip`/`.gz`；
3. 以管理员权限运行；
4. 烧录过程中若 Windows 弹「需要格式化」，**选「否」**。

烧完后可选做完整性校验：

```bash
# 在 Linux 主机上核对首尾扇区是否有有效分区表
sudo fdisk -l /dev/sdX
```

### 预防

官方 FAQ 列出的烧录失败原因里，工具与环境类占了一半：烧录软件版本、USB 接口/驱动、操作系统权限（Windows 下需管理员）、杀毒软件干扰。**当「提示成功但不启动」时，第一反应应该是换工具，而不是怀疑板子。**

> 来源：官方文档 FAQ/hardware_and_system Q29

### 2.7 系统能烧进去但起不来 / 起来后 WiFi 等模块异常

### 现象

两类看似无关的现象，实际同源：

- 烧录完成后无法启动；
- 系统能启动，但 Wi-Fi 及其他模块不可用、某些软件功能无法加载。

> 来源：社区帖 30925（https://forum.d-robotics.cc/t/topic/30925）

### 根因

官方技术支持在帖中给出的机制说明：

> 在 RDK X5 平台中，Miniboot 固化在板载的 NAND Flash 中，启动后负责加载 SD 卡上的文件系统与核心组件。

> 在开发和使用过程中，大家使用的 SD 卡品牌、型号各不相同，这些 SD 卡在上电时序、启动方式等方面存在差异，导致系统在某些卡上存在兼容性问题。为了解决这一问题，我们对 Miniboot 引导程序进行了升级，从而显著提升了对主流 SD 卡的兼容性。

关键点：**Miniboot 不在 SD 卡上，在板载 NAND 里**。所以「重刷 SD 卡」并不会更新 Miniboot。一块 Miniboot 版本很旧的板子，换什么卡都可能起不来——而用户会误以为是「镜像问题」或「卡的问题」。

这也解释了为什么「系统起来后 Wi-Fi 异常」会和「起不来」归到同一类：Miniboot 负责早期初始化，它没把硬件带起来，后面所有模块都受影响。

### 处置

**情况 A：系统能进** —— 在线升级（**需要 sudo**，且需要联网）：

```bash
sudo rdk-miniboot-update
```

先确认会用哪个镜像：

```bash
rdk-miniboot-update -l
```

指定文件升级：

```bash
sudo rdk-miniboot-update -f /userdata/miniboot.img
```

也可以用 `srpi-config` 走菜单：`1 System Options` → `S7 Update MiniBoot`。

**情况 B：系统进不去** —— 手动烧录 Miniboot，需要 Windows + XBurn + Micro-USB 线。烧录工具参数里存储介质必须与实际一致（板载 NAND 选 nand）。

> 来源：官方文档 Appendix/rdk-command-manual/cmd_rdk-miniboot-update（https://developer.d-robotics.cc/rdk_x_doc/Appendix/rdk-command-manual/cmd_rdk-miniboot-update）、FAQ/hardware_and_system Q39、社区帖 30925、社区帖 28030

### 预防

**升级顺序有讲究**，官方在多个帖子里重复了同一句建议：

> 目前建议更新的方式是在可以进入 Ubuntu 系统中，更新 miiniboot 后，烧录最新系统，然后在最新系统中再更新一次 miniboot，避免系统和 miniboot 版本差异过大导致无法启动。

即：**先升 Miniboot → 再刷系统 → 再升一次 Miniboot**。这个「升两次」的顺序看起来多余，实际是为了避免「新系统 + 旧 Miniboot」这个最危险的组合。

> 来源：社区帖 28135、28919、29063、29124、31310 中官方回复均给出同一建议

### 2.8 内核解引用空指针 panic，换卡、换电源、升 Miniboot 都无效

### 现象

```
[ 14.756590] vs-dc 3e000000.dc8000Nano: Failed to get aux devices
[ 9.510712] aicbsp: sdio_err: : bus down
[ 15.233738] Unable to handle kernel paging request at virtual address 0000000000100108
[ 15.287630] Internal error: Oops: 0000000096000004 [ #1 ] PREEMPT SMP
Kernel panic - not syncing: Oops: Fatal exception
```

调用栈指向 `__device_attach_driver → bus_for_each_drv → deferred_probe_work_func`。

> 来源：社区帖 35112（https://forum.d-robotics.cc/t/topic/35112）

### 根因

崩溃点在**延迟设备探测（deferred probe）**里，说明某个硬件驱动在初始化时空指针解引用。前置的 `vs-dc ... Failed to get aux devices`（显示控制器）和 `aicbsp: sdio_err: : bus down`（Wi-Fi SDIO）是两条强线索：某个外设没探测成功，其驱动的 probe 函数在拿不到资源时没有做判空。

但这条与 2.1 的区别在于：**用户已经排除了所有软件侧与供电侧因素**——官方电源、最新 Miniboot（串口日志显示 `BL2: Built : 19:55:47, Jan 22 2026`）、最新镜像、闪迪 A1 卡、无外设，仍然在启动约 15 秒时崩溃。

此时官方给出的结论是换货：

> 您好，建议联系销售渠道进行换货

也就是说，**当崩溃点在硬件驱动探测链、且所有可换件都换过之后，剩下的可能只能是板子本身**。

### 处置

自查清单（全部做完再联系渠道）：

```bash
# 1. 确认 Miniboot 版本（看串口第一屏的 U-Boot 日期，或）
sudo rdkos_info

# 2. 确认系统版本
cat /etc/version

# 3. 尝试屏蔽可疑驱动（临时验证，需在 U-Boot 命令行操作）
#    Hobot> editenv bootargs
#    追加 modprobe.blacklist=aic8800_fdrv
#    Hobot> saveenv
#    Hobot> boot
```

如果是保修期内，凭完整串口日志 + 板子序列号（标签 SN）+ 购买渠道联系售后。

### 预防

**在拆封后第一周内做「满载 30 分钟 + 反复冷启动 10 次」的稳定性验证**，有问题的板子尽早发现。这个动作能避免项目中期才发现板子本身有问题。

### 2.9 烧录时弹「安装时出错」

### 现象

社区帖中为截图，用户的文字描述是：「烧写弹出『安装时出错』」。

> 来源：社区帖 28005（https://forum.d-robotics.cc/t/topic/28005）

### 根因

RDK Studio 通过 Type-C 闪连与板子通信时，「安装时出错」通常是 **PC 侧网络配置没配好**，而不是烧录本身失败。RDK Studio 的闪连依赖一个虚拟网卡，PC 需要有正确的 IP 配置才能和板子的 `usb0` 网段（`192.168.128.10/24`）通信。

帖子里的解决方法是「主要是配置好PC的网络IP」，另有用户反馈「多点了几次可以了」——后者说明这也可能是瞬态握手失败。

> 来源：社区帖 28005、官方文档 FAQ/hardware_and_system Q19（X5 闪连口默认 `192.168.128.10/24`）

### 处置

1. 确认 PC 侧虚拟网卡 IP 在同网段（如 `192.168.128.100/24`）；
2. 重插 Type-C 线，等待板子枚举完成再点烧录；
3. 若仍失败，改用 SD 卡烧录 + Rufus，绕开闪连链路。

### 预防

**烧录不要依赖闪连**。闪连适合日常调试传文件，烧录这种一次性重活优先走「读卡器 + Rufus」，链路最短、变量最少。

### 2.10 板子刷机后起不来，怀疑变砖

### 现象

用户描述：「这个板子应该是2020年最早一批旭日X3的板子，刷机刷的起不来了，有没有参考资料，和对应固件」。

> 来源：社区帖 34193（https://forum.d-robotics.cc/t/topic/34193）

### 根因

这条的价值在于**「变砖」这个词被滥用了**。绝大多数所谓变砖，实际是「Miniboot 被刷坏」或「卡上的引导内容被刷没了」，而板载的 BootROM 是掩膜在芯片里的，**不可能被刷坏**。

判据：能不能在串口看到 `SNOTICE: Welcome to Horizon X5 ASIC BOOTROM`。

- 看得到 → BootROM 活着，板子没砖，问题在 BL1 之后（Miniboot/卡）；
- 看不到 → 才需要考虑硬件层面。

帖子里的板子是早期 X3（X3R1C09R 标签），与 X5 的固件不通用，这一点也常被混淆。

### 处置

按启动链自下而上恢复：

1. **接串口**（921600-8-N-1），上电看有没有 `SNOTICE`；
2. 有 `SNOTICE` 但停在 `main bl2 fail` → 重烧 Miniboot（见 2.7 情况 B）；
3. 能到 U-Boot 但起不来 → 重刷 SD 卡系统镜像；
4. 用最小启动固件兜底：

```bash
wget http://sunrise.horizon.cc/downloads/miniboot/disk_nand_minimum_boot_2GB_3V3_20230413.img
```

烧到 TF 卡，插卡后**按住复位键上电**再松开。

5. 全部无效 → 联系渠道。

> 来源：社区帖 34193

### 预防

- **刷机前先确认板子型号**（X3 / X3 Module / X5 / X5 Module 的固件互不通用）；
- 保留一份当前的 Miniboot 版本号（`sudo rdkos_info` 里的 `RDK Miniboot Version`），出问题时能对比；
- 刷机前把串口接好并开始录日志——**这是唯一能在「变砖」后还告诉你真相的通道**。

## 三、常见误区

1. **「烧录工具说成功就是成功了」**。工具只验证写入完成，不验证可引导。换 Rufus 重烧是这条的最短路径。
2. **「起不来就是镜像问题，重刷就好」**。如果串口停在 `main bl2 fail`，重刷 SD 卡一万次也没用——问题在板载 NAND 里的 Miniboot。
3. **「Miniboot 在 SD 卡上」**。错。Miniboot 固化在板载 NAND，重刷卡不会更新它。
4. **「重启解决不了就重刷，重刷解决不了就换板」**。中间还有一层：Miniboot 升级 + 换卡 + 换电源 + 换线。这一层能解决掉大部分「疑似坏板」。
