# 6.3 网络与远程登录故障

## 本章解决什么

「能 ping 通但 SSH 超时」「SSH 能用但 VNC 拒绝连接」「用着用着就断」「WiFi 图标一直转」——网络类故障的难点不在修，而在**分清是哪一层断了**：物理链路、IP 配置、服务进程、还是系统本身已经不稳定。

本章按「从下往上」排列：先确认板子和电脑在不在同一个可互通的网络里，再确认 IP 有没有取错，然后才是服务与稳定性。**大量「连不上」的根因根本不在网络配置，而在 IP 取错了网卡，或者供电不足以让系统撑住。**

## 6.3.1 先记住 RDK X5 的三张网卡与默认 IP

X5 同时存在三张网卡，各自的 IP 段完全不同。**取错网卡是 SSH 连不上的第一大类原因。**

| 网卡 | 用途 | 默认 IP（RDK OS 3.0.0） |
| --- | --- | --- |
| `eth0` | 有线以太网口 | `192.168.127.10/24` |
| `usb0` | 闪连（USB Device 虚拟网卡，Type-C 口） | `192.168.128.10/24` |
| `wlan0` | WiFi | DHCP 分配，随路由器变化 |

> 来源：官方文档 FAQ/hardware_and_system Q19「RDK X5 不同系统版本的网口的 IP 是什么？」

注意 `usb0` 的 `192.168.128.10` 是**只有插着 Type-C 线时才有意义**的地址。拔掉线改走 WiFi 后，必须换成 `wlan0` 的地址——这一步漏掉的案例在社区里反复出现（见 3.1）。

对照 RDK X3 的历史差异：X3 的 2.0.0 及以下版本有线网口是 `192.168.1.10/24`，2.1.0 及以上改成 `192.168.127.10/24`。跨型号抄 IP 会直接连不上。

> 来源：官方文档 FAQ/hardware_and_system Q18

## 6.3.2 故障条目

### 6.3.2.1 用 Type-C 闪连配好 WiFi、拔线后 SSH 就连不上了

### 现象

用 Type-C 线连上板子，配好 WiFi，然后拔掉线改走无线，SSH 就连不上。用户自述的排查过程：「原先连接的IP是usb0的192.168.128.10，是通过usb线提供的以太网（有线网络）IP」，改连 `wlan0` 的地址后依然不通。

> 来源：社区帖 28080（https://forum.d-robotics.cc/t/topic/28080）

### 根因

这里其实叠了**两个独立问题**，很容易被当成一个：

**第一个：IP 取错网卡。** 配 WiFi 时用的 `192.168.128.10` 是 `usb0` 的地址，拔掉 Type-C 线后这张网卡就没了，这个 IP 自然不可达。必须换成 `wlan0` 的地址。

**第二个（更隐蔽）：路由器开了客户端隔离。** 帖子里的用户最后发现，问题出在自己用的是**校园网**——这类网络的路由器普遍开启了 AP 隔离，同一个 SSID 下的设备之间不能互访。此时两块设备「确实在同一个局域网」，IP 也正确，但二层就被隔离了，`ping` 必然不通。用户最后通过手机热点中转解决，因为手机热点是本地设备自建的、没有隔离策略。

判据：**同一网段、能互相看到的 IP、但 `ping` 不通** → 优先怀疑 AP 隔离，而不是板子。

### 处置

第一步，确认网卡与 IP（板子上执行，不需要 sudo）：

```bash
ip addr show
ip route
```

第二步，在电脑上确认能到达：

```bash
ping <板子的 wlan0 IP>
```

第三步，若 `ping` 不通但确认同网段，换一个不受隔离的中转网络：

```bash
# 方案 A：电脑开热点，板子连电脑热点
# 方案 B：手机开热点，电脑和板子都连手机热点
# 方案 C：路由器上关闭「AP 隔离 / 客户端隔离」
```

第四步，若要用命令行连接 WiFi（不需要 sudo，`nmcli` 用当前用户权限即可）：

```bash
sudo nmcli device wifi rescan
sudo nmcli device wifi list
sudo wifi_connect "WIFI名字" "WIFI密码"
```

### 预防

**配完 WiFi 之后，先 `ip addr show` 抄下 `wlan0` 的地址再做远程连接**，不要复用配网时用的 `usb0` 地址。另外一个实用判据：如果 `ping` 返回的是 `Destination Host Unreachable`（本机 ARP 都拿不到），几乎一定是同网段但被隔离；如果是 `Request timeout`，才更可能是防火墙丢包。

### 6.3.2.2 SSH 一直连接超时，网段也对得上

### 现象

用户描述「电源线和串口线已经连接，网络状态已确认到如图所示」，SSH 仍然连接超时。

> 来源：社区帖 31104（https://forum.d-robotics.cc/t/topic/31104）

另一帖：「windows和RDK X5使用ssh/vnc连接超时」。

> 来源：社区帖 29124（https://forum.d-robotics.cc/t/topic/29124）

### 根因

官方人员给的判断很直接：

> 请检查板卡的所有网卡和Windows的所有网卡，存不存在IP地址冲突，MAC地址冲突的问题，一般都是这样的问题。

> 来源：社区帖 31104

机制上：RDK X5 有三张网卡（`eth0` / `usb0` / `wlan0`），Windows 侧可能同时有以太网、WiFi、VMware/VirtualBox 虚拟网卡、WSL 虚拟网卡、Docker 虚拟网卡。**只要两边有任何一张网卡落在同一 IP 或同一 MAC 上，路由就会选错出口**，表现就是「板子明明在线但连不上」。

典型触发场景：把板子固定 IP 设成 `192.168.127.10`，而 Windows 侧某个虚拟网卡恰好也在这个网段；或者 VM 的 NAT 网卡用了 `192.168.128.x`，和 `usb0` 撞车。

另一类：**版本问题**。同一帖的官方回复指出「一些问题在RDK X5的3.2.3的系统中已经修复」，并给出升级顺序建议。

> 来源：社区帖 29124

### 处置

Windows 侧列出全部网卡与地址：

```powershell
ipconfig /all
arp -a
```

Linux 侧：

```bash
ip addr
arp -n
```

对照三件事：

1. 有没有两个接口在同一网段；
2. 有没有重复的 MAC；
3. 板子的 IP 是不是被另一台设备占用（`arping` 探测）。

```bash
# 需要 sudo
sudo arping -I eth0 192.168.127.10
```

确认冲突后，改板子的固定 IP 到一个干净的网段：

```bash
# netplan 配置示例（X5 用 netplan）
sudo nano /etc/netplan/50-cloud-init.yaml
sudo netplan apply
```

### 预防

- **固定 IP 前先扫一遍网段**，避开 `192.168.127.x` / `192.168.128.x` 这两个 RDK 默认段；
- 关掉不用的虚拟网卡（VMware、VirtualBox、Hyper-V 的 vEthernet）；
- 若系统版本低于 3.2.3，先按 2.7 的顺序升级（先升 Miniboot → 刷系统 → 再升 Miniboot）。

### 6.3.2.3 网线直连板子连不上，WiFi 却正常

### 现象

用户描述「通过WIFI方式可以顺利连接，但是通过网线无法连接，网络是通畅的，wifi连接成功，证明烧录系统也是正常的，但就是连接不上」。用户还确认「我的ip和开发版的ip是在一个网段的，都处于192.168.11.X网段」。

> 来源：社区帖 32169（https://forum.d-robotics.cc/t/topic/32169）

### 根因

官方回复指向手册里的一个具体规定：**网口的固定 IP 是 `192.168.127.10`**。

也就是说，用户的 PC 在 `192.168.11.x`、板子的 `eth0` 在 `192.168.127.x`，两者根本不在同一网段——用户以为「都设了固定 IP 就同网段」，但板子那侧设的其实不是他以为的网段。

这里还有一个容易忽略的细节：**`eth0` 的默认静态 IP 与 `usb0`（`192.168.128.10`）只差一个数字**，抄错一位就永远 ping 不通。

### 处置

确认板子 `eth0` 的地址：

```bash
ip addr show eth0
```

PC 侧配成同网段（示例，`192.168.127.100/24`）：

```powershell
# Windows：网络和共享中心 → 适配器设置 → IPv4 属性
# IP: 192.168.127.100
# 掩码: 255.255.255.0
# 网关: 留空或 192.168.127.1
```

然后：

```bash
ping 192.168.127.10
ssh sunrise@192.168.127.10
```

### 预防

**网线直连场景下，PC 侧必须是 `192.168.127.x` 网段**，不要用 `192.168.11.x`、`192.168.1.x` 这类常见家用网段——那些是你接路由器时的网段，直连时板子并不在那个网段里。这是「WiFi 能用、网线不能用」最标准的解释。

### 6.3.2.4 SSH / VNC 用一段时间必断，断的瞬间外设也一起掉

### 现象

用户描述：「我使用RDK X5通过ssh远程连接时间长后容易中断，不管是使用vscode还是cursor还是MobaXterm都是如此」。补充信息：「掉的一瞬间我的外设也会同步掉线，而且usbhub的顺序还会乱，插拔之后就恢复了」。

> 来源：社区帖 34284（https://forum.d-robotics.cc/t/topic/34284）

另一帖现象更极端：「用MobaXterm_Personal_24.1两分钟后就会连接不上开发板，拔掉重新插上连接线可以连上，但是一两分钟后又连接不上」。

> 来源：社区帖 33113（https://forum.d-robotics.cc/t/topic/33113）

### 根因

这条的判据全在用户的补充里：**「掉的一瞬间外设也同步掉线，USB Hub 顺序还会乱」**。

如果只是 SSH 会话超时，外设不应受影响。外设同时掉、且 USB 拓扑重新枚举，说明**整个系统在这一刻发生了复位或严重降频**，SSH 只是受害者。这已经不是网络问题。

两类根因：

1. **供电不足**。X5 在 USB 满载 + WiFi 工作时电流需求会冲高，电源撑不住就压降，系统复位。社区里这条被明确记录过，35112 帖的引用列表里就把它标为「供电不足导致系统崩溃」。
2. **省电模式导致降频/休眠**。官方建议把系统模式调成 `performance`。

社区官方在 33113 的回复里也把「检查供电」列在 Type-C 闪连场景的第一步排查。

### 处置

先排除省电策略（**需要 sudo**）：

```bash
sudo systemctl mask sleep.target suspend.target hibernate.target hybrid-sleep.target
```

再把 CPU 调到性能模式：

```bash
# 需要 sudo
sudo cpufreq-set -g performance
# 或直接写 scaling_governor
echo performance | sudo tee /sys/devices/system/cpu/cpufreq/policy0/scaling_governor
```

确认频率确实上去了：

```bash
cat /sys/devices/system/cpu/cpufreq/policy0/scaling_cur_freq
sudo hrut_somstatus
```

若调完仍断，转供电排查（见 [启动供电与烧录故障 2.1](02-启动供电与烧录故障.md)）：换 5V/5A 电源、摘掉非必要 USB 外设、换质量好的 Type-C 线。

同时检查温度——95°C 会触发深降频，表现也是「网络卡住」：

```bash
sudo hrut_somstatus
```

### 预防

社区用户在 33824 帖里给出的实测结论可以直接照抄：

> 经过我的实际测试, 1电源要相当稳定, 2要有风扇不能过热 3也不能开成省电模式

> 来源：社区帖 33824（https://forum.d-robotics.cc/t/topic/33824）

**判断口诀：SSH 断的时候外设掉不掉？掉 → 系统层问题（供电/散热/降频）；不掉 → 网络层问题。**

### 6.3.2.5 VNC 报 The connection was refused by the computer，但 SSH 正常

### 现象

```
The connection was refused by the computer
```

用户描述「ssh登陆没问题，但VNCviewer会报错」。

> 来源：社区帖 28793（https://forum.d-robotics.cc/t/topic/28793）

### 根因

`Connection refused` 是 **TCP 层收到 RST**，含义很明确：**主机可达、端口没人监听**。这跟 `Connection timed out`（主机不可达）是完全不同的两类问题——很多人在这一步就走错了方向，去查网络，其实网络是好的。

VNC 端口没人监听，原因有三：

1. 烧的是 **Server 版镜像**，根本不含图形桌面和 VNC 服务；
2. VNC 服务没启动；
3. 服务启动了但监听在别的 display 号（端口 `5900 + N`）。

社区里一位用户的回复点出了关键：

> rdk 本身需要启动 x11vnc.service , 否则连不上

> 来源：社区帖 28793

### 处置

第一步，确认系统是 Desktop 版：

```bash
cat /etc/version
systemctl status lightdm
```

第二步，检查 VNC 服务状态：

```bash
systemctl status x11vnc
ss -lntp | grep 590
```

第三步，启动服务（**需要 sudo**）：

```bash
sudo systemctl start x11vnc
sudo systemctl enable x11vnc
```

第四步，确认监听端口后，客户端连 `IP:5900`（或 `IP:1` 对应 5901）。

官方 FAQ 也给出了同一套排查顺序：先确认 Desktop 镜像、再确认 VNC 服务已开启（2.1.0 及以上需在 `srpi-config` 里手动开启）、再确认端口与密码（默认 VNC 密码可能是 `sunrise`，或在 `srpi-config` 里设过）。

> 来源：官方文档 FAQ/hardware_and_system Q30「连接不上 RDK X3 的 VNC 远程桌面怎么办？」

### 预防

**先分清 `refused` 和 `timed out`**：

| 报错 | 含义 | 查哪一层 |
| --- | --- | --- |
| `Connection refused` | 主机在，端口没监听 | 服务进程 |
| `Connection timed out` | 主机不可达 | 网络/IP/隔离 |
| `No route to host` | 路由到不了 | 网段/网关 |

### 6.3.2.6 按网上教程改了 x11vnc.service，VNC 从此彻底连不上

### 现象

用户描述：「本来已经成功了，但是因为太卡顿，按照DeepSeek给的方法修改了，导致现在一直连接失败了」，改动内容是在 `/etc/systemd/system/x11vnc.service` 写了一整个 unit：

```
[Unit]
Description=x11vnc VNC Server
After=network.target

[Service]
User=sunrise
Group=sunrise
Environment=DISPLAY=:0
ExecStart=/usr/bin/x11vnc -display :0 -forever -loop -noxdamage -repeat -rfbport 5901 -shared

[Install]
WantedBy=multi-user.target
```

> 来源：社区帖 31356（https://forum.d-robotics.cc/t/topic/31356）

### 根因

这个 unit 有几个问题，任一条都能让 VNC 起不来：

1. **`User=sunrise` 但 `DISPLAY=:0`** —— `:0` 通常由 `lightdm` 启动的图形会话持有，普通用户 `sunrise` 未必有权限访问该 X server 的授权（`~/.Xauthority`）；换个用户跑 `x11vnc -display :0` 通常会报 `XOpenDisplay failed` 或权限拒绝。
2. **`Group=sunrise`** —— `sunrise` 用户可能不在自己同名组里，或该组不存在。
3. **`ExecStart` 路径与参数与系统自带的不同** —— RDK 自带的 `x11vnc.service` 已经处理好了授权与环境，手写覆盖会丢掉这些设置。

**最关键的一点：这是「本来能用、改完不能用」**，所以处置方向不是继续调参数，而是**恢复原状**。

### 处置

删掉手写的 unit，恢复系统默认（**需要 sudo**）：

```bash
sudo rm /etc/systemd/system/x11vnc.service
sudo systemctl daemon-reload
```

然后重装或重新启用系统自带的：

```bash
sudo apt install --reinstall x11vnc
sudo systemctl enable --now x11vnc
systemctl status x11vnc
```

如果 apt 源里没有对应的包，走 `srpi-config` 里的 VNC 开关重新打开一次——它会写入正确的 unit。

### 预防

**改系统 unit 之前先备份**：

```bash
sudo cp /etc/systemd/system/x11vnc.service /etc/systemd/system/x11vnc.service.bak
```

更重要的原则：**「本来能用」的系统，修改前先记录原始状态**。这类「照 AI 建议改坏了」的帖子在社区里不止一例，共同点都是没备份、也没记录改了什么。

> 若 VNC 卡顿本身要治，正确方向见 3.4 的性能模式与散热，以及官方 FAQ Q35 给出的「接 HDMI 欺骗器/虚拟显示器、降色深、降分辨率」思路，而不是改 unit 文件。
> 来源：官方文档 FAQ/hardware_and_system Q35「RDK X5 使用 VNC 远程桌面时感觉显示卡顿」

### 6.3.2.7 apt upgrade 之后 wlan0 消失了

### 现象

用户描述「昨天（2025/7/20）在RDK X5上使用apt update; apt upgrade更新完系统后就连不上wifi了！使用ifconfig -a 也看不到wlan0网卡，两个内存卡两个系统都是！有线网可以使用。」

> 来源：社区帖 31759（https://forum.d-robotics.cc/t/topic/31759）

### 根因

`ifconfig -a` 都看不到 `wlan0`，说明**无线网卡驱动或固件没加载**，不是「连不上」而是「设备不存在」。这与「能看到 wlan0 但连不上」是两个层级的故障。

`apt upgrade` 会连带升级内核与 `hobot-wifi` 相关包。若内核升级了而 Wi-Fi 驱动模块没跟着升（或固件包被替换成不兼容版本），模块加载就会失败，网卡不出现。这也解释了用户说的「两个内存卡两个系统都是」——两台都是同一时间做的同一次升级。

### 处置

第一步，查内核日志里有没有无线相关错误：

```bash
dmesg | grep -iE "wlan|wifi|aic8800|sdio"
```

第二步，查 RFKill 软阻塞（**需要 sudo**）：

```bash
sudo rfkill list
sudo rfkill unblock all
```

第三步，确认驱动包：

```bash
apt list --installed | grep -iE "hobot-wifi|aic8800|firmware"
```

第四步，若驱动确实缺失，走「升 Miniboot → 重刷系统 → 再升 Miniboot」的完整路径恢复，而不是继续 `apt` 折腾。

> 来源：官方文档 FAQ/interface Q7「开发板无线网络无法使用，使用ifconfig命令查询不到wlan0设备」给出了同一套顺序：先 `rfkill unblock`、再查 `dmesg | grep -i wlan`、再确认 `hobot-wifi` 包。

### 预防

- **`apt upgrade` 前先记下当前版本**（`sudo rdkos_info` 存一份），出问题能对比；
- 生产设备不要随手 `apt upgrade`，尤其不要单独升级内核；
- 需要在纯字符界面执行升级——官方明确提示「直接在图形桌面的终端中更新，有时在升级桌面自身相关的包时可能会导致显示中断或 X Server 重启，从而造成黑屏」。

> 来源：官方文档 FAQ/hardware_and_system Q20「系统执行 apt upgrade 时桌面环境黑屏怎么办？」

### 6.3.2.8 WiFi 图标一直转、连不上，或连上了但没网

### 现象

用户描述：「板子是电池供电，手机开热点，4个usb接口接满，一个雷达、一个超声波、一个控制板，一个口作为显示屏供电……现在开机之后右上角的wifi图标一直旋转，显示网络offline」，并补充「重启之后连上了一会又自动断开，有时直接就没连上，拔掉外设重新启动可重连上」。

> 来源：社区帖 32598（https://forum.d-robotics.cc/t/topic/32598）

另一帖：「我买了2台 rdk x5带散热片版本的，我现在连上wifi 通过ssh 连上去编程，一段时间就会掉网」。

> 来源：社区帖 33824（https://forum.d-robotics.cc/t/topic/33824）

### 根因

判据在「**拔掉外设重新启动可重连上**」这一句。这不是 WiFi 配置问题，是**供电被外设吃穿**：

- 电池供电，本身电压平台就不稳；
- 4 个 USB 口接满（雷达 + 超声波 + 控制板 + 显示屏供电），USB 总线电流需求极高；
- WiFi 模块是高瞬时电流负载，供电跌落时它最先掉。

于是表现为「WiFi 图标一直转」——它在反复尝试关联、失败、重试。而拔掉外设后供电压力下降，就能连上了。

社区官方在 33824 给出的第一条建议也是「推荐测试一下供电是否正常 5V5A」。

### 处置

按「减负载 → 换电源 → 再谈配置」的顺序：

```bash
# 1. 看当前 USB 负载（不需要 sudo）
lsusb

# 2. 关掉 WiFi 省电（需要 sudo）
sudo iw dev wlan0 set power_save off

# 3. 查看供电与温度
sudo hrut_somstatus
```

物理上：拔掉非必要 USB 设备，或改用**带独立供电的 USB Hub**，把外设的电流从板子上挪走。

### 预防

- 带多个外设（尤其雷达、显示屏）的场景，**不要用电池直接供板子**，用 5V/5A 适配器；
- 外设多的场景必须用独立供电 Hub；
- 判断口诀：**拔掉外设就好 → 供电问题；拔掉外设还一样 → 配置问题。**

### 6.3.2.9 以太网 UDP 通信掉包，网口连接灯会熄灭

### 现象

用户描述：「我通过网线将RDK X5和另外的控制器进行以太网UDP通信，在传输过程中一直存在掉包问题。经过测试人员测试发现，在传输过程中以太网口上的连接灯绿灯会熄灭，而换了另外一款产品，运行相同的测试代码没有出现掉包问题，已经测试了3块RDK X5开发板存在相同问题。」

> 来源：社区帖 33669（https://forum.d-robotics.cc/t/topic/33669）

### 根因

官方回复里给了两条关键信息：

> udp本身确实没有tcp协议稳定，网卡灯熄灭一般是接触问题

这两句拆开看：

1. **UDP 本身不可靠**。UDP 没有重传、没有拥塞控制，掉包是协议特性而不是故障。用 UDP 做控制指令时，应用层必须自己做序号/重传/超时，否则一定会「偶发丢帧」。
2. **网口灯熄灭指向物理层**。链路灯灭意味着 PHY 侧检测到链路断开（link down），这是物理层事件：网线水晶头没卡紧、线材质量差、接口氧化、或对端设备在省电。

「换了另一款产品同样代码不掉包」这一点很重要——它说明代码在别的硬件上能跑，但**不能反证 RDK X5 有缺陷**，因为两款产品的 PHY 芯片、驱动默认的 EEE（节能以太网）策略可能不同。反过来「3 块 X5 都是同样现象」说明这是共性，不是单板故障。

### 处置

第一步，抓统计计数定位丢在哪一层：

```bash
ip -s link show eth0
ethtool -S eth0
ethtool eth0 | grep -iE "speed|duplex|link"
```

重点看：`RX errors` / `RX dropped` / `overruns` / `carrier`。`carrier` 增长说明物理链路在反复 up/down，指向线材/接触；`overruns` 增长说明收包太快、缓冲区不够，指向软件。

第二步，关闭网卡节能与唤醒（**需要 sudo**）：

```bash
sudo ethtool -s eth0 wol d
sudo ethtool --set-eee eth0 eee off
```

第三步，换一根成品屏蔽网线，两端水晶头重新压接或直接换线，观察 `carrier` 是否还在涨。

### 预防

- 控制类通信优先用 TCP，或 UDP 之上加应用层可靠性（序号 + ACK + 重传）；
- 长期运行的设备定期采 `ethtool -S eth0` 的计数快照做趋势对比；
- 工业环境用屏蔽网线并做好接地。

### 6.3.2.10 串口登录突然找不到 COM 口

### 现象

用户描述：「已经在地瓜官网安装了CH340驱动，且之前已经成功串口登录过开发板……串口登录时却显示找不到com7」，附图中设备管理器检测不到设备。

> 来源：社区帖 29281（https://forum.d-robotics.cc/t/topic/29281）

### 根因

「之前能用、现在找不到 COM 口」——这是纯粹的**PC 侧枚举问题**，与板子无关。官方回复也确认「目前所描述的问题不涉及到板卡本身的问题」。

常见原因：

1. USB 转串口模块本身松脱或损坏；
2. Windows 驱动被系统更新替换掉；
3. **COM 口号变了**——同一模块插不同 USB 口，Windows 可能分配新的 COM 号（COM7 变 COM9），而终端软件还记着 COM7；
4. 用了「仅充电」线（无数据线芯）。

### 处置

Windows 侧逐项确认：

```powershell
# 列出所有串口设备
Get-PnpDevice -Class Ports
mode
```

1. 设备管理器 → 端口（COM 和 LPT），看有没有黄色感叹号；
2. 没有设备 → 换 USB 口、换数据线、换模块；
3. 有设备但号不同 → 在 MobaXterm/PuTTY 里改选实际 COM 号；
4. 驱动异常 → 从官方驱动目录重装：

```
https://archive.d-robotics.cc/downloads/software_tools/serial_to_usb_drivers/
```

连接参数固定为 **921600-8-N-1，无流控**。

> 来源：官方文档 FAQ/interface Q3

### 预防

**优先用设备名而不是 COM 号**：MobaXterm 里可以按设备描述选择。或者插固定那个 USB 口，避免重新分配。接线务必确认「模块 TX → 板卡 RX、模块 RX → 板卡 TX、GND → GND」——只接 TX/RX 不接 GND，会出现「能收不能发」或完全无输出。

### 6.3.2.11 srpi-config 里配置 WiFi 时报 There was an error running option S1 Wireless LAN

### 现象

用户描述：「烧录桌面版的系统后，连接显示器没有信号，使用串口连接wifi时，返回There was an error running option S1 Wireless LAN」。

> 来源：社区帖 29063（https://forum.d-robotics.cc/t/topic/29063）

### 根因

`srpi-config` 的 S1 选项本质是调用 `wpa_supplicant` / `nmcli` 的一套包装。报「error running option」通常意味着底层调用失败，而不是菜单本身坏了。导致失败的常见前提：

1. `wlan0` 不存在（驱动/RFKill 问题，见 3.7）；
2. 该会话没有 root 权限（`srpi-config` 必须以 `sudo` 启动）；
3. `wpa_supplicant` 服务状态异常；
4. 系统版本偏旧，该菜单项在该版本上有缺陷。

官方在同一帖（以及多个帖子）重复给出的处理是升级系统：

> 一些问题在RDK X5的3.2.3的系统中已经修复，可以在社区的上方的「资料」栏目来下载最新的系统。

> 来源：社区帖 29063

### 处置

先用 `nmcli` 绕开菜单直接配（**需要 sudo**）：

```bash
sudo nmcli radio wifi on
sudo nmcli device wifi list
sudo nmcli device wifi connect "SSID" password "密码"
nmcli connection show
```

配通之后再回头确认 `srpi-config` 是否恢复正常。

若 `wlan0` 完全不出现，按 3.7 处理。

### 预防

**图形菜单配不通时，直接用 `nmcli` 命令行**——它给的是明确的错误信息，比菜单的「error running option」可诊断得多。这是排障时的一条通用原则：**能用命令行就别用菜单，命令行会告诉你为什么。**

### 6.3.2.12 装了 RDK Studio 之后 PC 本地网络异常

### 现象

用户描述：「安装RDK Studio后，通过type c连接RDK X5，本地网络异常，重置网络设置后，本地网络正常了」。

> 来源：社区帖 31696（https://forum.d-robotics.cc/t/topic/31696）

### 根因

RDK Studio 为了走闪连（Type-C 虚拟网卡），需要在 PC 上创建/修改一个虚拟网络适配器，并把它加入路由表。如果它创建时占用的网段与 PC 现有网络（家里 `192.168.1.x`、公司内网等）冲突，或者它把自己设成了默认网关，PC 的上网路由就会被劫持。

用户「重置网络设置后恢复」正好印证了这一点：恢复动作清掉了被改动的路由/适配器配置。

### 处置

Windows 侧查看路由表，找出可疑条目：

```powershell
route print
Get-NetAdapter
Get-NetIPAddress
```

把 RDK Studio 创建的虚拟适配器**取消勾选「默认网关」**，或把它的接口跃点数调高：

```powershell
# 查看接口索引
Get-NetIPInterface
# 提高跃点数（数值越大优先级越低）
Set-NetIPInterface -InterfaceIndex <N> -InterfaceMetric 9999
```

### 预防

- 装完 RDK Studio 后先 `route print` 对比一次，确认默认路由还是原来那张网卡；
- 不用闪连时把该虚拟适配器禁用；
- 拔掉 Type-C 线后若 PC 网络仍异常，直接禁用对应的虚拟适配器。

## 三、常见误区

1. **「同一个 WiFi 下就是同一个局域网」**。校园网、酒店网、部分企业网开了 AP 隔离，同 SSID 的设备之间互不可见。这时该换中转网络，不是改板子。
2. **「IP 是我自己设的所以肯定对」**。三张网卡、两个相邻的默认段（`192.168.127.x` / `192.168.128.x`），抄错一位就永远连不上。永远用 `ip addr` 实测。
3. **「SSH 断了就是网络问题」**。看外设掉不掉——外设一起掉，是系统复位/降频，去查供电和散热。
4. **「`Connection refused` 和超时是一回事」**。前者是服务没起，后者是网络不通。方向完全不同。
5. **「照网上的 unit 文件改就行」**。`x11vnc` 涉及 X 授权，手写 unit 大概率起不来；改之前先备份。
