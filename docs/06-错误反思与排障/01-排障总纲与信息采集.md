# 6.1 排障总纲与信息采集

## 本章解决什么

RDK X5 的绝大多数「玄学问题」，最后都收敛到两类：**信息没采全就下结论**，和**跳过下层直接查上层**。本章给出一套分层的排障模型（供电 → 启动 → 系统 → 外设 → 应用），一套开机就该跑的取证命令，以及一份能直接贴到社区就能被接手的求助模板。

后面五章的所有故障条目，都建立在本章这套采集动作之上。**先把这一章的六条命令跑完，再翻后面的章节**——这能省掉一半的来回。

## 6.1.1 分层排障模型

RDK X5 从上电到应用跑起来是一条严格的依赖链。链上的每一层都会以「上层报错」的形式暴露自己，所以**必须自下而上验证**，不能从上往下猜。

| 层 | 判定问题 | 一句话判据 | 主要证据源 |
| --- | --- | --- | --- |
| L0 供电 | 电够不够、稳不稳 | 板子能不能稳定跑满 30 分钟不重启 | 电源规格、`dmesg` 里的 regulator/panic |
| L1 启动 | BootROM→BL1→BL2→U-Boot→kernel 有没有走完 | 串口能不能打到 `Starting kernel …` 之后 | 串口日志（921600） |
| L2 系统 | 根文件系统挂没挂上、服务起没起来 | 能不能 SSH/串口登录拿到 shell | `journalctl -b`、`systemctl` |
| L3 外设 | 摄像头/网卡/CAN/串口有没有被枚举 | `dmesg` 里有没有对应设备节点和 I2C 地址 | `dmesg`、`i2cdetect`、`ls /dev` |
| L4 应用 | 业务代码/模型/推理链路对不对 | 换官方示例能不能跑通 | 应用日志、TROS 节点日志 |

**分层模型的核心用法是「切一刀」**：当你不确定问题在哪一层，就找一个**已知能工作的最小组合**去替换。比如怀疑是模型问题，就用官方自带的 `.bin` 跑同一个示例；跑通了，说明 L4 之上的模型有问题，L0~L3 是好的。社区里大量「折腾三周没解决」的帖子，问题就出在没做这一刀。

分层还有一个反直觉的推论：**L0 的故障会伪装成 L2/L4 的故障**。板子供电临界时，系统可能在启动 15 秒后内核 panic，也可能在跑推理跑十分钟后网卡掉线，看起来像两个完全不同的 bug。判断方法是看**故障点是否随机漂移**——同一块板子同一个镜像，每次崩的位置都不一样（这次崩在调度器，下次崩在设备驱动探测），那基本就是 L0。

## 6.1.2 开机必跑的六条采集命令

下面六条按顺序跑，覆盖 90% 的定位需求。**需要 sudo 的都标了**。

### 6.1.2.1 命令 1：系统与内核版本

```bash
cat /etc/version
uname -a
```

`cat /etc/version` 给出 RDK OS 大版本（如 `3.0.0`）；`uname -a` 给出内核版本与编译时间。这两条决定了你后面该查哪一版文档——**这是全库最重要的版本分界点**。

> 来源：官方文档 FAQ/hardware_and_system（https://developer.d-robotics.cc/rdk_x_doc/FAQ/hardware_and_system）Q2「如何查看 RDK 板卡的系统版本号？」

### 6.1.2.2 命令 2：一键信息汇总

```bash
sudo rdkos_info
```

`rdkos_info` 一次性收集：硬件型号与 Board Id、CPU/BPU 温度与频率、BPU 负载、总/已用/空闲内存、ION 内存大小、RDK OS 版本、内核版本、Miniboot（U-Boot）版本，以及最新 30 行系统日志。

选项：

| 选项 | 含义 |
| --- | --- |
| `-b` | 基础模式，不收集系统日志 |
| `-s` | 简洁模式（默认），输出 30 行最新日志 |
| `-d` | 详细模式，输出 300 行最新日志 |
| `-v` | 显示版本信息 |
| `-h` | 显示帮助 |

> 来源：官方文档 Appendix/rdk-command-manual/cmd_rdkos_info（https://developer.d-robotics.cc/rdk_x_doc/Appendix/rdk-command-manual/cmd_rdkos_info）

**这一条的输出就是社区求助的硬通货**。社区里几乎每个官方回复都在要 `rdkos_info`，缺了它基本没人能接。

### 6.1.2.3 命令 3：温度、频率、BPU 负载

```bash
sudo hrut_somstatus
```

输出三段：`temperature`（CPU 温度）、`cpu frequency`（每个核的 min/cur/max）、`bpu status information`（BPU 的 min/cur/max 与 `ratio` 负载率）。

X5 实际上有**三路独立温度读数**（DDR / BPU / CPU），`hrut_somstatus` 一次全给出来：

```
temperature-->
DDR : 48.7 (C)
BPU : 47.6 (C)
CPU : 47.6 (C)
```

> 来源：官方文档 Appendix/rdk-command-manual/cmd_hrut_somstatus（https://developer.d-robotics.cc/rdk_x_doc/Appendix/rdk-command-manual/cmd_hrut_somstatus）

温度阈值（RDK 镜像默认，来自 Thermal 控制）：启动 80°C 即开机降频、95°C 触发 CPU/BPU 降频（CPU 最低 240MHz、BPU 最低 400MHz）、105°C 关机且不会自动重启。

> 来源：社区帖 35824（https://forum.d-robotics.cc/t/topic/35824）

### 6.1.2.4 命令 4：内核日志与上一次启动的日志

```bash
dmesg | grep -iE "error|fail|watchdog|reset|panic|oom" --color
journalctl -b -1 -n 100 --no-pager
```

`dmesg` 是本次启动的内核环形缓冲；`journalctl -b -1` 是**上一次启动**的日志——这是抓「跑着跑着死机」的唯一有效手段。**必须在重新上电后立刻执行**，否则 `-b -1` 会漂移到更早的一次。

### 6.1.2.5 命令 5：已安装的地瓜软件包清单

```bash
apt list --installed | grep hobot
apt list --installed | grep tros
apt show tros
```

`apt list --installed | grep hobot` 给出 `hobot-boot`、`hobot-bpu-drivers` 等核心包版本；`apt show tros` 给出 tros.b 元包版本（如 `2.0.0-20230523223852`），代表整个发行版基线。

> 来源：官方文档 FAQ/hardware_and_system Q2、FAQ/applications_and_examples Q11（https://developer.d-robotics.cc/rdk_x_doc/FAQ/applications_and_examples）

### 6.1.2.6 命令 6：磁盘与内存余量

```bash
df -h
free -h
```

嵌入式设备上「磁盘满」会以极其诡异的方式表现出来：编译报错、日志丢失、服务起不来、甚至 `apt` 装包失败。社区健康检查帖里就出现过实测的 90%（50G/58G）占用、只剩 5.7GB 的情况。

> 来源：社区帖 34467（https://forum.d-robotics.cc/t/topic/34467）

清理方式：

```bash
sudo apt autoremove && sudo apt clean
sudo journalctl --vacuum-size=100M
```

## 6.1.3 日志落盘

默认日志是易失的。要定位「偶发、跑一段时间才出现」的问题，必须先把日志固定下来。

### 6.1.3.1 串口日志落盘（最可靠）

板子起不来、SSH 连不上时，**串口是唯一的信息通道**。参数固定为 921600-8-N-1，无流控。Windows 下用 MobaXterm / PuTTY 的「Log to file」；Linux 下：

```bash
picocom -b 921600 /dev/ttyUSB0 --imap lfcrlf | tee ~/x5-boot-$(date +%F-%H%M).log
```

**上电前就开始录，一直录到故障发生之后**。这样 BL1/BL2/U-Boot 阶段的输出才不会被漏掉——而这几段恰恰是启动类故障的决定性证据。

### 6.1.3.2 内核日志持久化

`dmesg` 默认重启即丢。把 `journald` 改成持久存储：

```bash
sudo mkdir -p /var/log/journal
sudo systemd-tmpfiles --create --prefix /var/log/journal
sudo systemctl restart systemd-journald
```

之后 `journalctl -b -1` 才真正跨重启有效。注意这会让日志占磁盘，配合上面的 `--vacuum-size` 定期清理。

### 6.1.3.3 应用日志

TROS 节点日志在 `~/.ros/log/` 或 `/root/.ros/log/`。排查前先清空旧日志再复现：

```bash
rm -rf ~/.ros/log/*
```

> 来源：官方文档 FAQ/tros_ros（https://developer.d-robotics.cc/rdk_x_doc/FAQ/tros_ros）Q1

## 6.1.4 求助模板

社区提问的质量直接决定能不能被解决。下面是按官方 FAQ 的「预排查通用建议」整理的最小可用模板，直接复制填写。

```markdown
## 基础信息
- 板卡型号：RDK X5 / RDK X5 Module（看板子丝印或 rdkos_info 的 Hardware Model）
- Board Id：<rdkos_info 里的 Board Id = NNN>
- 系统版本：<cat /etc/version 的输出>
- 内核版本：<uname -a 的输出>
- Miniboot 版本：<rdkos_info 里的 RDK Miniboot Version，或串口日志第一行的 U-Boot 日期>
- 供电：<适配器规格，如 5V/5A 官方电源>

## 现象
- 期望结果：
- 实际结果：
- 复现概率：必现 / 高 / 中 / 低（大致百分比）

## 已做的操作
1. <做了什么，结果如何>
2. <做了什么，结果如何>

## 日志（附件）
- rdkos_info_YYYYMMDD.txt（sudo rdkos_info -d 的输出）
- boot_serial.log（串口完整启动日志，从看到 SNOTICE 那一行开始）
- dmesg.log（dmesg 全量）
- 应用报错原文（不要截图，要文本）
```

关键几条：

1. **报错给文本，不要给截图**。截图无法被搜索，也无法被复制进命令。
2. **`rdkos_info` 必给**。官方回复里出现频率最高的一句就是「请提供 `sudo rdkos_info` 的输出」。
3. **说明已试过什么**。这一条能避免别人重复你已经排除的路径。
4. **串口日志从第一行开始给**。从 `SNOTICE: Welcome to Horizon X5 ASIC BOOTROM` 开始，不要从「Starting kernel」截断——BL1/BL2 的信息全在前面。

> 来源：官方文档 FAQ/hardware_and_system Q41「RDK 相关问题进行预排查的通用建议有哪些？」、FAQ/toolchain Q1「使用算法工具链遇到问题，在提问时需要提供哪些信息？」

## 6.1.5 排障动作本身会踩的坑

下面 10 条不是「板子的故障」，是「**查故障的过程出错**」导致的误判。它们全部来自社区真实案例，且每一条都导致过整条排查方向走偏。

### 6.1.5.1 版本查询命令用错，误判系统版本

### 现象

```
cat: /etc/horizon_version: No such file or directory
```

> 来源：社区帖 35560（https://forum.d-robotics.cc/t/topic/35560）

### 根因

RDK 系统里**不存在** `/etc/horizon_version` 这个文件。查大版本的正确命令是 `cat /etc/version`；如果想看完整信息（含内核、Miniboot、软包清单），用 `sudo rdkos_info`。一些教程里提到的文件名会被模型或搜索引擎二次传播，形成「看起来很像但不存在」的路径。

### 处置

```bash
cat /etc/version
sudo rdkos_info
```

两条都是只读，不需要额外权限（`rdkos_info` 需要 `sudo` 才能读全量日志）。

### 预防

把 `cat /etc/version` + `sudo rdkos_info` 固化成肌肉记忆。凡是看到网上给的路径，先 `ls` 一下确认存在再 `cat`——**路径不存在时的报错和「文件存在但内容不对」是完全不同的两类问题**，混淆了就会拿错版本去对文档。

### 6.1.5.2 只看最后一行报错，错过真正的第一因

### 现象

跑 MIPI 摄像头示例，终端最后刷出来的是：

```
TypeError: a bytes-like object is required, not 'NoneType'
```

> 来源：社区帖 35422（https://forum.d-robotics.cc/t/topic/35422）

### 根因

这行 `TypeError` 是 Python 侧**最后**才炸的，真正的第一因在更前面。同一段日志里还有：

```
ERROR [GetImageFrame][0711]get chn from 1920x1080 failed
```

以及大量**纯噪声**：

```
Cannot open file /sys/kernel/debug/vpu/venc.========================= VDEC =========================
Cannot open file /sys/kernel/debug/vpu/vdec.========================= JENC =========================
Cannot open file /sys/kernel/debug/jpu/jenc.======================= Buffer =========================
```

`Cannot open file /sys/kernel/debug/...` 这三行是调试节点没挂载导致的，**和故障无关**，但它在日志里出现得早、又带 `Cannot`，极容易被当成根因。真正的链条是：取流失败 → `nv12_bytes` 为 `None` → `split_nv12_bytes()` 拿 `None` 去切片 → `TypeError`。

本贴里更隐蔽的一层：用户把 `open_cam` 的输出分辨率改成了 640x480，但后续代码仍在请求 1920x1080 通道，于是 `get chn from 1920x1080 failed`。

### 处置

倒着找**第一个**「业务语义上的失败」，而不是第一个带 error 关键字的行：

```bash
# 把噪声过滤掉再看
grep -v "Cannot open file /sys/kernel/debug" app.log | head -50
```

对 Python 侧，要在取帧处加判空，避免把「取流失败」翻译成一个毫无信息量的 `TypeError`：

```python
if nv12_bytes is None:
    print("Frame get failed, retry")
    continue
```

### 预防

看日志的顺序是「**从上往下找第一个业务失败点**」，不是「看最后一行」。凡是 `Cannot open file /sys/kernel/debug/...` 这类调试节点告警，先记下来但不要当根因。

### 6.1.5.3 日志本身读不到，误判为「没有日志」

### 现象

```
[ 13.110389] systemd-journald[277]: Failed to read journal file /var/log/journal/93376d30162346569ffd698a59b4b039/user-1000.journal for rotation, trying to move it out of the way: Text file busy
```

> 来源：社区帖 35560（https://forum.d-robotics.cc/t/topic/35560）

### 根因

`Text file busy`（ETXTBSY）表示有另一个进程正持有该日志文件。常见于：上一次 journald 还没退出、或另一个会话正在 `tail` 同一个文件。此时 `journalctl` 会给出不完整甚至空的结果，让人误以为「系统没记日志」。

### 处置

```bash
sudo systemctl restart systemd-journald
journalctl -b --no-pager | tail -100
```

若仍异常，直接看内核环形缓冲（不依赖 journald 落盘）：

```bash
dmesg --time-format iso | tail -200
```

### 预防

排障时**优先用 `dmesg`**，它不依赖 journald 的文件状态。需要跨重启追溯时才用 `journalctl -b -1`，用之前先确认 `/var/log/journal` 存在且可写。

### 6.1.5.4 磁盘被日志写满，故障表现成「什么都坏」

### 现象

编译报错、`apt` 装包失败、服务起不来，报错内容五花八门且互相矛盾，没有统一线索。

### 根因

根分区写满后，所有需要写临时文件/日志/锁文件的操作都会失败，但每个子系统给出的错误文案各不相同，于是看起来像「系统全面崩坏」。RDK X5 的 eMMC/TF 卡容量有限，`journalctl` 持久化 + 反复编译 + 模型文件堆积，很容易占满。

### 处置

```bash
df -h
sudo apt autoremove && sudo apt clean
sudo journalctl --vacuum-size=100M
```

### 预防

社区实测给出过 90%（50G/58G）、仅剩 5.7GB 的案例，并明确把「磁盘空间」列为应当提前预警的健康指标。养成习惯：**任何「多处同时报错」的故障，第一条命令先跑 `df -h`。**

> 来源：社区帖 34467（https://forum.d-robotics.cc/t/topic/34467）

### 6.1.5.5 编译被 OOM killer 杀掉，误判为「编译器 bug」

### 现象

编译大型项目（C++ 项目、ROS2 工作空间、`colcon build`）时进程被 `kill`，或出现内存不足相关日志，无编译错误明细。

### 根因

Linux 的 OOM killer 在物理内存不足时会杀掉占用最多的进程——通常正是 `cc1plus`、`ld` 这些编译器进程。表现就是「编译到一半突然没了」，且没有任何编译错误输出。板端 4GB 内存跑并行编译（`make -j8`、`colcon build` 默认并行包编译）很容易触发。

### 处置

先加 Swap（示例 4GB）：

```bash
sudo fallocate -l 4G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
swapon --show
free -h
```

开机自动挂载，在 `/etc/fstab` 末尾加一行：

```
/swapfile none swap sw 0 0
```

再降并行度：

```bash
make -j1
colcon build --executor sequential --parallel-workers 1
```

> 来源：官方文档 FAQ/hardware_and_system Q40、FAQ/applications_and_examples Q2（https://developer.d-robotics.cc/rdk_x_doc/FAQ/hardware_and_system）

### 预防

板端编译前先 `free -h` 确认余量；大项目优先在 x86 开发机上交叉编译，板端只做部署验证。

### 6.1.5.6 APT 源被换掉，所有包都「无法定位」

### 现象

```
N: Unable to locate package tros-humble
```

> 来源：社区帖 29046（https://developer.d-robotics.cc/t/topic/29046）、社区帖 29019（https://forum.d-robotics.cc/t/topic/29019）

### 根因

RDK 的软件包来自地瓜自己的 APT 源（`archive.d-robotics.cc` 等），不在 Ubuntu 官方源里。用户为了装别的软件换源、或在「重装 ROS2」过程中把地瓜源删掉后，所有 `hobot-*` / `tros-*` 包都会变成「无法定位」。这不是包不存在，是**源里没有**。

与之关联的第二种情况：**包名写错**。X5 上的 TROS 包名以 `tros-humble` 开头，而网上教程常常给 `tros-mipi-cam` 这种简称。

### 处置

先确认源文件里还有没有地瓜源：

```bash
cat /etc/apt/sources.list
ls /etc/apt/sources.list.d/
```

X5（Ubuntu 22.04 / jammy）的源条目形如：

```
deb [signed-by=/usr/share/keyrings/sunrise.gpg] http://archive.d-robotics.cc/ubuntu-rdk-x5 jammy universe
```

补回后：

```bash
sudo apt update
apt search tros-humble        # 先搜索确认真实包名
sudo apt install tros-humble-<具体包>
```

### 预防

不要为了装一两个第三方软件去改 `sources.list` 主体；需要时用 `sources.list.d/` 单独放。装任何 `hobot-*` / `tros-*` 包之前，先 `apt search` 确认真实包名——**「无法定位软件包」十次里有八次是包名不对，两次是源不对，几乎不会是包真的下架了**。

> 来源：官方文档 FAQ/hardware_and_system Q10「apt update 命令执行失败或报错如何处理？」

### 6.1.5.7 串口没接就重刷系统，把可诊断状态刷成不可诊断状态

### 现象

板子起不来，直接重刷镜像；刷完还是起不来，于是再刷，反复几轮后连串口都没输出了。

### 根因

重刷是**破坏性操作**，它会覆盖掉原本还能用于定位的证据（分区表、原镜像、U-Boot 环境变量）。而「起不来」的原因可能在 L0（供电）或 L1（BootROM 之前的固件），重刷对这两层完全无效——重刷一百次也一样。

### 处置

**顺序必须是：先接串口取证，再决定要不要重刷。**

串口连接参数：921600-8-N-1，无流控；接线是「模块 TX 接板卡 RX、模块 RX 接板卡 TX、GND 接 GND」。

```bash
picocom -b 921600 /dev/ttyUSB0
```

上电后应当看到：

```
NOTICE: Welcome to Horizon X5 ASIC BOOTROM - V4.1
```

看到这一行，说明 BootROM 活着，问题在 L1 之后；**看不到这一行**，说明问题在 L0 或板子本身，重刷无意义。

> 来源：官方文档 FAQ/interface（https://developer.d-robotics.cc/rdk_x_doc/FAQ/interface）Q3「开发板上电后，调试串口无任何日志显示，怎么办？」

### 预防

把「串口能不能出 `SNOTICE`」作为第一条判据。社区里也有板子「只有电源灯亮、串口也连不上」，最终是重新烧录固件后恢复的案例——但那是**在确认了串口无输出之后**才做的决定，不是一上来就刷。

> 来源：社区帖 32853（https://forum.d-robotics.cc/t/topic/32853）

### 6.1.5.8 没测温度就归因到「软件卡死」

### 现象

板子跑一段时间卡死、掉网、重启；日志里没有明确错误。

### 根因

X5 有三路温度读数（DDR/BPU/CPU），且默认策略是 80°C 降频、95°C 深降频、105°C 关机。**105°C 关机后不会自动重启**，表现就是「突然没了」。而降频到 240MHz 时，上层应用会表现为「卡顿/超时/掉线」，看起来像网络或软件问题。

更反直觉的一点：**总功率小不代表温度低**。官方 FAQ 明确写了「发热量小不代表温度会低」——芯片功耗不高但散热不良时，热量积聚同样会让表面温度快速升高。

### 处置

```bash
sudo hrut_somstatus
grep . /sys/class/thermal/thermal_zone*/type
cat /sys/class/thermal/thermal_zone*/trip_point_*_temp
```

确认当前实测温度与各 trip point 阈值。若已接近 95°C，先解决散热（加风扇/散热片），再谈软件优化。

> 来源：社区帖 35824（https://forum.d-robotics.cc/t/topic/35824）、官方文档 FAQ/hardware_and_system Q36

### 预防

把 `sudo hrut_somstatus` 加进「跑长时间任务前必跑」的清单。**不要用「5-10W 的总功率」去反推是 DDR 过热还是 CPU 过热**——SoC 没有分模块功耗读数，只能看三路温度实测值。

### 6.1.5.9 I2C 节点不存在，误判为「摄像头坏了」

### 现象

```
Error: Could not open file /dev/i2c-1' or /dev/i2c/1': No such file or directory
```

> 来源：社区帖 35527（https://forum.d-robotics.cc/t/topic/35527）

### 根因

这个报错说的是「**这条 I2C 总线不存在**」，不是「摄像头不应答」。两者含义完全不同：

- `/dev/i2c-N` 打不开 → 该总线未被内核注册（设备树没使能、或板型就没有这条总线）；
- 能打开但扫不到地址 → 总线上没有设备（摄像头没接好、没供电、地址不对）。

把它当成后者去反复插拔摄像头，方向就错了。

### 处置

先枚举所有存在的总线，再逐个扫：

```bash
for i in 0 1 2 3 4 5 6 7; do
  echo "=== i2c-$i ==="
  i2cdetect -y $i 2>&1 | head -3
done
```

只有 `/dev/i2c-N` 存在的那几条，`i2cdetect` 的输出才有意义。

### 预防

看到 `No such file or directory` 就先去 `ls /dev/i2c-*` 确认总线存在性。**「设备节点不存在」和「设备不存在」是两个故障**，混淆会浪费大量时间在物理插拔上。

### 6.1.5.10 没确认版本口径就照最新文档操作

### 现象

照着官方文档改代码，接口对不上：`import` 失败、方法不存在、参数名不匹配。

### 根因

**RDKOS V3.5.0 是一条硬分界**：自 3.5.0 起，Python 算法推理、目标检测、语义分割等模块统一升级为 `hbm_runtime` 接口（基于 pybind11 实现，提供对 libdnn C++ 库的访问）；3.5.0 之前用的是 `pyeasy_dnn` / `hobot_dnn`，再往前的部署脚本里还有 `bpu_infer_lib`。

三者互不兼容。文档站默认展示最新版，所以一个 3.0.0 的板子照 3.5.0 的文档写代码，必然全线报错。

> 来源：官方文档 Release_Note（https://developer.d-robotics.cc/rdk_x_doc/Release_Note/release_note）「版本号：3.5.0」；社区帖 35476（https://forum.d-robotics.cc/t/topic/35476）

社区官方人员在回复里说得很直接：

> 由于 bpu_infer_lib 已停止维护，新模型及推理流程全面迁移至 hbm_runtime 库，请更新 rdk 系统版本到 3.5.0 以上

> 来源：社区帖 34823（https://forum.d-robotics.cc/t/topic/34823）

### 处置

先定版本，再选接口：

| RDKOS 版本 | Python 推理接口 | 示例目录 |
| --- | --- | --- |
| < 3.5.0（如 3.0.0 / 3.2.3 / 3.4.1） | `pyeasy_dnn` / `hobot_dnn`（部分脚本用 `bpu_infer_lib`） | 旧版 `/app/pydev_demo/` |
| ≥ 3.5.0 | `hbm_runtime` | 全量重写后的 `/app/pydev_demo/` |

```bash
cat /etc/version
```

### 预防

**每次开始写代码前的第一条命令就是 `cat /etc/version`。** 看到任何教程/示例，先确认它对应的版本，再决定照不照做。跨版本照抄是本仓库记录到的最常见的挫败源。

## 6.1.6 串口启动日志的分段判读

串口日志是排障的根证据，但它通常是几百到几千行，直接读会淹没在噪声里。正确的做法是按**启动链分段**，先定位「停在哪一段」，再看那一段的细节。

把日志按下面的标志行切开，一段一段看：

| 分段起点（标志行） | 这一段在干什么 | 段落内值得关注的行 |
| --- | --- | --- |
| `SNOTICE: Welcome to Horizon X5 ASIC BOOTROM - V4.1` | BootROM 启动，读 OTP、验签 | `otp exist: true/false`、`Manufacturer ID`、`Device ID` |
| `NOTICE: BL1: Booting BL2` | BL1 交棒给 BL2 | 任何 `ERROR:` 前缀的行 |
| `NOTICE: BL2: ...` → `NOTICE: ddr ready` | BL2 初始化 DDR | `ddr info:`、`matching profile:`、`ddr size:` |
| `U-Boot 2022.10+ (日期)` | U-Boot（Miniboot） | 编译日期即 Miniboot 版本；`Hit key to stop autoboot` |
| `Starting kernel …` | 内核开始执行 | — |
| `Booting Linux on physical CPU` | 内核已接管 | `Linux version`、`Machine model` |
| `ubuntu login:` | 系统起来，可登录 | — |

**判读的三个实用规则：**

**规则一：先看最后一段的起点。** 日志停在哪个标志行之后，问题就在那一段里。停在 `SNOTICE` 之后没有任何 `BL1` 行 → 卡在 BootROM 读存储；停在 `BL2` 段 → NAND/存储布局问题；停在 `Starting kernel` 之后的 panic → 内核或 rootfs。

**规则二：区分「NOTICE」和「ERROR」。** BootROM/BL1/BL2 阶段正常输出全部以 `NOTICE:` 开头。一旦出现 `ERROR:` 前缀，就是真的失败，例如：

```
ERROR: boot mode 5 main bl2 fail and switch to bakeup1…
ERROR: plat_error_handler -2
```

这两行意味着「四个 BL2 备份全部读失败」，是硬件/布局层面的问题，不是配置问题。

**规则三：内核段的 `[ 数字 ]` 是时间戳，先看它。** 内核日志形如 `[ 15.233738] Unable to handle kernel paging request ...`，方括号里是自内核启动起的秒数。这个数字很有信息量：

- 崩在 1~5 秒 → 早期初始化（时钟、电源管理、存储控制器）；
- 崩在 10~20 秒 → 外设探测与服务启动阶段（USB gadget、网卡、显示）；
- 崩在几分钟之后 → 运行期（散热、供电跌落、内存耗尽）。

社区帖 35112 的两次崩溃分别发生在 15 秒左右，且崩溃函数不同（一次 `update_load_avg`、一次 `__device_attach_driver`），这个「同时间窗、不同函数」的组合正是供电/内存不稳定的签名。

> 来源：社区帖 35112（https://forum.d-robotics.cc/t/topic/35112）、社区帖 35730（https://forum.d-robotics.cc/t/topic/35730）、社区帖 31743（https://forum.d-robotics.cc/t/topic/31743）

### 6.1.6.1 一个完整的判读示例

以 31743 帖的日志为例，把规则走一遍：

```
[ 14.589720] Kernel panic - not syncing: VFS: Unable to mount root fs on unknown-block(179,2)
[ 14.598171] SMP: stopping secondary CPUs
[ 14.621176] Rebooting in 5 seconds..
SNOTICE: Welcome to Horizon X5 ASIC BOOTROM - V4.1
```

三步判读：

1. **最后一段的起点**是 `Kernel panic`，说明内核已经起来了、走到了挂载 rootfs 这一步；
2. **时间戳 14.6 秒**，处于「外设探测与服务启动」之后、登录之前，符合「rootfs 挂载失败」的位置；
3. **`unknown-block(179,2)`** 里的 `179` 是 MMC 块设备主设备号、`2` 是分区号 → 是 `mmcblk1p2`，即 SD 卡第二分区。

结论：启动链前五段全部通过，坏在最后一环 rootfs。**处置方向是换卡/重刷，不是改 Miniboot、不是换电源。**

同一份日志里还能看到 `b300 61071360 mmcblk1`、`b302 60805120 mmcblk1p2`——说明卡被枚举出来了、分区表也读到了。这个细节进一步排除了「卡槽接触不良」，把范围收缩到「分区内容损坏」。

这个例子说明：**分段判读的价值不在于找到更多信息，而在于排除掉大量不相关的排查方向。**

## 七、常见误区

1. **「重刷能解决一切」**。重刷只能修复 L2（文件系统）层的问题。供电不足、BootROM/NAND 布局不匹配、硬件故障，重刷一百次也一样。而且重刷会覆盖证据。
2. **「报错最后一行就是根因」**。Python 的 `TypeError`、C++ 的 `terminate called after throwing`、ROS 的 `process has died` 都是**最后一环**，真正的第一因在更前面。
3. **「日志里有 error 就是问题」**。`Cannot open file /sys/kernel/debug/...`、`get camera calibration parameters failed`、`Unsupported op` 这三类在很多场景下都是**无害噪声**，官方 FAQ 甚至明确写了 `Unsupported op` 在性能可接受时可以忽略。
4. **「总功率小所以不热」**。X5 的三路温度必须实测，不能用功率反推。
